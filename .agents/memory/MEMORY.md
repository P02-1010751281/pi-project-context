# Project Memory

## Project
pi-project-context is a pi coding-agent extension that maintains durable project memory (MEMORY.md, CONTEXT.md) plus session context; written in TypeScript under extensions/project-context/.
Module layout: memory/store.ts (journal, atomic write, external-edit adoption), memory/report.ts (record_memory tool, refusal gating, /memory command), memory/status.ts (shared memory-status wording plus contextStatusLine), memory/pass.ts, memory/prompt.ts, memory/sections.ts, memory/journal.ts, memory/document.ts, memory/poison.ts, memory/backup.ts, shared/{config,llm,call-policy,lock,paths,migrate}.ts, handoff/*, autolearn/* (8 files), archive/* (4 files), plus handoff/handoff.ts as a test-only barrel.
The extension has 59 .ts modules totalling about 7,790 lines, all covered by the 2026-10-03 complexity audit plus three addenda.
Tests live in tests/ with run-all.mjs as entry (`node tests/run-all.mjs`, 15 tests, all green); they import the barrels, so a name-based coverage check undercounts.
Process artifacts live under .codestable/ (issues/, audits/, attention.md); each issue dir holds its design doc, fix note, review report and prompts/transcripts.
Runtime memory state lives in .agents/memory/ (tracked: .gitignore, MEMORY.md, CONTEXT.md, HANDOFF.md, project-context.json; untracked: memory.jsonl, session-logs/, backups, skill-candidates/); project-local skills live in .agents/skills/ and are tracked.
Docs live in docs/ (README.md index, architecture.md, configuration.md, handoff.md); CHANGELOG.md sits at the repo root.
Release model: a git tag consumed through a pinned entry in ~/.pi/agent/settings.json, installed into ~/.pi/agent/git/git.lentech.site/C02-1010751281/pi-project-context; the pin host ~/.pi is a separate pi-config repo (ssh://forgejo@git.lentech.site/C02-1010751281/pi-config.git).
There is a single git remote origin with two push URLs (forgejo ssh://forgejo@git.lentech.site/C02-1010751281/pi-project-context.git and github mirror ssh://git@ssh.github.com:443/P02-1010751281/pi-project-context.git), so one `git push origin master` reaches both.
Release state: v0.4.0 is latest (tag object 9e1b39d4acfd2cb5a8676d09df09d3c6c9bcae11, peeled commit f217e7d) and renames seven flat keys to mirror the command paths (`memoryEnabled`, `autolearnEnabled`, `handoffBudgetSummaryTokens`, `handoffBudgetRecentTokens`, `handoffThinking`, `handoffThresholdAuto`, `handoffLang`), collapses every toast to one prefix per layer and renames the status renderers; v0.3.2 made autolearn ask for a learned skill's body instead of pushing every body that fit; v0.3.1 let it supersede a skill it generated; v0.3.0 carried the one-command-per-layer surface, budget verbs, read-only session log and one-time legacy config migration; the ~/.pi pin is 8470e5b60cd1 and the installed clone was verified at describe v0.4.0.
The repo has no package.json; the release version exists only as a git tag.
Consumer repos on this machine (Quantum_Matrix, UniField, CipherCat, pi-custom-providers) are this extension's only runtime: they supply field evidence and receive local commits only.
The pi host bundle lives in ~/.pi/agent/install/releases/<version>/node_modules/@earendil-works/pi-coding-agent/dist/, with the active version in ~/.pi/agent/install/current-version (1.0.2 on 2026-10-04) and pi's own docs/ (skills.md, settings.md) beside it.
User surface is five slash commands (/project-context umbrella, then one per layer: /memory, /handoff, /autolearn, /session-log), all documented in docs/configuration.md, which also owns the entry-point relationship section.
Master stands at commit 1367027 (2026-10-05), which adds only the progressive-disclosure design doc on top of the v0.3.1 release lines.

## Invariants
External-edit adoption carries the prompt-time loadMemory().text as basisKey and refuses to publish a reply whose basisKey no longer matches current effective content.
Both sides of the basisKey comparison go through memoryComparisonKey with empty guards; a file holding only the header is a real edit, only zero-byte/whitespace counts as cleared.
On refusal nothing publish-side runs: no overflow copy, no cap/section-cap/poison errors.log line, no shortened log line, no removal warning, no publish toast; all sit behind one gate.
Callers that do not pass basisKey (migration, legacy tests) must stay byte-identical.
The fix never re-runs the model call: a stale reply is discarded and the next scheduled pass consolidates from the surviving content.
Stale detection uses memoryComparisonKey, so mtime-regressed or same-mtime external edits stay invisible by design (accepted residual).
When the pre-publish recheck fires, the newer bytes are appended to the journal before returning.
Independent review runs one round per frozen revision, in a /tmp sandbox copy with before/after zero-write proof against the live tree.
A review finding that asks for a new mechanism must first cite a field fact from this repo; with no field fact it goes to the non-goals instead of into the design.
Removing a user-facing command, verb or knob needs a design doc plus a field fact; because command usage is not measurable from artifacts, a nobody-uses-it removal is not justified, while a machine-checkable ground (an output another entry point reproduces byte-for-byte) is.
A mechanism may only be called justified or newly built if it traces to a field fact: an errors.log line, a journal line, a success artifact, or a reproducible probe; otherwise it is a residual or non-goal.
A zero-hit logError key proves the error did not occur, not that the mechanism never ran; look for success artifacts too.
Every feature toggle funnels through setFeature in shared/config.ts; since v0.3.0 all four features carry on|off in their layer command, the umbrella's on|off is the target-less batch, and only --no-project-context disables the extension.
Consumer-repo artifacts are read-only field evidence: cite them in .codestable audits only and never persist their measurements or volatile state into MEMORY.md, CONTEXT.md, docs/ or CHANGELOG.md; naming the repo and who owns an open item is fine; pi-generated artifacts (HANDOFF.md, session-logs/) are session state, not curated memory.
The consolidation prompt states the cross-project boundary twice (rule next to the secrets/filler rule, and as the caption opening <recent-conversation>); acceptance requires later renders to show zero foreign measurements.
The autolearn prompt adds two rules after a generated skill body held a consumer repo's measurements: a skill writes only this project's facts, and a check states a shape, never a measured value; the description stays one short line because descriptions are injected into every session.
The autolearn pipeline may supersede a skill it generated and nothing else: every skill a pass writes carries a body provenance marker (`<!-- autolearn-generated: … -->`, body not frontmatter, because pi injects only name/description/path and unknown frontmatter keys are undefined behavior), gate and write path both read that marker off the artifact, and only a marked project skill's name may be reused; hand-written, legacy-imported and global skills are refused by name exactly as before (v0.3.1).
Provenance lives in the artifact rather than a tracked side list: a marker dies with its skill, so a name freed by a deletion and later taken by a hand-written skill cannot be mistaken for one this pipeline wrote; a name list would need a content fingerprint to close that hole, and a fingerprint would also block updating a learned skill a human had since edited.
All seventeen project skills carry the marker by owner convention that this repo's skills are distilled output, never typed by the owner (commit 0ca0d91); that is provenance by naming, not by per-file artifact.
Autolearn pulls a learned skill's body on request instead of pushing every body that fits (v0.3.2, 997447a): the first-look prompt carries no skill body at all, the model asks by name with `inspectSkill` (at most two, the cap enforced in code because `maxItems` is not guaranteed), and the follow-up attaches whole bodies under `AUTOLEARN_SHOWN_BODY_CHARS = 20000`.
The set of names a pass actually rendered is one computation read by two guards - the gate in candidate.ts over the inventory and the write path in pass.ts over the file - so a one-sided mutation of either leaves the live-path refusal green; the candidate path has only the gate, so its two assertions are the ones a single mutation reddens. A learned name is therefore overwritable only in the pass that showed its body, and a request for a name that is not a learned project skill comes back as "not shown" instead of silently doing nothing.
Measured on 2026-10-05, the four injected bodies are adaptive-handoff-threshold-review 3,238, audit-claim-verification 9,272, auxiliary-alert-storm-triage 3,379 and gate-probe-mutation-check 2,754 (18,857 total), against an inventory block of 3,594, a prompt of 32,057 characters with bodies and 13,149 without (59% of the prompt is learned bodies).
The autolearn auxiliary call is a single completion offering only RECORD_SKILL_TOOL (pass.ts:102) with no tool loop, so the writing model cannot read skill files itself; any on-demand body fetch must be injected by the extension, and the existing `inspect` backtrack round is the shape to reuse.
pi's own skill spec blesses bundled resources: a skill directory may carry references/ and the executing agent reads them on demand by path relative to the skill directory (docs/skills.md:5,18,34,39,45 under the managed install tree), so layering is a sanctioned pi pattern, not an invention of this pipeline.
A design's code-size estimate runs low on this codebase (the external-edit design came in about 1.7x low because report.ts needed a larger gating restructure); budget implementation accordingly.
A memory render draws on the session's own context as well as the journal, so external state deleted by hand can come back in the next render: re-check the boundary at every render commit and treat a prompt-level boundary line, not hand cleanup, as the durable fix.
Project memory carries only durable, verifiable statements: no sibling commit distances, no sibling memory file sizes, no other projects' research values, no line numbers into MEMORY.md itself.
A field fact that needs a home goes into the audit that used it; a fact with no home stays out rather than being parked in this repo's memory.
Repository docs split by kind: architecture.md holds semantics only, field incidents belong in .codestable audits, and version-visible behavior changes belong in CHANGELOG.md.
docs/*.md prose is wrapped at sentence boundaries with no line exceeding 160 characters, and a formatting-only rewrite must be proven content-identical (whitespace-normalized) before it is committed.
Skill descriptions under .agents/skills/ are injected into every session's system prompt, so each stays one short what-plus-when line of at most 170 characters, with step-by-step prose left in the SKILL.md body.
pi allows a skill name of at most 64 characters and a description of at most 1024, a skill whose frontmatter has no description is not loaded, and name equal to directory is the portable choice; pi injects only name, description and path at startup, never the body, so autolearn provenance goes in a body comment.
pi's RegisteredCommand exposes only name, description, getArgumentCompletions and handler with no alias field, so a command rename here is either a hard cut or a second registration, matching the repo's no-alias, no-notice rename policy.
The command surface keeps one fact per name and one owner per fact: a parameter lives with the layer that changes it, the umbrella keeps only what two or more layers share, and /context retired in v0.3.0 with its lines split by ownership; the CONTEXT.md line comes from one shared contextStatusLine() on both sides, and since v0.2.3 the umbrella's first line is Features:. See .codestable/issues/2026-10-04-command-surface-convergence/command-surface-convergence-design.md.
The four layers name "run it now" differently on purpose (`/memory update`, `/session-log write`, `/handoff now`, bare `/autolearn`): each verb says what that layer does, so this is decided rather than drift.
Config keys mirror the command path that changes them, and the rename rode the same one-time migration as the legacy layouts: an old flat name folds into the new one, the new name wins when both are present, an old value that is junk falls back to the default, and a rewrite drops the old name. `legacyConfigPatch` is the only place that knows an old name, so a read path never grows a fallback term. Six renamed keys were shared with dsh, which means the two config surfaces now differ and dsh has to adopt the new spellings.
A toast carries one prefix per layer and does not repeat the layer after it (`Memory: updated <file>`); `Usage:` lines and the multi-line `/project-context status` labels are deliberately outside that rule, and `/memory` and `/project-context status` now print the same `Memory: ...` status line.
Vocabulary rules, their terminal states and the audit history live in `.codestable/reference/vocabulary-conventions.md`; a vocabulary change updates that file, the code, docs/CHANGELOG and this render in the same round, because v0.3.0 renamed the handoff budget verbs but left "Auto summarize target" in a notification until b869be3 fixed six strings at once.
/session-log's bare call is read-only (status line plus session index and logs paths) and writing moved to an explicit `write` verb, because pi already archives at turn_end, agent_settled and session_shutdown; the volume is in the archives, so trimming it is a retention question, not a command-surface change.
Curated surfaces must hold no dead module pointers: every extensions/project-context/*.ts reference in .agents/skills and docs resolves, while .codestable/ frozen records deliberately keep their pre-split paths.
Commit with explicit pathspecs and never `git add -A`: a pending memory render otherwise rides into an unrelated commit.
Autolearn candidates under .agents/memory/skill-candidates/ are untracked pipeline state, so a candidate still tracked after promotion is an anomaly; the promoted skill drops the evidence comment, which remains only in the candidate.
Before a consumer repo's pi-rendered MEMORY.md is committed or merged, HEAD's curated facts must be shown to survive in the render; a render that dropped them is left uncommitted and reported.
Design docs get status: design-frozen once implemented, and the banner records the implementing commit next to the revision number.
Only origin is pushed to (both push URLs); release tags are never moved, and release docs land in a separate commit from the tag.
Release evidence for a behavior-changing version must state that `pi update --extensions` requires a restart and record the tag object and peeled commit, both push URLs, the pin commit and the installed clone's HEAD/describe; see .codestable/issues/2026-10-05-autolearn-learned-skill-supersede/release-v0.3.1-evidence.md.
The ~/.pi pin host is the pi-config repo; a pin bump is its own commit there, and when that remote has advanced the bump is landed with pull --rebase and never a force push.
.agents/memory/MEMORY.md is tracked and committed deliberately in the `docs(memory): refresh the memory render` style; a render gets its own commit, is never bundled with audit or code changes, and a deliberate refresh also re-audits the render for stale facts.
The extension writes the whole config document, so key presence in project-context.json proves nothing about knob usage; only a value differing from DEFAULT_CONFIG counts.
Config compatibility is a one-time migration, not a read path: the pre-unification nested layout, <memory>/autolearn.json and the global ~/.pi/agent/auto-handoff.json are folded into flat keys on a project's first config load, written back as a full flat document under the cross-process lock; only legacyConfigPatch() knows those shapes, so a key added after the unification cannot pick up a fallback term.
Test gates: `node tests/run-all.mjs` must stay green at 15/15, tests/external-edit-test.mjs holds 69 assertions, tests/autolearn-test.mjs holds 66 (10 pinning the v0.3.1 provenance boundary), and the issue's repro-write-ordering.mjs must exit 0.
Refusal-fix regression lines need negative controls, and mutation checks (remove a gate, revert a comparison) must turn exactly the intended assertions red.
Mutation checks on a shared formatter must change one side, never the shared function alone: editing memory/status.ts leaves the equality assertions green and proves nothing.
Audit residuals must be re-checked against tests/harness.mjs and the actual test files before being written into MEMORY.md.
Prefer strict=prefer over require for constrainedSampling: prefer degrades silently on routes without compat, require throws there.
Provider compatibility flags must not go into pi's models.json; declare them in a provider extension after probing the upstream.
saveConfig in handoff/settings.ts:62 builds an eight-key patch and merges through updateConfig, which re-reads the file under a lock and Object.assigns in place, so the handoff mirror has no lost-update problem.
External-edit adoption protects a user edit from being clobbered by pi; it does not stop an external writer from dropping curated content, so a merge-on-external-edit guard is a legitimate candidate but deliberately not built.
The archive contract: a stored session archive is a snapshot of the pi session source plus tail appends rebuilt when the source's size/inode/mtime stamp breaks; pi's session JSONL is not append-only, so archives legitimately hold bytes the source has lost and size divergence is by design.
Committing a consumer repo's working tree on owner instruction must record in the commit message whatever a non-pi rewrite of .agents/memory/* dropped; when merging lost content back, prefer merging into the current file over restoring the parent version.
Autolearn-approved skills under .agents/skills/ are tracked after review; a newly added skill that cites a claim this project has already superseded must be corrected before it is committed.

## Pitfalls
/tmp sandboxes are about 100-130 MB each; accumulated review copies filled the 16 GB tmpfs and broke `cp -a`; clean old sandboxes after archiving their transcripts.
Sibling journals showing two appends tens to hundreds of ms apart are one recordMemoryDocument call appending twice and are byte-identical; they are not evidence of concurrent writers.
memoryComparisonKey(empty) returns the bare header, so a file holding only the header refuses the reply; only zero-byte/whitespace lets the reply win.
The stale window is the span from the adopt read to the publish; the observed field case is an edit landing before the adopt read, leaving only a narrow post-read window as a residual.
Each review round that adds machinery adds surface for the next round to find problems, so unconverged growth is a signal to stop rather than to add more.
The superseded 415-line v5 design is archived with a do-not-implement banner; it must not be resurrected.
The installed clone lags the repo by design through the pin, so verify the pin and the clone's tag before claiming a fix is live; `describe --tags` in the clone needs a fetch --tags first.
Line numbers written into design docs, fix notes or MEMORY.md rot at the next render or commit; keep pointers file-level and re-measure with grep -n against the final revision.
`git ls-remote origin` queries only the fetch URL; verify the github mirror through the second push URL separately.
A failing `git add <path>` aborts the whole add, so a deletion already staged by an earlier `git rm` rides into the next commit; check `git show --stat` per slice.
Two behavior changes whose assertions share one test file cannot be split into two commits that are each green, so v0.3.0's config migration and command surface landed as one self-consistent commit (0399e04).
A provider 429 or quota message blocks only that route: commandcode/deepseek routes hit weekly limits while deepseek/deepseek-v4-pro served design rounds and code review.
pi's handoff summary goes through compaction.js SUMMARIZATION_PROMPT (nine heading lines); prompt.ts's zh map covers all of them.
On this machine's routes (commandcode/scnet, no compat declared, detectCompat defaults supportsStrictMode false) the extension sends the non-strict function tool, so structured output rests on the schema description, voluntary compliance and the post-hoc extractors.
The one real handoff failure chain in errors.log is a memory consolidation error thrown during session_shutdown that fails ctx.newSession (handoff/run.ts), so handoff success is coupled to memory not throwing at shutdown.
Do not read not-exported-to-tests as not tested: tests/handoff-test.mjs drives runHandoff through a newSession mock and maybeTrigger's settle trigger, so the earlier untested-residual claim was false.
Dead-code hunts must grep the named consumer, not only the symbol: memory/journal.ts::newestMemoryArchiveSync survived because its JSDoc cited loadMemorySync, which no longer exists anywhere.
Knob usage cannot be read from key presence: the extension writes all 23 keys into every project-context.json, and across the nine files found on this machine exactly one value differs from DEFAULT_CONFIG and none of the eight handoff knobs was ever touched.
Journal rotation has never fired in the field (largest memory.jsonl is 373 KB against a 512 KB threshold); cite it as preventive, not field-evidenced, unlike backups and errors.log rotation.
Attributing a field artifact to a module requires checking that the module can produce that path: the 19 zero-byte .lock files found across three repos cannot come from any current or historical lock target, and the Codex port uses fcntl.flock.
A suspicious filename in the field is not proof of ownership: migration-manifest.json exists in two consumer repos but appears nowhere in this extension's code or history, so migrateProjectState still has 0/9 field evidence.
A lossy external rewrite of a consumer repo's memory layer is real: the curated parent-commit lines were dropped while the file grew several-fold, so byte growth is not evidence of retained content.
pi's own re-projection of a consumer repo's memory file is that repo's main eroder, not external writers.
A consumer repo's working-tree MEMORY.md is usually such a render and silently drops curated facts, so test key survival against HEAD before committing or merging one.
Sessions archived from pi diverge from their source: of 306 comparable sessions 239 archives are prefixes and 67 are not, most of the 67 larger than the source, so the archive layer preserves content pi's file dropped.
All 55 [autolearn] errors.log entries are auxiliary-call failures (connection, balance, usage limits, timeouts, one stale extension ctx) and none is a mechanism error, so its two degradation branches have zero hits.
A pi re-render is produced from the extension's own memory state plus the model reply, not from the current bytes of MEMORY.md, so a host-side merge-back is not durable; the sibling-measurement re-leak recurred a third time, so hand-cleaning memory holds only until the next pass.
Adoption does work on an external merge-back: the write is journaled as an adoption before the next render runs, so merged lines reach the journal even though they are not durable across renders.
A prompt-content assertion cannot prove the model stopped re-introducing external state: the boundary sentence in memory/prompt.ts is only validated by checking later renders for sibling-repo measurements.
A full-tree pointer sweep finds dead pre-split module references of two kinds: curated surfaces are fixed, while the ones under .codestable/ are frozen records and must not be fixed.
Machine-bound-path sweeps need judgement: HANDOFF.md's absolute repo paths are pi-generated session state, tests/handoff-test.mjs's paths are fixtures, and tests/harness.mjs's legacy pi path is an intentional fallback.
Sweep .agents/memory/skill-candidates/ as well as .agents/skills/: a tracked candidate carried hard-coded sibling repo names and was already superseded by the promoted skill, so it was deleted.
A hand-written invariant does not survive a render: three facts written into MEMORY.md by hand were gone from the next render, which restored the older sentence verbatim, because a render is rebuilt from the journal plus the session's own context; editing the render is a stopgap.
Layering skills with references/ does not by itself cut the autolearn prompt: the 17 entry files still sum above the 20000-character budget, and a merge that only sees the entry leaves references stale, so on-demand fetch is the prerequisite.
Relaxing the autolearn gate's learned exception stays green under mutation, because the pass write-path check still rejects the hand-written name; the gate's own observable role is blocking a candidate file for a hand-written name, so a gate mutation there must assert that no candidate file appears.
Dropping the provenance marker in the shared promotedDocument reddens eight assertions at once, so it proves the marker is load-bearing but is not usable as a one-sided mutation check.
A synthesized skill body below MIN_SKILL_BODY_CHARS 160 is rejected as too short, so merge-test fixtures must be padded past that floor.
