# Project Memory

## Project
- pi-project-context is a pi coding-agent extension that maintains durable project memory (MEMORY.md, CONTEXT.md) plus session context; written in TypeScript under extensions/project-context/.
- Module layout: memory/*.ts (store, report, status, pass, prompt, sections, journal, document, poison, backup, injection, input), shared/*.ts (config, llm, call-policy, lock, paths, migrate, inject, lang, limits), handoff/* (no summary.ts since v0.4.1), autolearn/*, archive/*, plus handoff/handoff.ts as a test-only barrel; the Index below is the per-file map.
- Tests live in tests/ with run-all.mjs as entry (`node tests/run-all.mjs`, 15 tests plus a repo-hygiene check outside the count); they import the barrels, so a name-based coverage check undercounts.
- tests/harness.mjs loadNamespace is the same module-loading path production uses, so probes driven through it yield authoritative values (used for the DEFAULT_CONFIG census, the inventory measurement and the clip-shape probe).
- Process artifacts live under .codestable/ (issues/, audits/, features/, reference/, attention.md); each issue dir holds its design doc, fix note, review report, prompts/transcripts and release evidence; every sub-skill reads attention.md (report language, project fragment knowledge) before it starts.
- Runtime memory state lives in .agents/memory/ (tracked: .gitignore, MEMORY.md, CONTEXT.md, HANDOFF.md, project-context.json, errors.log; untracked: memory.jsonl, session-logs/, backups, skill-candidates/); project-local skills live in .agents/skills/ and are tracked.
- Docs live in docs/ (README.md index, architecture.md, configuration.md, handoff.md); CHANGELOG.md sits at the repo root.
- The repo has no package.json or manifest, so a release version exists only as a git tag plus the CHANGELOG heading.
- Release model: a git tag consumed through a pinned entry in ~/.pi/agent/settings.json, installed into ~/.pi/agent/git/git.lentech.site/C02-1010751281/pi-project-context; the pin host ~/.pi is a separate pi-config repo, where a pin bump is its own commit landed with `pull --rebase`, never a force push. Release state: v0.4.5 is latest, and every commit after it is docs/records only (no extensions/ or tests/ change), so the tag covers all code; per-section shares are targets, so a drop means the document reached maxMemoryChars, and the prompt layer asks for compression before deletion (v0.4.4); `pi update --extensions` needs a restart.
- There is a single git remote origin with two push URLs (forgejo and an ssh github mirror, both in .git/config); only origin is pushed to, a release tag is never moved, and release docs land in their own commit, separate from the tag.
- Release evidence for a behavior-changing version records the tag object and peeled commit, both push URLs, the pin commit and the installed clone's HEAD/describe.
- .agents/memory/MEMORY.md is committed as `docs(memory): refresh the memory render` in its own commit, never bundled with code or audits; a refresh re-audits the render for stale facts.
- Consumer repos on this machine (Quantum_Matrix, UniField, CipherCat, pi-custom-providers) are this extension's only runtime: they supply field evidence and receive local commits only.
- The pi host bundle lives in ~/.pi/agent/install/releases/<version>/node_modules/@earendil-works/pi-coding-agent/dist/, with the active version in ~/.pi/agent/install/current-version and pi's own docs/ (skills.md, settings.md) beside it.
- User surface is five slash commands (/project-context umbrella, then one per layer: /memory, /handoff, /autolearn, /session-log), all documented in docs/configuration.md, which also owns the entry-point relationship section.
- The dsh plugin is the sibling implementation of the same config surface: it mirrored all seven v0.4.0 renames and reads no alias, so the two config surfaces do not diverge in spelling; only the storage and the keys without a counterpart differ.
- Two modules append to the system prompt on every before_agent_start (see the report.ts and archive.ts index entries), both re-sent every turn and, since v0.4.1, both rendering section pointers instead of whole text.
- Each session's session-logs/<id>/ holds session.md (grep-friendly markdown rendering, header: canonical session.jsonl link plus entry count) and session.jsonl; the rendering is larger than the raw jsonl and can far exceed a context window, so a successor can only grep it or read it by offset.
- The extension ships pipeline-layer project skills under .agents/skills/ (notably pi-project-context-headless-runs, pi-project-context-release, pi-project-context-memory-cap-budget-change, pi-project-context-prefix-cache-analysis), tracked like any other project artifact.
- pi's memory layer updates at four registered points (report.ts): session_start (migration and config notices only), before_agent_start (injection, nothing written), agent_settled (automatic fire-and-forget consolidate, throttled by consolidateTurns 6 and consolidateIntervalMs 5min, both required), and session_shutdown (forced consolidate that bypasses the throttle, silent, inside the guard); only forceDedupeMs 15s dedupes a repeated forced pass, so the exit pass, not the throttled settle pass, is today what guarantees a session's tail reaches MEMORY.md.

## Invariants
- External-edit adoption carries the prompt-time loadMemory().text as basisKey and refuses to publish a reply whose basisKey no longer matches current effective content; both sides go through memoryComparisonKey with empty guards; nothing publish-side runs on refusal (no overflow copy, no cap/section-cap/poison log line, no shortened log line, no removal warning, no toast), callers without a basisKey stay byte-identical, the model call is never re-run, the stale reply is discarded and the next pass consolidates from surviving content, and a pre-publish recheck appends the newer bytes to the journal before returning (memory/store.ts).
- Stale detection uses memoryComparisonKey, so mtime-regressed or same-mtime external edits stay invisible by design (accepted residual); memoryComparisonKey(empty) returns the bare header, so a file holding only the header refuses the reply and only zero-byte/whitespace lets the reply win; the stale window is the span from the adopt read to the publish.
- Independent review runs one round per frozen revision, in a /tmp sandbox copy with before/after zero-write proof against the live tree; a review finding that asks for a new mechanism must first cite a field fact from this repo, otherwise it goes to the non-goals; a mechanism may only be called justified or newly built if it traces to a field fact (errors.log line, journal line, success artifact, reproducible probe), and a zero-hit logError key proves the error did not occur, not that the mechanism never ran.
- Every feature toggle funnels through setFeature in shared/config.ts; since v0.3.0 all four features carry on|off in their layer command, the umbrella's on|off is the target-less batch, and only --no-project-context disables the extension.
- Consumer-repo artifacts and field facts are read-only evidence with one home: cite them in .codestable audits, never persist their measurements or volatile state into MEMORY.md, CONTEXT.md, docs/ or CHANGELOG.md, and leave a fact with no home out rather than parked in this memory; pi-generated artifacts (HANDOFF.md, session-logs/) are session state, not curated memory.
- The consolidation prompt states the cross-project boundary twice (rule next to the secrets/filler rule, and as the caption opening <recent-conversation>); acceptance requires later renders to show zero foreign measurements.
- The autolearn prompt adds two rules after a generated skill body held a consumer repo's measurements: a skill writes only this project's facts, and a check states a shape, never a measured value; the description stays one short line because descriptions are injected into every session.
- The autolearn pipeline may supersede a skill it generated and nothing else: every skill a pass writes carries a body provenance marker (`<!-- autolearn-generated: ... -->`, body not frontmatter), gate and write path both read that marker off the artifact, and only a marked project skill's name may be reused; hand-written, legacy-imported and global skills are refused by name exactly as before (v0.3.1). Provenance lives in the artifact, not a tracked side list; all project skills carry the marker by owner convention (0ca0d91).
- Autolearn pulls a learned skill's body on request instead of pushing every body that fits (v0.3.2, 997447a): the first-look prompt carries no skill body, the model asks by name with `inspectSkill` (at most two, cap enforced in code), and the follow-up attaches whole bodies up to AUTOLEARN_SHOWN_BODY_CHARS = 20000.
- The set of names a pass actually rendered is one computation read by two guards - the gate in candidate.ts over the inventory and the write path in pass.ts over the file - so a one-sided mutation of either leaves the live-path refusal green; a learned name is overwritable only in the pass that showed its body.
- The autolearn auxiliary call is a single completion offering only RECORD_SKILL_TOOL (pass.ts:102) with no tool loop, so the writing model cannot read skill files itself; any on-demand body fetch must be injected by the extension, and the existing `inspect` backtrack round is the shape to reuse.
- The autolearn inventory is capped at 8000 characters and, when truncated, must say so: the injected list ends with `- (N more skill(s) not listed: the 8000-character inventory cap was reached)` (v0.4.3), so the model knows the list is partial and an operator can see the cap was hit (field-confirmed, audits §9.14).
- pi's own skill spec blesses bundled resources: a skill directory may carry references/ and the executing agent reads them on demand by path relative to the skill directory, so layering is a sanctioned pi pattern; one level deep is also in the spec, which is why the design allows only references/*.md.
- A design's code-size estimate runs low on this codebase (the external-edit design came in about 1.7x low); budget implementation accordingly.
- Before a pi-rendered MEMORY.md is committed or merged, the facts curated in HEAD must be shown to survive; a render that dropped a durable rule is restored before the commit (8baab6f did exactly that). A consumer repo's working-tree MEMORY.md is usually such a render and drops curated facts silently while the file still grows, so byte growth is no evidence of retained content and key survival must be tested against HEAD; there, pi's own re-projection, not external writers, is the main eroder.
- Per-section shares (0.2/0.4/0.25/0.15) are targets, not caps: renderMemoryDocument pools the slack and lends it to over-target sections by overage ratio, so entries are dropped only when the whole document reaches maxMemoryChars (v0.4.5). The pool must be measured against the document's real body (cap minus memoryStructureOverheadChars), never the floored target sum, or a memory that fits the cap still loses entries; two pinned properties hold it - content that fits drops nothing, any input stays under the cap. See the consolidation-keeps-entries issue.
- Project memory carries only durable, verifiable statements: no sibling commit distances, no sibling memory file sizes, no other projects' research values, no line numbers into MEMORY.md itself.
- Repository docs split by kind: architecture.md holds semantics only, field incidents belong in .codestable audits, and version-visible behavior changes belong in CHANGELOG.md; docs/*.md prose is wrapped at sentence boundaries with no line exceeding 160 characters, and a formatting-only rewrite must be proven content-identical (whitespace-normalized) before it is committed.
- Skill descriptions under .agents/skills/ are injected into every session's system prompt, so each stays one short what-plus-when line of at most 170 characters, with step-by-step prose left in the SKILL.md body.
- pi caps a skill name at 64 characters and a description at 1024, does not load a skill whose frontmatter lacks a description, and injects only name, description and path at startup - never the body - so autolearn provenance goes in a body comment; name equal to directory is the portable choice, and pi -p implies --no-session.
- pi's RegisteredCommand exposes only name, description, getArgumentCompletions and handler with no alias field, so a command rename here is either a hard cut or a second registration, matching the repo's no-alias, no-notice rename policy.
- The command surface keeps one fact per name and one owner per fact: a parameter lives with the layer that changes it, the umbrella keeps only what two or more layers share, its first line is Features:, and /context retired in v0.3.0 with its lines split by ownership; the CONTEXT.md line comes from one shared contextStatusLine() on both sides. See .codestable/issues/2026-10-04-command-surface-convergence/command-surface-convergence-design.md.
- The four layers name "run it now" differently on purpose (`/memory update`, `/session-log write`, `/handoff now`, bare `/autolearn`): each verb says what that layer does, so this is decided rather than drift.
- Config keys mirror the command path that changes them, and the rename rode the same one-time migration as the legacy layouts: an old flat name folds into the new one, the new name wins when both are present, a junk old value falls back to the default, and a rewrite drops the old name, so legacyConfigPatch is the only place that knows an old name. All seven v0.4.0 renamed names are shared with dsh, which reads no alias by design; the fallback differs - this project migrates an old name once on the first config read, a dsh profile holding one must be edited before that host restarts. The pi-only keys are handoffMode, handoffGuard and autolearnAt (dsh's counterpart is handoffPendingQuestion); handoffLang is not pi-only.
- The legacy-config compat layer is kept with no retirement window: two of the ten project-context.json files on this machine still carry all six pre-v0.4 names, so retiring the read-side migration would silently drop those projects' settings (addendum §2.2).
- A retired config key is not a rename and carries no alias: parseConfig keeps only known keys and updateConfig rewrites the whole document, so an unknown old key - or a retired verb such as /handoff thinking, (no pi-side reader; its dsh counterpart is uncheckable from here, audit R-2) - is ignored and disappears at the next write, and its command verb, completions and legacyConfigPatch entry retire with it. handoffThinking retired in v0.4.2; handoffBudgetSummaryTokens and /handoff budget summary stay because threshold.ts reads that value (naming fork closed as 'keep' on measured evidence).
- Both handoff modes obey the same physical drop floor (baseline + keep + MIN_DROP_TOKENS): fixed-ratio mode is refused by the same gate as adaptive mode, the status line names the refusal in fixed mode too (it used to echo a ratio that could never fire), and `/handoff threshold <ratio>` prints the status line so a dead configuration is visible when it is set (v0.4.3); the refusal now has field-confirmed live text.
- The threshold ratio range has one exported source (MIN_THRESHOLD_RATIO / MAX_THRESHOLD_RATIO) that the validator, the parseRatio parser, the usage sentence and the receipt advice all read; a mutation that moves the constant alone keeps the suite green only because the readers genuinely read it.
- A toast carries one prefix per layer and does not repeat the layer after it (`Memory: updated <file>`); `Usage:` lines and the multi-line `/project-context status` labels are deliberately outside that rule, and `/memory` and `/project-context status` now print the same `Memory: ...` status line.
- A cap/drop notice inlines samples of the dropped entries and carries no pointer to errors.log: the first cap event in the process may be a cut-only event, and that log line is written once per project per process, so a pointer would be false (v0.4.5, review rounds R3-R6).
- Vocabulary rules, their terminal states and the audit history live in `.codestable/reference/vocabulary-conventions.md`; a vocabulary change updates that file, the code, docs/CHANGELOG and this render in the same round.
- /session-log's bare call is read-only (status line plus session index and logs paths) and writing moved to an explicit `write` verb, because pi already archives at turn_end, agent_settled and session_shutdown; the volume is in the archives, so trimming it is a retention question, not a command-surface change.
- Commit with explicit pathspecs and never `git add -A`: a pending memory render otherwise rides into an unrelated commit; a failing `git add <path>` aborts the whole add, so check `git show --stat` per slice.
- Autolearn candidates under .agents/memory/skill-candidates/ are untracked pipeline state, so a candidate still tracked after promotion is an anomaly; the promoted skill drops the evidence comment, which remains only in the candidate. A candidate whose rule already has a durable home elsewhere is retired rather than kept pending, but only after its body is proven recoverable from .agents/memory/session-logs/ (its evidence session id is greppable there). Sweep .agents/memory/skill-candidates/ as well as .agents/skills/.

- Design docs are design-frozen once implemented, with the implementing commit in the banner; a frozen doc must not claim a mechanism that commit lacks, so the corrected doc lists the unbuilt part as a follow-up.
- A knob is useless only if it lacks a code reader: local non-use is usage evidence, not mechanism evidence; no reader -> deletion candidate, no local edits -> keep and record.
## Pitfalls
- A /tmp sandbox of the built repo needs node_modules for the extension's bare imports to resolve in a headless probe; the tests-only /tmp copies do not.
- /tmp sandboxes are about 180 MB each; accumulated review copies filled the 16 GB tmpfs and broke `cp -a`; clean old sandboxes after archiving their transcripts.
- A headless probe sandbox needs one directory per variant: the consolidation pass writes CONTEXT.md and session-logs/ into it at agent_settled, and `--mode json` never emits the system prompt, so injection shape cannot be read back from the run output and a run's own hallucination returns as CONTEXT.md bait.
- A python heredoc inside a bash script does not see the script's shell variables (`NameError: name 'D' is not defined`); write the literal path into the heredoc instead, and when a Chinese string match fails in a heredoc but works standalone, edit the file with the edit tool instead of the shell.
- The headless-runs skill's flag set is `-ne -ns -np` (`--no-tools` is `-nt`; `-np` is prompt templates, and mixing them once ran a round with no tools at all).
- Sibling journals showing two appends tens to hundreds of ms apart are one recordMemoryDocument call appending twice and are byte-identical; they are not evidence of concurrent writers. The earlier reading of the 10:48:14Z double op as the extension adopting its own render is retracted: the mechanism does not exist in one build, and the two ops were a genuine adoption plus the render.
- Each review round that adds machinery adds surface for the next round to find problems, so unconverged growth is a signal to stop rather than to add more; a 'single source' claim must be checked against every reader, since v0.4.3's round 11 found the validator and usage string still hardcoding the old numbers.
- The recurring review finding on this repo is a user-visible sentence promising what the code does not do (pool basis, cut-only reported as reaching the cap, a log pointer that may not exist); read every notice against the code path that actually writes it before freezing a revision.
- The superseded 415-line v5 design is archived with a do-not-implement banner; it must not be resurrected.
- The installed clone lags the repo by design through the pin, so verify the pin and the clone's tag before claiming a fix is live (`describe --tags` there needs a fetch --tags first; a grep for the fix's own symbol is the cheapest confirmation a merged fix is not yet running). A running process does not hot-swap modules, so expect mixed-version noise until the restart.
- Line numbers written into design docs, fix notes or MEMORY.md rot at the next render or commit; keep pointers file-level and re-measure with grep -n against the final revision.
- `git ls-remote origin` queries only the fetch URL; verify the github mirror through the second push URL separately, since another session can push to one URL only and leave the two forked.
- Two behavior changes whose assertions share one test file cannot be split into two commits that are each green, so v0.3.0's config migration and command surface landed as one self-consistent commit (0399e04).
- A 429 or quota message blocks only that route: commandcode hit weekly limits while the deepseek routes served design rounds, code review and the RPC field run.
- On this machine's routes (commandcode/scnet, no compat declared, detectCompat defaults supportsStrictMode false) the extension sends the non-strict function tool, so structured output rests on the schema description, voluntary compliance and the post-hoc extractors; the deepseek direct route caches within a session but whether a relay passes cache_control through is unverified.
- The one real handoff failure chain in errors.log is the 2026-09-22 line whose stack runs from the model call error through consolidate into ExtensionRunner.emit -> emitSessionShutdownEvent: the error escaped the session_shutdown handler into pi's runner, which is what the shutdown guard now covers; that guard cannot be pinned through the harness (every harness variant is caught inside the pass), so it stays recorded as defensive with the errors.log line as its field fact and now has its own issue dir. The incident supports accepting and recording the coupling rather than a new mechanism (one occurrence, none since the guard).
- Do not read not-exported-to-tests as not tested: tests/handoff-test.mjs drives runHandoff through a newSession mock and maybeTrigger's settle trigger, and one of its cases pins the A anchor for a split turn.
- Dead-code hunts must grep the named consumer, not only the symbol: memory/journal.ts::newestMemoryArchiveSync survived because its JSDoc cited loadMemorySync, which no longer exists anywhere.
- An export-surface probe (definition-file-external references) is the reliable dead-export detector; most `export`s are internal-only, so `export` alone proves nothing about an API's reach.
- Unreachable branches hide behind a boolean that every call site passes the same way: runHandoff's `force` was always true, so its three `!force` re-check blocks never ran; deleting them closed the 'estimatedAfter unreachable' review note.
- Knob usage cannot be read from key presence: the extension writes all 22 keys into every project-context.json, and across the thirteen files found on this machine exactly one value differs from DEFAULT_CONFIG and none of the seven handoff knobs was ever touched.
- Journal rotation has never fired in the field (largest memory.jsonl is 373 KB against a 512 KB threshold): cite it as preventive, not field-evidenced.
- Attributing a field artifact to a module requires checking that the module can produce that path: both leftover lock families trace to the Codex port's contextctl.py file_lock (O_CREAT, no unlink), not to this extension, and migration-manifest.json appears nowhere in its code or history.
- Sessions archived from pi diverge from their source (most are prefixes, some larger than the source), so the archive layer preserves content pi's file dropped; every [autolearn] errors.log entry is an auxiliary-call failure, none a mechanism error.
- A pi re-render is produced from the extension's own memory state plus the model reply, not from the current bytes of MEMORY.md, so a host-side merge-back is not durable even though adoption journals the merged bytes; the sibling-measurement re-leak recurred a third time, so hand-cleaning memory holds only until the next pass. It also draws on the session's own context, so external state deleted by hand can come back: re-check the boundary at every render commit, treat a prompt-level boundary line - validated only by later renders showing zero foreign measurements - as the durable fix, not hand cleanup.
- An inferred migration-key list is not evidence: my first legacy-config scan guessed the old names and produced a false positive; read legacyConfigPatch's RENAMED_KEYS and re-run with the names the code actually recognizes.
- The regression guard's logged counts (3/12/8/24) over-report against net entry changes of -1..-8, because its exact-match comparison counts a rewrite or a merge as a deletion; keep it a detector and do not turn it into a refusal to publish.
