# Project Memory

## Project
- pi-project-context is a pi coding-agent extension maintaining durable project memory (MEMORY.md, CONTEXT.md) plus session context; TypeScript under extensions/project-context/.
- Module layout: memory/*.ts (store, report, status, pass, prompt, sections, journal, document, poison, backup, injection, input), shared/*.ts (config, llm, call-policy, lock, paths, migrate, inject, lang, limits), handoff/*, autolearn/*, archive/*, plus handoff/handoff.ts as a test-only barrel; the Index is the per-file map.
- Tests live in tests/ with run-all.mjs as entry (`node tests/run-all.mjs`, 15 tests plus a repo-hygiene check outside the count); they import the barrels, so a name-based coverage check undercounts.
- tests/harness.mjs loadNamespace is the module-loading path production uses, so probes driven through it yield authoritative values.
- Process artifacts live under .codestable/ (issues/, audits/, features/, reference/, attention.md); each issue dir holds its design doc, fix note, review report, prompts/transcripts and release evidence.
- Runtime memory state lives in .agents/memory/ (tracked: .gitignore, MEMORY.md, CONTEXT.md, HANDOFF.md, project-context.json, errors.log; untracked: memory.jsonl, session-logs/, backups, skill-candidates/); project-local skills in .agents/skills/ are tracked.
- Docs live in docs/ (README.md index, architecture.md, configuration.md, handoff.md); CHANGELOG.md sits at the repo root.
- The repo has no package.json or manifest, so a release version exists only as a git tag plus the CHANGELOG heading.
- Release model: a git tag pinned in ~/.pi/agent/settings.json and ~/.pi/README.md (a bump updates both in one commit) and installed under ~/.pi/agent/git/git.lentech.site/C02-1010751281/pi-project-context; the pin host ~/.pi is a separate repo where a bump is its own commit landed with `pull --rebase`, never a force push; `pi update --extensions` needs a restart.
- One git remote origin carries two push URLs (forgejo and an ssh github mirror, both in .git/config); only origin is pushed to, a release tag is never moved, and release evidence lands in its own commit after the tag.
- Consumer repos on this machine (Quantum_Matrix, UniField, CipherCat, pi-custom-providers) are this extension's only runtime: they supply field evidence and receive local commits only.
- The pi host bundle lives in ~/.pi/agent/install/releases/<version>/node_modules/@earendil-works/pi-coding-agent/dist/, with the active version in ~/.pi/agent/install/current-version and pi's own docs/ (skills.md, settings.md) beside it.
- User surface is five slash commands (/project-context umbrella, then /memory, /handoff, /autolearn, /session-log), all documented in docs/configuration.md, which also owns the entry-point relationship section.
- The dsh plugin is the sibling implementation of the same config surface: it mirrored all seven v0.4.0 renames and reads no alias, so the two config surfaces do not diverge in spelling; only the storage and the keys without a counterpart differ.
- Two modules append to the system prompt on every before_agent_start (memory/report.ts and archive/archive.ts), both re-sent every turn and, since v0.4.1, both rendering section pointers instead of whole text.
- Each session's session-logs/<id>/ holds session.md (grep-friendly rendering; header carries the canonical session.jsonl link and entry count) and session.jsonl; the rendering is larger than the raw jsonl and can far exceed a context window, so a successor can only grep it or read it by offset.
- The extension ships pipeline-layer project skills under .agents/skills/ (pi-project-context-headless-runs, -release, -memory-cap-budget-change, -prefix-cache-analysis), tracked like any other project artifact.
- pi's memory layer writes at four registered points in memory/report.ts: session_start (migration/config notices), before_agent_start (injection only), agent_settled (fire-and-forget consolidate, throttled by consolidateTurns 6 AND consolidateIntervalMs 5min; /memory update is the explicit forced pass, deduped within forceDedupeMs 15s), and session_shutdown (model-free flush adopting a hand-edited MEMORY.md into the journal and republishing the fold only when the render is missing, empty or not newer than the journal).
- .agents/memory/MEMORY.md is committed as `docs(memory): refresh the memory render` in its own commit, never bundled with code or audits; a refresh re-audits the render for stale facts.
- The handoff trigger model (as of the 2026-10-18 handoff-before-compaction issue): a session_before_compact guard preempts pi's compaction so handoff fires before compaction, never after; settle trigger and guard share the trigger predicate, with the cooldown/backoff clocks kept at both call sites.

## Invariants
- Memory decisions rest on one version of the render: a read's bytes and the mtime it observed come from the same read; adoptExternalEdit re-verifies immediately before the append that the file still holds those bytes (whatever source its key came from, including the write path's key read before the model call) and refuses with an errors.log line rather than shadowing a newer edit with a stale key; a post-model nowKey recheck journals the file's newer bytes instead of publishing the reply (memory/store.ts); removing that one guard reddens seven checks.
- Adoption also carries the prompt-time loadMemory().text as basisKey and refuses to publish a reply whose basisKey no longer matches, both sides going through memoryComparisonKey with empty guards; nothing publish-side runs on refusal (no overflow copy, no cap/section-cap/poison or shortened log line, no removal warning, no toast), callers without a basisKey stay byte-identical, the model call is never re-run, and the next pass consolidates from surviving content.
- Stale detection uses memoryComparisonKey, so mtime-regressed or same-mtime external edits stay invisible by design (accepted residual); a file holding only the header refuses a reply while zero-byte/whitespace lets the reply win, and the stale window runs from the adopt read to the publish; residual R-L1 (loadMemory's pure-read sites pairing the render's bytes with a separately taken stat) was fixed in b7e2a31 - see the shutdown-flush review report.
- Independent review runs one round per frozen revision, in a /tmp sandbox copy with before/after zero-write proof against the live tree; a finding that asks for a new mechanism must first cite a field fact from this repo (errors.log line, journal line, success artifact, reproducible probe) or it goes to the non-goals, and a zero-hit logError key proves the error did not occur, not that the mechanism never ran.
- A chain stops the moment a revision passes - VERDICT: PASSED closes the issue and leftovers become follow-ups in the review report; any change to the reviewed revision invalidates that PASS, a finding is closed either by fixing and re-running the round or by registering it as a named residual, and a claim only the reviewer can construct (an unforceable concurrent window) is accepted with the reviewer's probe as its evidence rather than by adding a test hook.
- A chain may also be stopped without a PASS when every remaining finding lives in a file the model re-renders each settle: the stop reason and the unclosed items go in the review report's close-out note, and the record states plainly that no PASS was taken.
- A fix round must not widen its own surface: round 5 fixed the borrowed-key hole and found the read.changed early exit non-load-bearing (deleting it changed no test outcome), so the fix reduced the guards to one instead of adding a second.
- Every feature toggle funnels through setFeature in shared/config.ts; since v0.3.0 all four features carry on|off in their layer command, the umbrella's on|off is the target-less batch, and only --no-project-context disables the extension.
- Consumer-repo artifacts and field facts are read-only evidence with one home: cite them in .codestable audits, never persist their measurements or volatile state into MEMORY.md, CONTEXT.md, docs/ or CHANGELOG.md, and leave a fact with no home out rather than parked in this memory; pi-generated artifacts (HANDOFF.md, session-logs/) are session state, not curated memory.
- The consolidation prompt states the cross-project boundary twice (rule next to the secrets/filler rule, and as the caption opening <recent-conversation>); acceptance requires later renders to show zero foreign measurements.
- The autolearn prompt adds two rules after a generated skill body held a consumer repo's measurements: a skill writes only this project's facts, and a check states a shape, never a measured value; the description stays one short line because descriptions are injected into every session.
- The autolearn pipeline may supersede a skill it generated and nothing else: every skill a pass writes carries a body provenance marker (an autolearn-generated HTML comment in the body, not the frontmatter), gate and write path both read that marker off the artifact, and only a marked project skill's name may be reused; hand-written, legacy-imported and global skills are refused by name exactly as before (v0.3.1); all project skills carry the marker by owner convention (0ca0d91).
- Autolearn pulls a learned skill's body on request instead of pushing every body that fits (v0.3.2, 997447a): the first-look prompt carries no skill body, the model asks by name with `inspectSkill` (at most two, cap enforced in code), and the follow-up attaches whole bodies up to AUTOLEARN_SHOWN_BODY_CHARS = 20000.
- The set of names a pass actually rendered is one computation read by two guards - the gate in candidate.ts over the inventory and the write path in pass.ts over the file - so a one-sided mutation of either leaves the live-path refusal green; a learned name is overwritable only in the pass that showed its body.
- The autolearn auxiliary call is a single completion offering only RECORD_SKILL_TOOL (autolearn/pass.ts:102) with no tool loop, so the writing model cannot read skill files itself; any on-demand body fetch must be injected by the extension, and the existing `inspect` backtrack round is the shape to reuse (see docs/handoff.md).
- The autolearn inventory is capped at 8000 characters and, when truncated, must say so: the injected list ends with `- (N more skill(s) not listed: the 8000-character inventory cap was reached)` (v0.4.3).
- pi's own skill spec blesses bundled resources: a skill directory may carry references/ read on demand by path relative to the skill directory, so layering is a sanctioned pi pattern; one level deep is also in the spec, which is why the design allows only references/*.md.
- A design's code-size estimate runs low on this codebase (the external-edit design came in about 1.7x low); budget implementation accordingly.
- Before a pi-rendered MEMORY.md is committed or merged, the facts curated in HEAD must be shown to survive, and a render that dropped a durable rule is restored before the commit (re-adding the entry to the local journal in the extension's own op shape stops the next render reverting it); the restore pass is mechanical, not an eyeball one - bullet-ending punctuation plus a removed-line classification against the previous render.
- Every hand edit ends with a journal op in the extension's own shape whose text equals the committed bytes - verify that equality rather than assuming it - and write a render's size/headroom line last, from the final bytes, in memoryDocumentChars (which runs one character under the raw file count here).
- Per-section shares (0.2/0.4/0.25/0.15) are targets, not caps: renderMemoryDocument pools the slack and lends it to over-target sections by overage ratio, so entries are dropped only when the whole document reaches maxMemoryChars (v0.4.5); the pool must be measured against the document's real body (cap minus memoryStructureOverheadChars), never the floored target sum (see .codestable/issues/2026-10-06-consolidation-keeps-entries/).
- A curation pass on a render already within a few hundred characters of the cap retires skill-homed process rules rather than compressing wording, since compression alone cannot buy room for the next pass.
- Process rules with their own homes: the sandbox/probe pitfall set (node_modules, ~180 MB per copy, the zero-write exemption, the 6-turn/5-min floor behind a one-shot probe, `-ne -ns -np`, heredoc fixtures) in pi-project-context-headless-runs section Gotchas; release evidence in release-tag-and-pin-sync; explicit-pathspec commits in curated-surface-hygiene section 12.
- Project memory carries only durable, verifiable statements: no sibling commit distances, no sibling memory file sizes, no other projects' research values, no line numbers into MEMORY.md itself.
- Repository docs split by kind: architecture.md holds semantics only, field incidents and measured values belong in .codestable audits, and version-visible behavior changes belong in CHANGELOG.md; docs/*.md prose is wrapped at sentence boundaries with no line exceeding 160 characters (the rule covers docs/*.md only, not CHANGELOG.md), and a formatting-only rewrite must be proven content-identical (whitespace-normalized) before it is committed.
- The repo-hygiene check inside tests/run-all.mjs gates the memory render: the punctuation stop set is built from one STOP_CHARS constant and self-asserts uniqueness, so every bullet ends with punctuation from that set and a re-introduced duplicate fails the check.
- Skill descriptions under .agents/skills/ are injected into every session's system prompt, so each stays one short what-plus-when line of at most 170 characters, with step-by-step prose left in the SKILL.md body.
- pi caps a skill name at 64 characters and a description at 1024, does not load a skill whose frontmatter lacks a description, and injects only name, description and path at startup - never the body - so autolearn provenance goes in a body comment; name equal to directory is the portable choice, and pi -p implies --no-session.
- pi's RegisteredCommand exposes only name, description, getArgumentCompletions and handler with no alias field, so a command rename here is either a hard cut or a second registration, matching the repo's no-alias, no-notice rename policy.
- The command surface keeps one fact per name and one owner per fact: a parameter lives with the layer that changes it, the umbrella keeps only what two or more layers share, its first line is Features:, and /context retired in v0.3.0 with its lines split by ownership; the CONTEXT.md line comes from one shared contextStatusLine() on both sides (see .codestable/issues/2026-10-04-command-surface-convergence/command-surface-convergence-design.md).
- The four layers name run-it-now differently on purpose (`/memory update`, `/session-log write`, `/handoff now`, bare `/autolearn`): each verb says what that layer does, so this is decided rather than drift.
- Config keys mirror the command path that changes them, and the rename rode the same one-time migration as the legacy layouts: an old flat name folds into the new one, the new name wins when both are present, a junk old value falls back to the default, and a rewrite drops the old name, so legacyConfigPatch is the only place that knows an old name; all seven v0.4.0 renamed names are shared with dsh, which reads no alias by design (a dsh profile holding one must be edited before that host restarts, while this project migrates an old name once on the first config read); the pi-only keys are handoffMode, handoffGuard, autolearnAt and handoffBudgetToolResultTokens (the optional per-result tool-output cap).
- The legacy-config compat layer is kept with no retirement window: consumer projects on this machine still carry the pre-v0.4 flat names, so retiring the read-side migration would silently drop their settings; the dated file list and counts live in the config audit addendum, not here.
- A retired config key is not a rename and carries no alias: parseConfig keeps only known keys and updateConfig rewrites the whole document, so an unknown old key - or a retired verb such as /handoff thinking - is ignored and disappears at the next write, and its command verb, completions and legacyConfigPatch entry retire with it; handoffThinking retired in v0.4.2; handoffBudgetSummaryTokens and /handoff budget summary stay because threshold.ts reads that value.
- Both handoff modes obey the same physical drop floor (baseline + keep + MIN_DROP_TOKENS): the adaptive branch resolves to undefined (a refusal, e.g. below-quality-knee) rather than clamping up when knee(window) is under the floor, fixed-ratio mode is refused by the same gate, the status line names the refusal in fixed mode too, and `/handoff threshold <ratio>` prints the status line so a dead configuration is visible when it is set (v0.4.3); the refusal has field-confirmed live text.
- The threshold ratio range has one exported source (MIN_THRESHOLD_RATIO / MAX_THRESHOLD_RATIO) that the validator, the parseRatio parser, the usage sentence and the receipt advice all read; a mutation that moves the constant alone keeps the suite green only because the readers genuinely read it.
- A toast carries one prefix per layer and does not repeat the layer after it (`Memory: updated <file>`); `Usage:` lines and the multi-line `/project-context status` labels are deliberately outside that rule, and `/memory` and `/project-context status` print the same `Memory: ...` status line.
- Vocabulary rules, their terminal states and the audit history live in .codestable/reference/vocabulary-conventions.md, and a vocabulary change updates that file, the code, docs/CHANGELOG and this render in the same round.
- A handoff test that asserts a cancel/cooldown path must give the fixture a session branch long enough to have something to drop: a two-message branch produces the `nothing older than the recent window` skip instead, and the guard harness (`runHandlers`) and handoff state accessors are how the cooldown is asserted (handoff/state.ts) rather than through notifications alone.

## Pitfalls
- A FIFO fixture's blocking open is the scheduling barrier that makes a read-vs-replace race deterministic; a non-blocking O_RDWR open keeps every assertion green while deleting the race (caught in review, not by the suite), so restore the blocking open and bound it with a timer, and use SIGKILL inside that timer because process.exit() does not end a process whose libuv threadpool is stuck in a blocking FIFO open (measured).
- A SIGKILL watchdog cannot run the fixture's `finally`, so each FIFO watchdog clears its own subtree (`rm -rf`) before the signal and leaves the memory artifacts for diagnosis.
- Findings that recur in the model-re-rendered CONTEXT.md are self-inflicted (a table row pushed out of its table, a duplicated character class): fix the source document and stop the chain rather than chasing that file.
- A reply outside this extension's own shape (a `## <section>` heading plus `- ` at column 0) never replaces a stored document: memory kept, one diagnostic; only a project with no stored document accepts any shape, and since v0.4.7 an opaque reply carrying no markdown heading at all cannot replace a stored four-section document either.
- A marker grep against the installed clone must use a single-line substring: a comment wrapped across two lines returns 0 hits and reads as a missing fix.
- The `changed` flag a render read returns is `renderChangedAcrossRead`: mtime + size + ctime, so a same-size replacement that preserves mtime (`cp -p`, `rsync -t`) still counts as a change; only a replacement inside the filesystem's ctime granularity stays invisible (docs/architecture.md).
- A review round's transcript is the round's only evidence: when it cannot be recovered, re-run that round on the same frozen revision and label the re-run in the report rather than summarizing from memory.
- Sibling journals showing two appends tens to hundreds of ms apart with identical bytes are one recordMemoryDocument call appending twice, not concurrent writers; the earlier reading of a double op as the extension adopting its own render was retracted (a running process does not hot-swap modules).
- Two failure modes recur in this repo's reviews: each round that adds machinery adds surface for the next to find, so unconverged growth is a signal to stop rather than to add more, and a single-source claim must be checked against every reader; the characteristic finding is a user-visible sentence promising what the code does not do, so read every notice against the code path that actually writes it before freezing a revision and again after a new doc sentence.
- When a curation or repair edits a table in a record, insert or remove rows inside one contiguous table: a note placed between two rows orphans the row below it and silently drops it from the rendered table, so check table contiguity mechanically after such an edit.
- The superseded 415-line v5 design is archived with a do-not-implement banner; it must not be resurrected.
- Line numbers written into design docs, fix notes or MEMORY.md rot at the next render or commit; keep pointers file-level and re-measure with grep -n against the final revision.
- `git ls-remote origin` queries only the fetch URL; verify the github mirror through the second push URL separately, since another session can push to one URL only and leave the two forked (the github ssh ls-remote is flaky and may need retries).
- Two behavior changes whose assertions share one test file cannot be split into two green commits, so they land as one self-consistent slice.
- Do not read not-exported-to-tests as not tested: tests/handoff-test.mjs drives runHandoff through a newSession mock and maybeTrigger's settle trigger, and one of its cases pins the A anchor for a split turn.
- Dead-code hunts must grep the named consumer, not only the symbol: a helper survived because its JSDoc cited a function that no longer exists anywhere.
- An export-surface probe (definition-file-external references) is the reliable dead-export detector; most exports are internal-only, so `export` alone proves nothing about an API's reach.
- Unreachable branches hide behind a boolean that every call site passes the same way: runHandoff's `force` was always true, so its three `!force` re-check blocks never ran; the same shape recurred in the flush guard, where the read.changed early exit looked load-bearing but deleting it changed no test outcome.
- Knob usage cannot be read from key presence: the extension writes every config key into each project-context.json, so a file listing a knob proves nothing about use; compare each key against DEFAULT_CONFIG, and keep the machine-wide sample in the dated config audit addendum.
- Attributing a field artifact to a module requires checking that the module can produce that path: both leftover lock families trace to the Codex port's contextctl.py, not to this extension.
- Sessions archived from pi diverge from their source (most are prefixes, some larger than the source), so the archive layer preserves content pi's file dropped; every [autolearn] errors.log entry is an auxiliary-call failure, none a mechanism error.
- A pi re-render is built from the extension's own memory state and the session context, not from the current bytes of MEMORY.md, so a hand edit or a host-side merge-back holds only until the next pass and externally deleted state can come back: re-check the boundary at every render commit and treat the prompt-level boundary line - validated only by later renders showing zero foreign measurements - as the durable fix.
- An inferred migration-key list is not evidence: a first legacy-config scan guessed the old names and produced a false positive; read legacyConfigPatch's RENAMED_KEYS and re-run with the names the code actually recognizes.
- The regression guard's logged counts over-report against net entry changes, because its exact-match comparison counts a rewrite or a merge as a deletion; keep it a detector and do not turn it into a refusal to publish.
- Text written into a skill is read as ground truth by the next operator: an autolearn pass wrote a section-budget log string into the memory-cap skill although no such log string exists, so a skill's log-string references must be copied from the code that writes them.
- Rules that only the end-to-end path exercises can look load-bearing while silently drifting: CRLF normalization, fence skipping and the {0,3} boundary had no reddening mutation until they were pinned as pure-function contracts in tests/sections-test.mjs (11 hasMemoryDocumentShape cases), so a shape rule with no unit-level case is only as good as the path that happens to cover it.
- Mutation counts in the review report and CHANGELOG are measured as the `^FAIL ` lines of `node tests/run-all.mjs` (so unit-contract failures count too), and numbers from earlier rounds are historical values on their own revisions - do not re-run them against a later tree and call the record wrong.
