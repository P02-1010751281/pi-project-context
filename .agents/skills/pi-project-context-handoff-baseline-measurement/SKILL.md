## Shipped state (2026-10-14, v0.4.10)

The baseline is the minimum `prompt − chars/8` density bound over the accepted records (text only: system messages, image payloads and
`convertToLlm`-excluded inputs are out; `chars` follows pi's projection including `context_edit`); the rate only converts the receipt and
the split-turn budget; a record billed at or before the newest compaction is not a sample at all, and an interval whose overhead the text
cannot carry under the `<=2 tokens-per-added-character` assumption restarts the minimum. The re-anchor is a documented heuristic, not a
proof. Both the compaction-eligibility mirror (step 21, `44f7104`) and the wording sweep are shipped in v0.4.10 (the tag is peeled at the
docs commit `7b38cf4`); what is
still open is what design §14 registers (residuals ①③④⑤⑦⑧⑨ and the two rate-scope differences), not this.

# When to use
Use when `/handoff status` shows a below-quality-knee refusal that may be an estimator artifact, when the baseline residual (`usage.tokens` minus pi's chars/4 `estimateTokens` of the branch) is suspect, or when adding/changing the baseline sampler in `extensions/project-context/handoff/threshold.ts` (`measureContext` / `contextTokensAtRate` / the status-line baseline suffix).

## Procedure
1. Read the current semantics before touching code: `docs/handoff.md` owns the threshold and refusal rules; `extensions/project-context/handoff/threshold.ts` holds the baseline/floor; the status line distinguishes a resolved threshold (real `drop` projection) from an unresolved one (`drop budget N` = the configured fallback display, not a projection). The parenthetical after `threshold auto` is a refusal gate, not a clamp.
2. Establish what pi actually puts in the branch before trusting any reading: pi's `getBranch(fromId)` (installed bundle, `core/session-manager.js`) is a plain parent-chain walk with **no filtering**, so the session's `system` message entry is part of the branch, and `estimateTokens` (`core/compaction/compaction.js`) counts that entry's content plus `sections` plus the JSON of `toolsAdded`. **Historical (the bug this sampler replaced)**: subtracting `atRate(branch estimate)` from the usage also removed pi's estimate of the system prompt and tools, a fixed per-session fail-open bias. Shipped: system messages are out of the estimated content and no session rate scales the baseline, so that bias is gone - but the *branch* still holds the system entry, which matters whenever you compare a bound against `usage.tokens`.
3. Decide real vs artifact next: a reading built on pi's chars/4 `estimateTokens` alone under-counts tokens on a CJK-heavy branch, while the shipped density bound only assumes `chars/8 <= T <= chars`. Falsifiable probe: run `/handoff status` before and after the branch grows (the reading must stay put), then repeat in an ASCII-heavy session as contrast; a manual `/handoff now` is not gated by the threshold, so it stays available while you investigate.
4. Check the fixtures' branch shape before trusting a green suite: production branches always carry a system entry, so `grep -c 'role: "system"' tests/*.mjs` returning zero means every contract case, mutation and probe validates a branch shape production never has. Add a system entry to the fixtures before claiming the sampler is exact, and expect existing threshold cases to exercise only the fallback path.
5. Do not hunt the value in session-logs: the archive holds replayed predecessor usage records and non-message entries, and right after a handoff pi's newest usage record is itself the replayed one, so a file's own characters cannot reconstruct the prompt (the branch is bigger than the file). Require instrumentation instead.
6. Measure the baseline from the branch pi actually sends: walk the records along the parent chain (pi's context builder follows `parentSession` links), and for each assistant record take `prompt = input + cacheRead + cacheWrite` (never the reply's own output tokens) against the estimate of only the messages *before* that record, form `prompt - chars/8` (the density upper bound) and keep the **minimum** of those bounds; a residual (`prompt - estimate`) is only the historical form.
7. Rebuild "the branch up to record r" with r itself as the leaf, not with the current leaf: a record's prompt was billed against the branch as it existed then, so charging an older record the current leaf's character count gives it characters it was never charged for and the bound falls below the truth. Fixture: insert a replayed predecessor block of growing size ahead of a record and assert the reading stays at or above the known true overhead; the wrong reconstruction under-reads by roughly the replayed size.
8. Give non-text blocks their own accounting: pi's estimate charges each image block a fixed character constant while the provider bills the image's real tokens, so a density bound spread over all content can fall below the truth for small images (screenshots, low-detail thumbnails) and then win the minimum. Keep the density (chars-per-token) bound over text only and add the non-text part separately, so a message carrying an image still yields an upper bound; fixture: a known baseline plus a small image must not read below the truth.
9. Reject records that are not measurements: a record whose `prompt` is not strictly above the bound's own value (the chars-derived lower bound) yields a non-positive or meaningless bound, so skip it rather than letting it drive the minimum. State the rule in the code comment, and pin it with a mutation (count such a record).
10. (Historical, still useful for the receipt) The rate no longer decides the baseline: it is the median of `4 * delta(estimate) / delta(prompt)` over the last few accepted pairs, clamped to a band covering 1 token/char (CJK), and it converts the receipt / split-turn budget only. An accepted pair has already passed the interval rule, so the band's upper half is not checked. When no delta is usable, fall back to `rate = 4` and mark it uncalibrated.
11. Measure the reading's *stability*, not just its level: feed the production `measureContext` the branch truncated at the k-th usage record and print every sample's reading. Across one session the reading should be near-constant (only an injected-block refresh steps it); a spread of tens of thousands of tokens between samples means a non-message event moved the prompt. The code's own interval rate is the diagnostic: a rate far above the chars/token ceiling cannot come from message text. The three causes seen in real sessions are a replayed predecessor record (its prompt covers the predecessor's whole branch while the local file holds only the retained fragment), a `context_edit`/compaction (prompt drops, local characters stay), and an injected-block refresh (overhead change counted as message growth).
12. Classify the change: the levers are (a) which records are samples (credibility, interval consistency, excluded inputs) and (b) what counts as characters (text only, per pi's projection). There is no session-wide rate left to fix; an overhead increase is re-anchored only when it is provable. If you do re-anchor, anchor the trigger on the *interval's own text difference* (a form like `delta(prompt) > 2 * delta(chars)`, i.e. the increase the added text cannot carry under the tokens-per-added-character assumption) and write in the doc block that it is a heuristic whose false positive only raises the reading. A proof derived from the density band instead (a form like `chars_r - chars_p/8`) hands the interval most of its own previous text to the text budget, so an ordinary refresh never trips it and the re-anchor is dead code - the field fixture (a prefix, a refreshed block, then a few characters of new text) is what exposes that. Historical framing: plus provider-exact deltas so the reading is constructively stable, but it needs a record-eligibility rule (skip replayed records, re-anchor at `context_edit`/compaction, exclude intervals whose overhead changed). The bias fix alone leaves the drift; the drift fix alone still low-reads the overhead unless its anchor and eligibility exclude it. State which one you ship and register the other as a residual instead of implying it is fixed.
13. Preserve the no-usage path byte-for-byte: a session with no usage records must fall through to the old formula unchanged.
14. Funnel every consumer through the single conversion helper: the receipt's `dropping ~X / carrying ~Y`, the mid-turn snapshot budget, `keptTokens` and `anchorTokens` in `handoff/run.ts` must all read the same converted value; a second consumer is easy to miss.
15. Surface the measurement rather than implying a smaller baseline is the lever: the suffix is `· baseline <value> (chars/8 bound over <n> records; receipt at <rate> c/t)`, with `(chars/4, no usable record)` without samples and `receipt at chars/4, no usable delta` when none calibrated. Historical framing: has no usable delta.
16. Pin it with fixtures that chain `parentId`: pi's context builder follows the parent chain, so a flat message list exposes only the leaf, tests run through the fallback path, and a coverage claim built on them is false. Check fixture shape before trusting such a claim.
17. Run `node tests/run-all.mjs`, then prove each guard with a mutation matrix: sample the last record instead of the minimum; subtract `totalTokens`; fix `rate = 4`; drop the clamp band; remove the fallback subtraction; ignore the rate in the receipt; count a record's own reply in its own estimate; subtract the branch estimate with and without the system entry; re-admit system/compaction messages into the subtracted estimate; swap `min` for `max`; reconstruct older records from the current leaf; drop the "not a measurement" skip; spread the density bound over image blocks; revert the status suffix wording; sample a record billed before the newest compaction; drop the provable-overhead re-anchor; loosen the re-anchor trigger back to the band-derived form; sample a retained pre-compaction record. Each mutation must redden at least one check, and expect some checks to be reddened by only one of them.
18. Smoke-test on a real route (see the headless-runs skill for route/RPC mechanics): copy the repo to /tmp, set `memoryEnabled: false` in the copy's `project-context.json` so settle-time renders and auxiliary calls stay out, and read the first request's prompt tokens from a one-shot session; run the same tiny-prompt probe in a second sandbox whose cwd is not the repo, so the reading can be attributed to the extension's injection block instead of pi's own prompt. Note that a one-shot session holds a single record, so it cannot exercise the delta path - the pure-function contract cases, not the smoke, separate old behaviour from new.
19. Register the known boundary instead of widening the change: the cut point is still pi's `findCutPoint` (chars/4), so on CJK-heavy branches the actually carried size can deviate substantially from the keep budget; changing that means reimplementing pi's turn alignment.
20. Per repo convention, freeze the revision and run one independent read-only review round on a `/tmp` sandbox copy with a zero-write proof (see the independent-review skill); file the round's transcript, prompt and findings under the issue dir and expect fail-open findings (image blocks, replay eligibility) to come back from it rather than from the local mutation matrix.
21. When adding record eligibility, mirror pi instead of inventing a rule: pi core invalidates a record whose assistant message is from before the newest compaction (`assistantIsFromBeforeCompaction` in `core/compaction/compaction.js`) even though `firstKeptEntryId` keeps that message in the branch, so a retained-but-pre-compaction record must not be sampled. Read that predicate in the installed bundle first, then pin it with a fixture whose branch keeps a pre-compaction message and mutate it.
22. Treat the reading's error as two-sided: a session-level scalar rate only holds for prefixes at the same rate, so a guard that rejects one sign of the correction (e.g. "the scaled residual fell to or below zero") leaves the opposite sign reading below the truth. Fixture shape that exposes it: a sparse ASCII prefix followed by a dense CJK tail, plus the same branch without the tail - adding the tail must not drop the reading. Ship no wording that claims the sampler "never under-reads" unless the argument covers heterogeneous prefixes; if it cannot, register the exposure as a named residual in the issue record.

## Gotchas
- A record's own reply text counted into its own estimate reads the baseline low; that is a real bug shape, not a rounding detail.
- The branch estimate includes the system entry; treating `prompt - atRate(estimate)` as "non-conversation overhead" is the most common wrong assumption here. Verify the entry is in the branch (step 2) before arguing about the value.
- pi's own estimate for the `toolsAdded` JSON is chars/4 over dense JSON, so it under-counts there; even a corrected baseline wants a rate correction or a conservative margin, and an anchor-based form must stay a provable lower bound (e.g. chars/8) rather than a second guess.
- Min-sampling over records *is* the reading now that no rate scales the baseline, so pin it with records whose bounds differ (with `r < 8` the bound grows as the branch fills) or the guard looks unpinned; conversely, once a scalar rate calibrates a homogeneous session, `min`-vs-last can become unobservable and the check silently stops pinning anything.
- A fail-open direction is the dangerous one: a bound that can sit under the true overhead must be fixed or named as a residual, not described as "never under-reads".
- A re-anchor threshold loosened back to the band-derived form, and a re-anchor that never fires on real sessions, both look green locally; keep the field fixture (prefix + refreshed block + a few new characters) asserting a fail-closed reading, and keep a mutation that loosens the trigger.
- Compaction interacts with eligibility twice - the estimate/rate gap of a summary record, and `firstKeptEntryId` retaining pre-compaction messages - so a fix that only handles one of them still mis-samples.
- Keep the status line's growth in mind - length there is convention-bearing in this repo - and trim a new suffix deliberately.
- Provider 402/429/quota failures are not validation of this path; report them apart from deterministic tests.
- The sampler also feeds the mid-turn snapshot and receipt paths; a fix that only touches the status line leaves the other consumers on chars/4.
- A fix round must also sweep the wording it invalidates (CHANGELOG bullet, `docs/handoff.md`, code comments, the issue's residual list); leaving the old formula's justification in place is how a later round flags a residual as still open when it is not.
