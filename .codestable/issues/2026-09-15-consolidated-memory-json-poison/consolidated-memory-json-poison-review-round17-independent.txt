## Nit

1. **N17-1 `cleanStaleTemps` 的 `.broken-*` 回收与实际生产者不对称** — `project-state.ts:437`（`if (!entry.isFile()) continue`）vs `263-266`、`298-300`（两处 rename 都只在 `!info.isFile()` 时发生）。
   - 事实：协议产生的 broken 产物（目录/FIFO/设备/symlink）**必然是非普通文件**，因此永远过不了 `isFile()` 闸门；探针确认 broken 目录在 migration 后仍在（`somedir.broken-1234abcd`，以及目录锁自愈产生的 `MEMORY.md.lock.broken-*` dir）。能匹配的只有恰好叫 `*.broken-<8hex>` 的用户普通文件，反而新增了删除面。影响：每个外部制造的非文件占据锁/claim 路径就留下一个永久（被 gitignore）的 broken 产物，只能人工清；有界但 N16-6 的「回收」对真正的来源无效。修复边界：明确决定「非文件 broken 是用户数据、故意保留」并写进注释；若要回收，只删 **空目录** 且更老于 cutoff（绝不递归，目录内可能含用户数据），并给该分支留测试。
2. **N17-2 `tests/run-all.mjs:15` 的 `spawnSync` 仍无 timeout** — round 16 N16-2 的后半条未落实。影响：任何测试文件未来出现锁外死锁/挂起，CI 仍会无限等待（锁死锁主向量已被子进程 timeout 与 5s deadline 封住，风险低）。修复边界：`{ encoding: "utf8", timeout: 60_000 }`，`status === null` 时按失败上报。

## Learning

- 同一盲点在协议两个入口（`<lock>` 与 `<lock>.steal`）各犯一次，说明自愈/校验应作为**协议入口的统一预处理**，而不是逐路径打补丁；N16-1 的对称化修好了调用侧，但清理侧又按「文件」直觉设闸，忽略了「rename 只可能产出非普通文件」这一生产者事实。
- `lockMtimeMs` 的「ENOENT=0」语义意外成为 dangling symlink 的自愈通道（stat 失败→视为无限陈旧→steal `rm` 摘链），与「非 ENOENT=Infinity」的 fail-closed 形成互补，探针已证实两种 symlink 行为都正确。
