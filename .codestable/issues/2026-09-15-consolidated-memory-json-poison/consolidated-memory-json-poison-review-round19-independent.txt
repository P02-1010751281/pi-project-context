## 发现

### Blocking
无。

### Important
1. **dangling symlink 不会自愈（与声明的「目录/FIFO/dangling symlink 自愈」目标不符，且新测试未覆盖）**
   - 复现（真模块）：
     - `<MEMORY.md>.lock` 为 dangling symlink → `ok=false elapsed=5011ms err=timed out…`，残渣 `MEMORY.md.lock` 原样保留；
     - `<MEMORY.md>.lock.steal` 为 dangling symlink + 陈旧锁 → 同样 5s 超时，锁永远无法被回收。
   - 根因：`open(path,"wx")` 对 symlink 一律 `EEXIST`（POSIX O_EXCL），随后 `stat()` **跟随** symlink 抛 `ENOENT`；`tryLock`/`acquireClaim` 的 catch 把「stat 失败」等同于「文件已消失」直接 `return undefined`，于是 `info.isFile()` 的 rename-aside 分支永远不执行；`lockMtimeMs` 又把 ENOENT 映射为 0（无限陈旧），`stealStaleLock` 的 `readFile` 同样 ENOENT 提前 return。结果是该项目的每次内存写在 5s 后永久失败，需人工删链。
   - 触发条件：内存目录中存在一个指向不存在目标的 symlink（第三方同步工具、手工操作、半失败的外部脚本；扩展自身不会创建 symlink，故非数据损坏、非攻击面扩大，但要人工介入）。
   - 建议修复：在 `stat` 抛 ENOENT 时回退一次 `lstat`，若条目仍存在则以 `rename(..., .broken-<rand>)` 移开并 `continue`（锁与 claim 两处同修）；或统一用 `lstat` 分类。并补 dangling symlink（及 FIFO）测试。

### Nit
- `stealStaleLock` 的「连读两次比对」并未把删除对象钉在做过 mtime 判断的那个 inode 上：若锁在第一次 read 前就被替换，两次读到的是同一份新字节，比对恒等。真正兜底的是 claim 令牌复核；可改为 `stat` 取 ino/dev/mtime → read → 复核同一 ino 再 rm，语义才与注释一致。
- `tryLock`/`acquireClaim` 的 inode 守护用 `dev+ino`，存在极小概率的 unlink 后 inode 复用别名（同设备）。`handle.stat()` 失败时宁可不清理，方向是对的。
- `MEMORY_BACKUPS_MAX` 与 `MEMORY_BACKUPS_KEPT` 的差值语义耦合（`index < MAX-KEPT`），建议注释或断言 `MAX >= KEPT`，避免后续改常量时静默变义。

### Suggestion
- 新增测试：FIFO、dangling symlink 于 lock 与 `.steal` 两个路径的自愈；`tryLock` 写失败后「后继者锁不被误删」只能靠 inode 复用构造，建议至少保留静态注释。
- 备份测试可再加一条「25 次后保留集合等于最新 20 个名字」，当前只断言数量与最新存在，稍弱。

### Learning
- `open(O_CREAT|O_EXCL)` 对 symlink 的 EEXIST 先于跟随；`stat` 与 `lstat` 在自愈分支里是两种语义，混用会把「永存的坏条目」误判为「瞬时消失的竞态」。
- claim 令牌 + 每次删除前所有权复核，把 steal 的 TOCTOU 从「任意长挂起」压缩到「复核→rm 的微秒窗口」，这是无内核锁（flock/锁目录）前提下能做到的合理上界。

### Praise
- `${pid}-${uuid}` 令牌、`claimStillOurs` 前置复核、只删观察字节、`tryLock`/`acquireClaim` 的 inode 级清理，方向正确且探针可证：claim 被回收后原持有者确实不再删除任何锁（确定性单测 + 12 轮多进程压力 0 重叠 0 泄漏）。
- 备份硬上限实测严格收敛 25→20、50→20、老化→5，且「最新保留 + 最老优先 + stat 失败不猜删」三者互不破坏。

### Residual-risk
1. **`claimStillOurs` → `rm` 的微窗口**：若进程恰在最后一次 claim 复核通过后被抢占 **>30s**，同时另一进程完成「claim 过期回收 → 删陈旧锁 → 建新锁」，原进程恢复后可能删掉后继者的 fresh 锁，导致两个写者短暂重叠。触发需「微秒级窗口内被调度器挂起 ≥30s」+ 完整并发 steal，现实概率可忽略，且比改动前窗口大幅缩小；彻底关闭需 `flock`（Node 无内建）或锁目录 + 原子 rename 协议。
2. **mtime 检查与 read 不绑定 inode**（见 Nit），单独不可利用，与 1 组合才有意义。
3. **stat 持续失败的后备永不轮换**（按设计 fail-safe），病态文件系统下目录可增长；不影响有备份保护的丢更新。
4. 上述 1 与 2 只会破坏「互斥」而非「已有备份的回滚」，且需要 >30s 挂起，不属于有备份保护的丢更新路径。
