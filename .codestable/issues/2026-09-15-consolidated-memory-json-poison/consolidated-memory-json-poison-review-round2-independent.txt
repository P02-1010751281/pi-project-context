## 1. Findings

### blocking

**B-1 `healPoisonedMemory` 会在健康记忆上静默、破坏性地重写文件（本轮新引入的读路径写副作用）**

- 证据（`extensions/project-context/project-state.ts:390-404`）：
  - 判定 = `body.indexOf("{")` 在前 200 字符内（`:392-393`）+ 在**其后全部文本任意位置**正则命中 `"memory_markdown"\s*:\s*"`（`:394`）；
  - **未闭合值完全绕过**「值即记忆文档」的守卫（`:398` 只在 `field.complete` 时要求 `startsWith("# Project Memory")`）。
- 反例 1（平衡 JSON，无引号失衡；/tmp 实测）：健康 MEMORY.md 开头有一个 `json` 代码块示例，其 `memory_markdown` 值以 `# Project Memory` 开头：
  - 输入：`# Project Memory\n\n```json\n{"memory_markdown": "# Project Memory\\n\\n## Example\\n- the documented reply format", ...}\n```\n\n## Real notes\n- keep this...`
  - 输出：`# Project Memory\n\n## Example\n- the documented reply format`（`## Real notes` 整段消失，`real notes kept: false`，仅留 1 个备份、无通知）。
- 反例 2（/tmp 实测）：前 200 字符内有任意 `{`（如普通 JSON 代码块），文件末尾任意位置出现未闭合的 `"memory_markdown": "`：
  - 输入含 10 行 durable facts + `- the old bug wrote {"memory_markdown": " and cut the rest` + `- final fact that must survive`
  - 输出：`# Project Memory\n\nand cut the rest`（前缀与末尾事实全丢）。
- 影响：`loadMemory` 是注入/整理/autolearn//memory 的共享读路径，命中时 **健康记忆被静默替换**；恢复只能靠人工发现 `.poison-backup-*`。analysis §5-A.2 明确要求「正常记忆不得误判」，且本轮 IMP-3 的修复只挡住了 complete 形态。
- 建议修复边界：对「对象起点 + 字段起点 + 值形态」三者同时加约束，例如要求字段出现在 `{` 之后很短的窗口内（而非文件任意位置）、要求 JSON-ish 前缀占支配地位，或在 incomplete 时也要求值像记忆文档（可用更宽松的 `# Project Memory`/一级标题判定）。把上述两个反例固化为「预期不写回」的测试。

### important

**I-1 headless（`-p`/`--json`）自动路径的剪裁完全无痕**

- 证据：`extensions/project-context/consolidate.ts:267-272`：`if (!silent && (memoryChanged || update)) { notify(...) } else if (outcome.clipped) { logError(...) }`。`notify` 在 `ctx.hasUI === false` 时是 no-op（`project-state.ts:107-113`），而该分支成立时 `else if` 不会执行。
- 仓库事实：print/json 模式 `bindExtensions` 不传 `uiContext`（`dist/modes/print-mode.js:53`），RPC 模式才传；`agent_settled` 在 core 层无条件发出（`dist/core/agent-session.js:350`），因此 headless 下自动整理会真实发生。
- /tmp 实测（harness `hasUI=false` + `agent_settled` + 6 轮）：`notifications: 0`，`errors.log` 长度 0、无 `shortened` 痕迹，但 MEMORY.md 已被剪裁输入重写。
- 影响：`-p`/JSON 会话中记忆/上下文中间段被永久丢弃，没有任何可见或落盘留痕——正是 IMP-2 要消除的「静默永久丢失」的一种残余。
- 建议修复边界：把留痕与 `silent/UI` 解耦（例如 `if (outcome.clipped && (!ctx.hasUI || silent || !changed)) logError(...)`），并补 headless 断言。

**I-2 `budget < MIN_CLIP_CHARS(400)` 时分配退化：context 可超出全部预算、memory 被清空，测试结论「context 不吃掉 memory」在该区间不成立**

- 证据：`consolidate.ts:180-184`：`contextLimit = min(context.length, max(400, budget/2))`；当 `budget < 400` 时 context 保留上限 400，可大于 `budget`，随后 `memoryLimit = max(0, budget - contextText.length)` 归零；`clipText(limit<3)` 只输出 `\n\n`（`:153-158`）。
- /tmp 实测（CJK 记忆/上下文，cap 取模型元数据 `maxTokens`）：
  - cap=1400：`maxTokens=1400, budget=385, memory=(none), context=400 chars, total=406 > budget`，`clipped=true`；
  - cap=1300：`budget=283, memory=(none), context=400 > budget`；
  - cap=1424：`budget=410, memory=" # Pro\n\nORY"`（头尾各被截到几字符）；
  - cap=2048：`memory=525 / context=525`，分配正常。
- 可达性：当前 pi 目录 `maxTokens` 最小值为 3685（bundled catalog 统计），故默认/常见模型不可达；但 pi 允许用户在 `models.json` 自定义模型（本地 ollama/llama.cpp 等）并把 `maxTokens` 设为 1024–1400，`MIN_AUX_MAX_TOKENS=256` 的配置也不能阻止（`maxTokens` 会被 `needed` 抬高，只有模型元数据会成为硬顶）。此区间内 (a) 模型收不到任何记忆输入仍被要求重写，(b) 发送内容超过 `budget`，仍可能截断失败——即 IMP-1 的收敛性问题在元数据小的模型上重演。
- 建议修复边界：让 context 上限不超过 `budget`（如 `contextLimit = min(context.length, max(0, budget - MIN_MEMORY_FLOOR), max(MIN_CLIP_CHARS, floor(budget/2)))` 之类的预算内夹取），`limit < 3` 时不要只发 joiner；补 cap∈{1024,1400,1424,2048} 的断言（memory 非空、`sent ≤ budget`）。

**I-3 自愈召回边界：complete 但值不以 `# Project Memory` 开头的存量污染永不修复；前缀 >200 字符的污染不修复**

- 证据：`project-state.ts:393`（前缀 >200 直接返回）、`:398`（complete 值不满足精确 `startsWith` 即放弃）。
- /tmp 实测：
  - `# Project Memory\n\n{"memory_markdown": "## Project\n- real facts...", "context": {...}}\n` → `healed=false`（旧 `parseConsolidated` 回退同样会写出这种 complete-but-unparseable 形态，例如 stray member）；
  - 250 字符散文前缀 + 截断 JSON → `healed=false`。
- 影响：这类存量坏文件继续被注入/回流，原 issue 的自锁症状不解除，且无 warning。三份真实事故备份（`{` 开头、截断或 complete 且带 header）已验证可修复，故属残余召回缺口而非主路径缺陷。
- 建议修复边界：明确 complete 值的判定（大小写/标题形态放宽）或记录为有意的 fail-safe；POISON_PREFIX_LIMIT 可结合「JSON 占比/主体性」判定放宽；补固定夹具。

### suggestion

### learning

- 读路径上的启发式判定必须对模式的**每一部分**都设界（对象起点、字段位置、值形态），并且「不完整匹配」不能成为绕过值形态检查的旁路——因为 needle 可以在文件任意位置被自由文本命中。
- 可见性分支要覆盖 (UI × silent × changed) 全矩阵；把 trace 放在 `else if` 里会漏掉「有通知分支但通知是 no-op」的 headless 情形。
- 预算 floor 必须被总预算夹取；floor > budget 会同时破坏公平分配与收敛性。

### praise

- 三条真实事故备份（Quantum×2、UniField×1）用新代码独立回放：分别 14385 / 14525 / 15055 字符，备份与原文逐字节一致，二次读取幂等——自愈主场景（截断 + `{` 开头 + 带 header）确实修好了。
- `readJsonStringField` 的搬移共享经我独立 60k 例差分 fuzz 验证，complete 路径与旧实现 0 mismatch；回复侧仍要求闭合，fail-closed 保护保持。
- 失败诊断（`replyHead` + toast 首行）与剪裁可见性（非 silent warning、命令 reply、silent errors.log）经实测均按设计生效；`clipText` 的长度精确性（`head + 2 + tail = limit`）正确。

### residual-risk

- token 率仍是估算且未计 JSON 转义膨胀（`\n` → 2 字符）；行密集文本仍可能触发截断，但 fail-closed 且 `errors.log` 有原始回复头。
- 剪裁写盘路径无独立备份，仅靠通知；用户错过 toast（或 headless）即无可回滚。
- `model.maxTokens` 元数据高于 provider 实际上限时，抬高后的 `maxTokens` 可能从「8192 可成功」变为「请求被拒」，整理会整体失败（有日志，但记忆停止更新）。
- 自愈在只读/权限不足时静默失败，污染继续注入；`.pi/` 与 OMP 回退来源不写回，其中的污染不会被修。
- 多进程共用 `MEMORY.md` 时 stale heal 覆盖新写入的风险仍在。
- 备份文件长期驻留项目目录。
