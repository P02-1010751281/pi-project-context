### nit
- **N-1 严格预算不变量可越界 0.4 token，测试容差不一致。** `consolidate.ts:225,253,260` 的收敛/保底判定用 `budget + 0.5`，而 `tests/consolidation-test.mjs:467` 断言 `≤ cap + 0.001`；随机输入下 1574/8000 落在 (0.001,0.4]。影响：率是保守估计，实际不可感知；但该断言在新增 fixture 下可能偶发失败。修复边界：把三处 slack 收到 `budget`，或测试容差改为 0.5 并注明。
- **N-2 `clipText` 可切开 surrogate pair / 孤立代理对。** `consolidate.ts:182-188` 按 UTF-16 索引 slice；仅影响 prompt 边缘字符，已是记录残差。
- **N-3（沿用 round 9）命令回执不指向实际备份。** `consolidate.ts:443,451,463-469` 对 `clipped` 一律回中性文案，而同一次调用 `:373` 的自动通知会带备份路径；显式 `/memory-learn` 用户不知道刚写的备份在哪。属展示问题。

### learning
- 定点收敛必须「每次从原始文本 re-clip」而非在已剪裁中间结果上继续剪：`consolidate.ts:226-227,248-249` 始终以 `memory/context` 为源，保证增长单调、内容始终是原文本头尾并集，不会像 round 9 那样把一侧清零或振荡。
- claim 释放条件应与「本次是否持久化了被保护产物」绑定（`wroteMemory`），而不是「是否进入 catch」；这是 round 9 IMP-2 与 round 10 N-R10-1 的通用修复模式。
- 删除类保留策略 = 全名锚定正则 + `isFile` + mtime + 排除本次刚写项，可同时抵抗名字伪装与时钟错位。

### praise
- round-10 三个 finding 均以可复现数字关闭：R10 反例预算利用率 100% 且 memory 整份保留；claim 四场景无回放；预算矩阵 0 地板破坏/0 浪费超标。收敛逻辑（按需分配→实际文本迭代→阻尼增长回填→字符保底）在 9k+ 探针下没有清零、没有越界（>0.4 token）、没有过度剪裁。
- fail-closed 与写时无条件备份的组合经受住 EISDIR/EACCES/部分写/并发/时钟错位测试，字节保真可靠。
