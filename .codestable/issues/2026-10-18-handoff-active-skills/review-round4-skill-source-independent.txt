# Independent Review — R4: explicit `/skill:` skill-load source

## What I verified against the installed pi (1.3.0)

**Parser identity (correctness ✓).** `parseSkillBlock` is pi's own parser, exported from the package root (`dist/index.js:5`, typed in `dist/index.d.ts:3`), and it is the exact parser pi's TUI uses to recognize a skill invocation in a user message (`interactive-mode.js:3195`). The extension imports it from `@earendil-works/pi-coding-agent` alongside the already-used `sessionEntryToContextMessages`. Using pi's parser instead of a forked regex keeps the extension's definition of a "skill block" in lockstep with pi.

**Block shape (✓).** pi's generator (`agent-session.js:1710`, `_expandSkillCommand`) emits
`` `<skill name="${skill.name}" location="${skill.filePath}">\nReferences are relative to ${skill.baseDir}.\n\n${body}\n</skill>` ``
plus `\n\n${args}` when a trailing message is present. The parser regex (`^<skill name="…" location="…">\n…\n</skill>(?:\n\n…)?$`, fully anchored) matches both forms; I probed the real installed parser and confirmed: generated block with/without args → parses, `location === skill.filePath` (a `SKILL.md` path for the portable form); leading prose, a single-`\n` trailer, a missing `\n` before `</skill>`, malformed attributes, and CRLF all return `null`. `messageText` joins text blocks with `\n` and trims — correct extraction for the single-text-block messages pi stores (verified `sessionEntryToContextMessages` returns the message verbatim). A non-SKILL location parses but is rejected by the `isSkillFile` guard.

**Priority/ordering (✓).** The `remember` order counter behaves as intended — probed through the harness: read→`/skill:` of the *same* file upgrades to one entry at priority 4; `/skill:`→read does not downgrade; a repeated command dedupes; at the 8-cap a `/skill:` entry survives and the oldest read is evicted. No lower-priority index source can evict a priority-4 entry (priority is the primary sort key). `/skill:` outranking a real `read` is the right call: the command is direct user intent, while a read can be the model browsing for reference — and the block already contains the skill body, so no read usually follows.

**False positives (✓).** The gate is pi's anchored regex, not a substring search: a block quoted inside prose, a block with appended text lacking `\n\n`, a malformed block, and handoff-prompt text (multi-section, `- name: path` skill lines in `prompt.ts:50/72`) all fail to parse. A user deliberately pasting a full block *is* accepted — but pi's own UI renders any such user message as a skill invocation, so by pi's definition that is a real load, not noise.

**Tests/mutations (✓).** `node tests/handoff-test.mjs` — all checks pass including the 4 new ones (lines 33–36) and the pre-existing active-skill/prompt-recognition checks. `node tests/run-all.mjs` — all 15 suites pass. Mutations on copies under `/tmp` reproduce exactly: remove the whole scan → 3 FAIL; `SKILL_COMMAND_SOURCE` 4→2 → 1 FAIL; remove the `isSkillFile` guard → 1 FAIL. The tests exercise the real installed parser (the fixture block passes through pi's code), so they are not self-referential. No model call: the baseline "no scenario above reached a model" pin still holds. Zero-write proof: `git status` shows only the six modified files, nothing untracked.

## Findings

### Important

**I-1 — docs re-claim "most recent" ordering for the index sources** — `docs/handoff.md:122`, `CHANGELOG.md:21`
Impact: "同一级按最近出现排序" follows "提示/压缩的文件清单最后" and naturally applies to all levels. Prompt/compaction lists are pi-sorted indexes with no activity order, rendered in reverse block order — this is exactly the claim class R1/I-1 corrected because treating index line order as recency let the 8-cap evict the active skill. The code comment added in this same diff says the opposite ("file indexes … no activity order … reverse block order"), and the fix-note states it correctly; the two user-facing summaries do not. Docs-only, no behavior impact.
Fix boundary: reword both parentheticals, e.g. "`/skill:` 与真实 `read` 内按最近出现排序，提示/压缩的清单按块内倒序只填剩余名额" (CHANGELOG should also say the index lists rank last). No code change.

### Nits

- **N-1** — `extensions/project-context/handoff/file-ops.ts:23`: "Bound on the active-skill list: the read-sourced head is recency-ordered" — the head is now `/skill:`+read sourced. Reword to "the explicitly-sourced head".
- **N-2** — `fix-note.md:52-53, 67-75`: the Verification list omits the non-SKILL-guard check, and the mutation list has no entries for the three R4 mutations (scan removed 3 FAIL / priority 2 1 FAIL / guard removed 1 FAIL), unlike every prior source. Add them.
- **N-3 (residual)** — standalone Markdown skills: pi documents "Pi accepts some standalone Markdown skills" (`docs/skills.md:63`). `/skill:name` on such a skill emits `location="…/foo.md"`, which `isSkillFile` rejects — so the new source (like the read source) misses them. Worth one residual line in the fix-note; consistent across all sources, not a regression.

### Suggestions

- **S-1** — pin same-file dedupe across `/skill:` and `read` in *both* orders. The current outranks test uses two different files, so the no-downgrade branch of `remember` (a later read must not drop priority 4→3) is mutation-invisible.
- **S-2** — pin a negative strict-gate case: a block embedded in prose, or with a single-`\n` trailer, is not treated as a load. This locks the anchored-regex property against a future loosening to a substring check.
- **S-3** — pin the 8-cap survival of a `/skill:` entry over eight reads (verified by probe, unpinned).

### Learnings

- **L-1** — the `/skill:` block is the most replay-durable evidence: it lives in a user message replayed verbatim into the successor, so it survives hop 2+ as long as it stays in the recent-token slice. The strongest source also decays slowest.
- **L-2** — importing `parseSkillBlock` binds the extension's load-time surface to a pi build that exports it (present in 1.3.0). An older pi would fail the whole extension at import, not just lose the feature.
- **L-3** — a pasted full block is indistinguishable from a real command, and pi's UI renders both identically; acceptance is semantically correct, not a false positive.

### Praise

- Reusing pi's parser instead of a local regex (P-1); mutation matrix reproducing exactly at 3/1/1 with tests running against the real installed parser (P-2); the `remember` monotonic-order + priority-first sort verified for upgrade, no-downgrade, repeat, and cap scenarios (P-3); the fix-note residual narrowing to `bash`/`cat` and codemode `nestedCalls` is precise (P-4).

### Residual risk

Unchanged and correctly disclosed: the 8-cap and successor-internal compaction can still drop a mode; a prompt-only hop-1 mode can be evicted at hop 2; the successor may ignore the instruction. New: standalone `.md` skills are invisible to every source (N-3).
