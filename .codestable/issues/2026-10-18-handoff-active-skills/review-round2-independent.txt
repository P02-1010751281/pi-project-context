Scope: `collectActiveSkills` priority/order comparator, new tests, mutation matrix, docs/claims, adversarial probes (13 shapes, run against the sandbox code via the test harness), field check against the live JSONL, regression suite. ## Verdict summary of I-1

The comparator is **correct** in every traced case. `extensions/project-context/handoff/file-ops.ts:98-103`:

- weaker source after stronger, same file → `order` bumps, entry keeps the stronger priority (probe D: read→prompt→read gives `[later, keep]` with correct read recency);
- same file in several sources → strongest priority wins and its own sighting sets the order (probe C: prompt+read dedupe to one entry, read-sighted);
- prompt after read (different files) → read stays first even though the prompt is later in the branch (probe B: read `z-late` outranks prompt `a-early`);
- within a source, later sightings sort first: reads are recency-ordered; within one prompt block the output is the block reversed (probes A/J).

The priority interpretation is sound. Verified against pi's installed dist again: `compaction/utils.js:59-60` sorts `readFiles` — prompt/compaction lists really are alphabetical indexes with no activity signal, so they can never legitimately outrank a real `read` (use-evidence with chronological order). The one "burying" shape — a prompt-sourced mode evicted by 8 newer read-sourced skills (probe I) — is the disclosed 8-cap residual, strictly better than R1 (where an index could outrank a real read), and requires ≥8 later reads to manifest. The 8-cap is defensible: bounded prompt payload, disclosed as "最多 8 个", and now orders its contents by the strongest available evidence.

Fix boundary: wording only.
- **N-B** `file-ops.ts:23,83` — "only the most recent are likely still active" / "most recently read first" is strictly true only for the read-sourced head; mixed lists append index-ordered entries. Comment-level.
- **N-C** The cap residual line ("Only the 8 most recently read skills are listed") doesn't cover the prompt-only shape: a 10-entry prompt-only list keeps the last 8 block lines — the same alphabetical eviction R1 flagged, now honestly disclosed as an arbitrary index order, but the residual wording fits read-sourced lists only. One clarifying line would complete the disclosure.
- **N-D** `docs/handoff.md:126` — "像 grilling 这样的模式也不会消失" is absolute; the cap and the compaction-inside-successor shapes can still lose a mode (both disclosed in `fix-note.md`, but not in this sentence).

### Suggestion

- **S-1** `language.ts:56-63` — `HANDOFF_PROMPT_CLOSINGS` does not contain the intermediate 0ca14ba `closingContinue` ("先复述上一轮用户的要求和当前进度（一两句话），再从上次中断处继续。" / "First restate in one or two sentences what the user last asked and where the work stands, …"). Field sweep across all pi sessions: **0 stored prompts end with it** (0ca14ba never shipped; the two phrase-bearing sessions are prose or end with `closingPaused`), so no shipped artifact breaks and the docs claim about released closings holds. Residual exposure: a non-paused handoff run from the local 0ca14ba build before v0.4.11 ships would create a successor prompt v0.4.11 can't recognize. Adding the two literal lines costs nothing.

### Residual risk (field facts, no new mechanisms)

- **R-A** (probe I): a prompt-sourced hop-1 mode is evicted when 8 newer read-sourced skills exist — index entries only fill the slots reads leave. Same root as the disclosed cap residual, now with a concrete shape.
- **R-B**: draft-mode flow (`guard=draft`/`mode=draft`): the stored message is the user's edited text; any appended answer fails `isHandoffPromptText` (the "quote with appended text" test pins the gating), so that message contributes no skills at hop 2 — only a successor re-read survives. Consequence of deliberate quote-gating, unrecorded.
- **R-C**: prompt-only 10-skill list keeps the last 8 block lines (alphabetically last of pi's sorted block); an alphabetically early active skill with no surviving read evidence is still evicted at hop 2. Arbitrary by nature of the index; see N-C.
