## Findings

**IMPORTANT 1** — `.codestable/issues/2026-10-18-handoff-active-skills/fix-note.md:91-93`
The residual bullet still says "Detection relies on a `/skill:` block, a `read` of `SKILL.md`, a compaction `readFiles`, or a prior handoff prompt. A `bash`/`cat` read, **a codemode `nestedCalls` read**, or an arbitrary command … is not detected." This directly contradicts the new feature and the same file's own updated verification list ("a codemode nested `read` is detected") and the replaced residual. Impact: the authoritative issue record misstates the behavior being shipped. Fix boundary: this one bullet — fold nested reads into the detected-sources list and drop the codemode mention from the undetected list (only `bash`/`cat` and arbitrary injection remain).

**IMPORTANT 2** — `.codestable/issues/2026-10-18-handoff-active-skills/review-report.md:101`
The residual-risks paragraph now says "a standalone `.md` skill is invisible to every source **except `/skill:`**". That is wrong: `collectActiveSkills` applies `isSkillFile` (basename `SKILL.md`) to the `/skill:` location too (`file-ops.ts:129`), and a standalone skill's location is its `.md` path — so it is invisible to **every** source, including `/skill:`. The fix-note's own residual (`fix-note.md:94-96`) states this correctly, so the two records now disagree. Fix boundary: revert to "every source" (or name the exception precisely, e.g., "only a `<dir>/SKILL.md`-shaped path counts").

**NIT 3** — `extensions/project-context/handoff/file-ops.ts:112-113`
Two comment imprecisions: (a) `nestedCalls` is recorded for **any** tool calling `ctx.executeTool()` (extensions, MCP), not only codemode scripts — pi's own comment says "for example from codemode scripts"; (b) "a skill read inside a script is a real read" overstates — it is script-side and pi's file index, not the assistant, treats it as a read. Suggest: "pi's `extractFileOpsFromMessage` counts nested reads in its file index, so treat them as reads too." No code impact; the gate itself is correct.

**NIT 4** — `file-ops.ts:116-119` (behavior nuance, consistent with pi)
A nested read with `status: "error"` (or from a failed script) is still counted, since the record is attached regardless of the parent result's success and `arguments` are recorded at call start. pi's `addFileOp` also ignores status, so this mirrors pi exactly — and the failed path would surface in pi's compaction `readFiles` anyway. Not a defect; worth one line in the record so "脚本里记录的嵌套 read" is understood to include errored calls.

**SUGGESTION 5** — asymmetry in the extension's own `extractFileOpsFromMessage` (`file-ops.ts:63-74`)
`collectFileOps` does not read `nestedCalls`, so a nested SKILL.md read is now skill evidence at priority 3 but still absent from the handoff's own `<read-files>` block (it does enter pi's compaction `readFiles`). Pre-existing and out of slice scope, but now slightly sharper; either mirror the nested scan there or note the asymmetry in the fix-note.

**SUGGESTION 6** — negative pins for the nested path (tests)
Only the positive detection is pinned; the mutation (remove scan → 1 FAIL) is solid and the `isSkillFile` guard is shared with the direct-read path (already mutation-pinned), but a nested non-SKILL read, a nested `write`, and a malformed `nestedCalls` that must not throw are unpinned. Cheap `check(...)` lines. The fixture could also carry `status`/`complete` for shape fidelity — the current omission is harmless because the code path doesn't read them.
