## blocking

### B-1. §2.3 的 recheck 判据按字面不可实现：`renderKey` 无定义 + 缺空守卫 ⇒ 空项目永久自锁，或清空误拦（与 T6/R-3 相反）
【修正已有机制】对应 F1/F2（两次 append 的写序）与 F4（复现线）
- **file:line**：B §2.3（设计 51–56 行）；源码 `store.ts:62`（现有 `renderRaw`）、`store.ts:77`（`appendMemoryOp(rendered)`）；`poison.ts:156`（`memoryComparisonKey` 已存在，**不是 B 新引入**，`store.ts:11` 已 import）。
- **影响**：B §2.3 的条件是 `memoryComparisonKey(await readOptional(...) ?? "", limit) !== renderKey`，而 `renderKey` 在 §2.1–§2.3 与 §3 中都没有定义。两种自然读法都坏：
  1. **renderKey = 文件起始 key，两侧都做 `.trim()` 守卫（v5 step 1 的写法，也是 T6 需要的语义）**：`memoryComparisonKey("")` 是 `"# Project Memory\n"` 而不是 `""`（探针实测）。于是**全新项目/`MEMORY.md` 不存在**时 `renderKey=""`、`nowKey="# Project Memory\n"`，recheck 每次都触发 → 返回 `written:false`，并把空内容/空 key append 进 journal。实测：只有空 replace 的 journal 会让 `loadMemory` 返回 `unreadable:true`（`foldMemoryJournal` 在 `journal.ts:92-93` 跳过空 text，`store.ts:96` 对空 fold 报 unreadable）⇒ 每次 pass 都判陈旧、回复永不发布、errors.log 反复出现"无法读取"。这是**正常路径的自锁**，不是窄窗口。
  2. **不做空守卫（renderKey = `memoryComparisonKey(renderRaw)`，nowKey 同式）**：新项目不锁，但**窗口内清空**时 `nowKey="# Project Memory\n" ≠ renderKey` ⇒ recheck 触发、回复被丢弃，直接违反 B 自己的 T6"窗口内清空 ⇒ 不拦"与 §5 R-3"清空时回复胜出（既有语义，未变）"。
- **修复边界**（照 v5 step 8 的两段守卫即可，不必新增机制）：
  ```ts
  // 函数入口（entries 分支之前）读一次并复用，保证 renderKey 与采纳块的 external 同源：
  const renderRaw = await readOptional(memoryFile(projectRoot));
  const renderKey = renderRaw.trim() ? memoryComparisonKey(renderRaw, limit) : "";
  ...
  // §2.3，line 77 之前：
  const nowRaw = await readOptional(memoryFile(projectRoot));
  const nowKey = nowRaw.trim() ? memoryComparisonKey(nowRaw, limit) : "";
  if (options.basisKey !== undefined && nowKey !== "" && nowKey !== renderKey) {
      await appendMemoryOp(file, "replace", nowKey);
      return { written: false, kept: (await loadMemory(projectRoot, limit)).text };
  }
  ```
  并把该判定抽成**有名字、导出**的纯函数（如 `export function nextRenderSupersedes(renderKey: string, nowKey: string): boolean`）——B §2.3 只在散文里说"判定抽成小纯函数做单测"，代码块是内联的，不落名字 T6 无法 import。窗口内写的内容恰好等于即将发布的 `rendered` 时，v5 还有 `nowKey !== key(rendered)` 一项；B 删掉它只会多走一次"未发布"（内容其实已生效），不丢数据，见 nit-3。

## learning

- `memoryComparisonKey("") === "# Project Memory\n"`：**空与"空文档"不是一个 key**。任何"文件字节 key"比较都必须两侧同做 `.trim() ? key : ""`，否则空文件与缺失文件会让判定恒真（probe-b6）。
- 只有空 replace 的 journal 会让 `loadMemory` 报 `unreadable:true`（`journal.ts:92-93` + `store.ts:96`），所以"append 空 key"的误触发不只是日志问题，会污染读路径。
- B §2.2 的检查必须在**写路径种子之前**跑；种子会把读侧 `clipToLineBoundary(raw.trim())` 归一化成 `normalizeMemoryDocument` 形态，这正是 v5 把 check 放在 seed 之前的隐藏原因（B 重写时丢了这层）。
- `basisKey = existing.text`（读侧原值、不是 `fitted.text`）这个选择是对的；B §2.2 的"直接调 `loadMemory`、不抽 `resolveMemory`"也比 v5 的契约式抽取更不容易漂移。
- 取消重跑后 R1-B1 的整个面（rerun 入口、version 断言、四种退出、三态门控、去重回放）确实全部消失——复杂度审计的结论在 B 上成立。

## praise

- B 用 2 个代码落点 + 1 个类型字段把方案压回现场证据需要的形状；R1-B1 被"不做重跑"干净地消掉，而不是带着旧机制修补。
- 核心时序在 v5 顺序落点下实测工作：journal `[A, B]`、`MEMORY.md` 保留编辑原始字节（CRLF 也保留）、`fold === kept === loadMemory().text`、回复从不进 journal、`errors.log` 两行（`adopted …` + `not published …`）（probe-b2/b4）。
- 无编辑路径在四个 fixture（普通 journal、preserveMarker、legacy 无 journal、全新项目）上与真实 `recordMemoryDocument` 的 op/text 序列与 `MEMORY.md` 字节逐字节相同（probe-b4），§2.2 的 `undefined` 守卫也真的把 migrate/legacy 保持原样。
- §5 的"不做"表与审计判据对齐得很好：不写 stale 留档、不加 seam、不动锁、不动读侧。

## residual-risk

- **recheck→rename** 的字节窗口（B R-6）与 **mtime 回退编辑**（B R-1）保持成立；后者在"编辑落在模型调用期间但 mtime 早于 journal"时也不被 §2.2/§2.3 看见（renderKey 取自已回退的文件），与 v5 的 R-1 边界一致。
- **拒绝分支跳过 rotation/gitignore**：journal 可暂超 512 KB，无损坏（v5 R-12）。
- **pass 读→report 写之间 cap 变更**：一次假陈旧、丢一份回复，下一轮自愈（v5 R-17）。
- **未升级 peer 进程**仍会顶掉编辑（B R-5）；被丢弃回复无副本（B R-4）；这些都是 owner 明示接受的取舍，不建议在 B 上加机制。
