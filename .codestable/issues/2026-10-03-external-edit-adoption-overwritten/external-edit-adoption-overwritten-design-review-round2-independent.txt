## blocking

无。核心链路（判陈旧→不发布→锁外重跑→version 断言→留档）在真实原语上成立：probe-v2sim 的 normal/stale/TOCTOU 三场景全部符合设计意图，probe-pass 的 4 次 completion 上界也真实可达。

## important

**IM-1 `external-edit-during-publish` 在报告级没有落地：空内容时会撒谎，非空时无结果句/无重跑决策。**
- `file:line`：设计 `:124`（step 7）、`:166-168`（结果句清单）、`:173-187`（退出形态）、`:248`（T6）/`:249`（T7）；源码 `journal.ts:91-93`（`foldMemoryJournal` 跳过空 text）。
- 影响：probe-v2sim "clear-in-window" 实测——窗口内 `MEMORY.md` 被清空时，step 7 因 `nowKey="" ≠ renderKey` 触发，但 `appendMemoryOp("replace","")` 对 fold 是 **no-op**，第 5 步 append 的 `rendered` 仍是生效 fold；函数却返回 `written:false, reason:"external-edit-during-publish"`。report 随后会留档并说"未发布"，而 `loadMemory()` 返回的正是这条"被丢弃"的回复 ⇒ **INV-2/INV-3 双双被违反**，`R-1` 只说"清空会被回复顶掉"，没描述这个"顶掉了但说没顶掉"的倒置；若拿 T13 测该状态，`memoryComparisonKey(MEMORY.md) === fold` 必红。非空编辑触发时，§8 也没有对应结果句（"重跑成功"句说 rerun，"重跑未产出"句说没重跑），且 §9 没说它是否进入同一重跑循环。
- 修复边界：step 7 镜像 step 2 的空守卫（`nowRaw.trim() ? key : ""`），空内容一律按 R-1 的已接受语义走发布（或与 `rendered` 的 key 比较后返回 `{written:true}`），不做假 adopt；明确 `external-edit-during-publish` 与 `pass-reply-was-stale` 共用同一个有界循环，并补一条第二次陈旧的准确结果句；T6 增加"窗口内清空"断言 final 日志与实际 fold 一致。

**IM-2 `{written:true}` 不携带采纳事实，§8 的"常态"结果句不可产出。**
- `file:line`：设计 `:166` vs `:199-203`；`report.ts:123-135`。
- 影响：report 只能在 `recordMemoryDocument` 返回后知道"写成功/未写"，无法区分"写了且同一次写里采纳了外部编辑"与"没有任何外部编辑"。按 §11 的类型，`written:true` 无字段可判；无条件输出 `:166` 就会在绝大多数没有外部编辑的 pass 上谎报"adopted an externally edited MEMORY.md"。这正是 I4 要消灭的"成功日志说假话"。
- 修复边界：`{written:true; adopted?: string}`（或返回 `externalKey/foldKey`），report 只在 `adopted` 存在时输出该句；T1/T3 各加一条"有采纳/无采纳时日志不同"的断言。

**IM-3 编辑早于 pass 读取时，v2 流程表丢掉了既有采纳 append，INV-1 与 T12 的 legacy 承诺都会破。**
- `file:line`：设计 `:116-125`（step 3-8 未提 `entries>0` 的旧采纳块 `store.ts:61-71`）；设计 `:32-33`（INV-1）；`:253`（T12 要求 legacy 不传 `basisKey` 时行为与今天一致，而今天的行为正是 `store.ts:68` 的采纳 append）。
- 影响：probe-v2sim "edit-early" 实测——pass 读到 B（`basisKey == current == B`）时，按流程表实现 journal 为 `A→C`，B **不再单独进历史**，而今天（`store.ts:68`）是 `A→B→C`，且 `repro-write-ordering.mjs` S1 的输出即含 B。若实现者保留旧块，则 `store.ts:70` 的完成态日志会回来，与 §8"store.ts 只输出两条中性事实"冲突。两种读法各有一个必须明说的后果。
- 修复边界：在流程表里显式写"`entries.length > 0` 的既有采纳块保留/替换/删除"。保留则把 `:70` 的完成态日志换成中性事实，并在 §8 增加对应结果句；删除则必须弱化 INV-1 并解释原始外部字节为何不再需要单独留史（T12 的"逐字节一致"要相应改为只对 migrate 的种子路径）。

**IM-4 `basisKey` 的口径在 v2 被删糊了：用 `fitted.text` 会永久自锁，用规范化键在无 journal 项目会有一次假陈旧。**
- `file:line`：设计 `:92`（只说"pass 读到的记忆"）、`:212`（构造于 `:323`）、`:232`（R-9"同一个 `effectiveMemoryKey`"）；源码 `pass.ts:161`（`existing`）、`input.ts:44`（`fitted`）。
- 影响：v1 曾明写 `basisKey = memoryComparisonKey(existing.text, …)`，v2 删掉了表达式。probe-v2sim 的 trap 实测：模型输出上限 8192 时，`fitMemoryInput` 把 29728 字符的密集记忆裁到 7585 字符（`fitted.text !== existing.text`）；若 `basisKey` 取自 `fitted.text`，`current`（完整有效内容）永远不等 ⇒ 每次 pass 都判陈旧、rerun 再判、有界停止，**永不发布**（模型工作全部白扔）。若取 `memoryComparisonKey(existing.text)` 而 `current` 是无 journal 路径的 raw clip（probe-store (b) 实测 raw≠key），第一次 pass 会白跑一轮。
- 修复边界：明确写 `basisKey` 就是同一次 `loadMemory()` 的 `.text`（即 `effectiveMemoryKey` 的返回值），不是 `fitted.text`、不另做规范化；T3/T12 增加"prompt 被 clip + 无 journal"两个 fixture，断言不判陈旧、发生发布。

**IM-5 `effectiveMemoryKey` 的功能契约不完整，I2 的修复全押在它身上。**
- `file:line`：设计 `:79`（签名）、`:83`（引用 `store.ts:110-118`）；源码 `store.ts:119-146`（空 journal 的 `MEMORY.md` raw、`newestMemoryArchive`、`.pi`/OMP legacy）。
- 影响：设计说"loadMemory 改为调用它（可观察行为不变）"，但 `loadMemory` 还返回 `source/poisoned/damaged/unreadable`，这些必须留在外层；外层若照旧复制一遍分支，就回到"两处漂移"。更实际的风险是空 journal：该函数的条目参数是 `entries`，容易只实现 journal 分支。probe-naive-key 已演示后果：首页 consolidation 的 stale 分支什么都不 append，B 永不进 journal，T5 仍绿。
- 修复边界：把契约写成"与 `loadMemory().text` 逐字节相同，含 entries 为空时的 archive/legacy 回退"；T5 判据改为"B 进 journal 且 rerun 的回复发布"，T3 用无 journal fixture 断言"不判陈旧"。

## suggestion

- **S-1** §12 补回 R1 的残余："陈旧分支跳过 rotation/gitignore"（v2 仍成立），否则读者会以为 v2 已覆盖。

## learning

- **L-1** "发布前 recheck 要比**将被覆盖的那个文件自己的字节**，不能比有效内容"这条 v2.1 自纠是对的（probe-store (a)：`append(rendered)` 后 `loadMemory()` 返回 `rendered`，旧式子恒真）。这条经验值得进 compound。
- **L-2** "prompt 基线"与"prompt 实际装下的内容"是两个概念；任何跨层传递的基线都必须是读取函数返回的**精确值**，不能是它的规范化形式，更不能是下游裁剪结果。
- **L-3** 返回值类型要按调用方的**日志需求**定：report 要发结果句，就必须拿到能区分结果的事实（IM-2），否则会把日志压力推回被明确禁止的层。

## praise

- 三条不变式 + version 断言 + 锁外重跑 + 写前备份/留档这一套方向正确；probe 在真实原语上确认了 store 层各形态（peer、TOCTOU、正常路径）都按设计工作。
- §3 的调用上界这次是**真数过**的：probe 实测 4 次 completion/attempt 可达，不是纸面值。
- §13 的测试计划比 v1 强很多，T10/T13/T14 直接针对 R1 的 I3/T5/T8 缺口；设计 `:16` 主动标注 v2.1 未评审，透明度好。

## residual-risk

- R-1（mtime 回退 + 清空）与 R-3（rotation 默认 32000）、R-4（模块级单飞不按 root 键）的"接受"判定**合理**；但 R-3 的 T13 修法声明在 rotation 触发时不成立（N-5）。F9 的"重跑不加剧"没有被证明（rerun 与普通调用一样可能 join 到另一个 project 的 active pass），只是概率不变。
- 陈旧分支仍跳过 rotation/gitignore（R1 已列，v2 漏记）。
- `memory-stale-*` 永不 prune（与 overflow 同类）。
- R-2 的 recheck→rename 窗口仍是字节级损失窗口，接受。
- `repro-write-ordering.mjs` 仍是 store 级，不能验证 report 级重跑（T14 要重写才能覆盖）。
