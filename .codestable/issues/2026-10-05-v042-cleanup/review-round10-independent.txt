## suggestion
1. **设置固定比例时的回执不提示拒绝** — `run.ts:446` 对 `/handoff threshold <ratio>` 只回 `Handoff: threshold X% of the window.`，而同语法的 `/handoff threshold auto` 会回整条 status（那里能看到拒绝）。v0.4.3 起固定比例可能永不触发，这条确认句就成为「配置成功」的错误暗示；建议 ratio 分支也 render `handoffStatusLine(ctx)`。
2. **拒绝文案的杆杆在极端配置下不成立** — `threshold.ts:239-240` 固定说「raise /handoff threshold or lower /handoff budget recent」，但当 `floor > min(0.95*window, window-4000)` 时抬比例无效（例：window 64k、baseline 40k、keep 20k → floor 68k，95% 阈值只有 60k，文案重放同一句；只有降 keep 才可能过门）。建议点名哪根杆在当前数字下可解。
3. **`docs/handoff.md:12` 的固定 bullet 没提下限**（下限在 `:88-90` 才出现）；`docs/configuration.md` 的固定模式句也没提。建议就地加半句，别让读者以为固定模式仍「比例即决定」。
4. **测试没钉数值与等值边界** — `tests/handoff-test.mjs:566-577` 只断言 `fixed-below-floor` 原因与端到端 `/fixed/ && /floor/`，没钉文案里的 `10.0k/78.0k` 数字；`tests/autolearn-test.mjs:40-44` 没钉 `N more` 的算术。做了 `<= floor` 单侧变异（`/tmp/pc-mut-e`）→ 15/15 全绿，证明等值边界无测试覆盖。建议各加一条数字断言。

## learning
- 这条下限是**对触发阈值 T 的门**（`T >= B+K+8000`），不是对当下丢弃量的门：它保证「首次越过阈值的瞬间 drop≥8000」，但会在「越阈值已久、本来能丢很多」的会话里也一律拒绝。固定模式下阈值不随会话增长，所以 `ratio*window < B+K+8000` 的配置是**永久惰性**，与后来会话多大无关。文档（`docs/handoff.md:82/88` 与 `F=B+K+8000`）与回执都说清了这一点；这条判据下次评审固定模式改动时可直接复用。
- `loadShared`（同 jiti registry 载入 handoff.ts+settings.ts）是测模块级 config 的正确姿势，直连断言因此不是摆设。

## residual-risk（对抗性一遍的结论）
**最可能的用户可见回归：固定比例配置在升级后静默失效。** 判据/最小复现（我实际跑了 v0.4.2 archive 与 HEAD 对照）：临时项目 `project-context.json = {handoffThresholdAuto:false, handoffThresholdRatio:0.4}`，window 200k，会话约 25k token（`"context ".repeat(12_500)`），usage 85k（baseline≈60k，keep=20k）→ v0.4.2 在 `agent_settled` 发出 `/handoff force-auto`；HEAD 不发任何消息，只有 `/handoff status` 显示 `threshold fixed 40% (the 80.0k-token threshold is below the 88.0k-token floor … raise /handoff threshold or lower /handoff budget recent)`。这正是本次要修的「丢几千 token 的交接」，语义正确、CHANGELOG 与 docs 都披露了；残余风险在于**运行时没有任何提示**（与自适应一致），且设置回执不校验（见 suggestion 1）。「固定比例 + 大窗口 + 小会话」本身不是失败路径（大窗口把 0.1×W 抬得很高，通常过门）；真正会挨门的是小窗口/大 keep/厚 baseline 组合，文档给了公式与可操作回执，这一点我认为**已文档化，不判 important**。
