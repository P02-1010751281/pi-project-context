## Important

### I-1 `extensions/project-context/handoff/text.ts:27,75` — 被排除的 `!!` 作为 kept slice 首条时绕过 `SPLIT_TURN_MARKER`，successor 的 provider 首条变成 assistant

- **现象**：`USER_FACING_ROLES` 无条件包含 `bashExecution`，但 `excludeFromContext: true` 的 bash 经 `convertToLlm` 是**整条消失**的。`findCutPoint` 把 `!!` 条目本身当作合法切点时（它是 turn start），kept slice 以该条目开头 ⇒ `replayable[0].role === "bashExecution"` 通过 user-facing 判定 ⇒ 不插 marker ⇒ ensure 的 user-first 不变量被打破。
- **最小复现**（我的脚本，与仓库无写交互）：`u0 100k 字符 → a0 → u1 "look at the log" → !! 300k 字符 → a1`，keep 预算 20,000，`findCutPoint.firstKeptEntryIndex` 落在 `!!` 条目；`replayMessagesFor` 得到 `["bashExecution","assistant"]`；再追加交接 prompt 后 `convertToLlm(buildSessionProjection(...))` 得到 **provider roles = `assistant,user`，无 marker**（`excludeFromContext=false` 的对照组则是 `user,assistant`）。run.ts 的 setup/withSession 顺序（先 replay 再 `sendUserMessage`）不改变这一点。
- **方向**：在 Anthropic / Gemini 这类要求 user-first 的路由上交接续接请求被拒（该 marker 存在的理由就是这条，代码注释自己也这么写）。这是 pre-existing（R7 未引入），但 R7 的语义「`excludeFromContext` ⇒ provider 不可见」恰恰说明该判定该同步；不属于 ①–⑥ 任何一条。
- **建议**：修。把首条判定改成 provider 可见性（`role === "bashExecution" && excludeFromContext !== true` 才算 user-facing，或在 `isReplayableRole` 中直接过滤 excluded bash），并补一个 `!!` 开头的 replay 契约（含 `!!` 与 `!` 对照）。

## Nit

### N-1 `extensions/project-context/handoff/threshold.ts:125-130` — `isExcluded` 用 `=== true`，`convertToLlm` 用真值判断

- **现象**：`convertToLlm` 的条件是 `if (m.excludeFromContext)`；采样器镜像用严格 `=== true`。`excludeFromContext: 1`（外来/手改 JSONL）时 provider 丢弃、采样器照计。
- **最小复现**：`u1 4,000 字符 → bash(row, 40,000, excludeFromContext=1) → a2 prompt 5,000`：采样器把 a2 当「自身密度下界不达标」剔除 ⇒ `samples=0`、`baseline=max(0,5000-11001)=0`；provider 视图只余 `[user,assistant]`，诚实 baseline ≈ 4,500。
- **方向**：低读（fail-open），但只对畸形文件；pi 自身的写者只写布尔 `true`（`agent-session.js:3164`）。
- **建议**：登记残余或改成真值判断（1 行）。

### N-2 `design.md:182,199`（及 `review-report.md:272`）— 残余⑥ 的低读门限写错，被说成「膨胀 8 倍、不可能」

- **现象**：设计写「低读需要摘要膨胀到 `summary > 8·S + 7·K`」「低读需摘要膨胀 8 倍……模型摘要不可能」。实际条件（由 `bound = prompt − chars/8` 直接推出，chars 单位）是 **`summary > 2·dropped + kept_before`**，即 2 倍出头即可。
- **最小复现**：`s0 8,000 字符 → a0(usage prompt = 17,766+2,000, firstKept 保留) → compaction summary 20,000 字符 → u1 2,000 → a1`：`summary/dropped = 2.5×` 时采样器读 **17,266 vs 真值 17,766（低 500）**；`D=40k / summary=100k` 低 2,500；恰 2.0× 为 0。对 734 个真实会话文件扫描的 25 条 compaction 而言 0 条超过 2×（所以现实风险低，但「不可能」不成立）。
- **方向**：fail-open 被低报（残余登记不诚实完备）。
- **建议**：改数字并保留「本机 25 条真实 compaction 均 < 2×、pi 正常摘要远短于被压缩前缀」的实测措辞；不必改代码。
- 附带：`design §11` 的 fail-closed 高读枚举漏了保留的 `!`（非 `!!`）bash 的 `Ran \`cmd\`` 包装（实测 est −4、bound +2，几 token，同类），可顺手提一句。

### N-3 `threshold.ts:394-405` — `contextTokensAtRate` 仍计图像块（与 system），而 `chars`/`estimated` 已去图（R4）

- **现象**：回执/中途切分预算走 `estimateTokens(message)` 原值，图像按 4,800 字符计；`estimated`/`chars` 走 `textEstimate` 去图。R4 只改了密度基准，未登记这条调用面。
- **最小复现**：单条 user「100 字符文本 + 1 图」在 rate 4 下：`contextTokensAtRate = 1,225`，`messageTokens = 25`。
- **方向**：显示/预算过报（对 `prefixTokens` 的 snap 是保守方向，fail-closed），不是低读，但 ①–⑥ 都没写。
- **建议**：登记，或把回执口径也统一为文本（含一则措辞说明）。
