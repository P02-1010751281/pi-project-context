## 二、Findings

### I-1（important，fail-open，未登记）图像块打破 `chars/8 ≤ T` 前提
- 位置：`extensions/project-context/handoff/threshold.ts:137-139`（band 假设）、`:245`（bound = `prompt − ceil(chars/8)`）；pi 每张图固定计 4,800 字符：`…/pi-coding-agent/dist/core/compaction/compaction.js:182`（`ESTIMATED_IMAGE_CHARS = 4800`）与 `:193-195`。
- 现象：band 要求每张图 ≥600 token 才不低读；pi 自己的注释说该估法是 "conservative (overestimates tokens)"，小图（截图缩略图、low-detail 85 token 级）远低于 600。图像在 `plain` 中按 4,800 chars 计入 ⇒ 上界被推到真值之下，且会赢 min。设计/审查报告的三条残余都没有图像，测试夹具 0 个 image。
- 最小复现（我的副本）：`node review/image.mjs`——一个含 image block 的 user 消息 + 一条 `input = 17,766 + 100`（真值：B=17,766、图 100 token）的记录，`measureContext` 返回 `baseline 17,264`，**低 502**；每张更小的图多低约 500，多图叠加。
- 方向：fail-open（floor 低 ⇒ 过早起跳；`dropTokens` 高报）。
- 建议：修（把 image block 从 `chars` 下界中单列，按已知保守 per-image token 下界处理）或至少在 design/review-report 登记为残余并加一条会变红的契约；顺带把「>8 chars/token 的长空白/重复串」一并写进同一残余（本机无真实 tokenizer，见下）。

### I-2（important，fail-open，低读侧未登记）`prompt <= chars/8` 不是记录合格性；后插入分支内容会让旧记录赢 min 并低读
- 位置：`threshold.ts:196-198`（唯一守卫）、`:241-249`（全局 min）、`tests/handoff-test.mjs:1570-1592`（4b 夹具）；与 design `§5.3`（`design.md:68-70`「'截至 r' 的重建必须用 r 自己当 leafId，不能用当前叶子截断，否则样本点算错」）相抵触。
- 现象：实现只走一遍当前 leaf 的分支，把当前前缀字符数记给每条历史记录。若一条记录计费后分支前插了 replay（或 `context_edit` 把消息改长），该记录的 `chars` 包含它没被计费的字符，bound = `prompt − chars/8` 可落到真值之下并赢 min。4b 夹具正是此形状（注释自称「first local request built before the replay landed」），测试把读数 **9,499** 钉为期望、只断言 `>= 0`；报告只登记了反向（虚高）的残余③。
- 最小复现：`node review/replay-low.mjs`。B=17,766，先落 R 字符 predecessor replay、再是「计费早于 replay」的本地记录（prompt=18,766）：R=50k→baseline **12,016**、R=100k→**5,766**、R=140k→**766**（分别低 5,750 / 12,000 / 17,000）；R=160k 守卫跳过该记录、fallback 读 17,998；R 很大且 `usage.tokens` 小于分支估计时 fallback 读 0（旧公式同样会读 0，非本 diff 新引入，但与守卫叠加后更容易进入 `samples===0`）。
- 方向：fail-open（低读 ⇒ floor 低、早交接）。
- 建议：修或登记。修法之一：记录不合格性判据用「`prompt` 是否覆盖该记录自己的 pi chars/4 估计」（`prompt <= plainBefore` 即剔除——4b 与 replay 形状会被滤掉，正常同质/CJK 记录不受影响），或按 §5.3 用记录 id 重建「截至 r」的分支。

### N-1（nit，用户可见文档与自登记残余矛盾）「永不低读」
- 位置：`CHANGELOG.md:13-14`、`docs/handoff.md:84`、`threshold.ts:140`、`:244`；自登记残余见 `design.md:139-141`（残余②「注入块在会话内刷新时低读其增量」）。
- 现象：读数取的是**会话史中各记录 overhead 的最小值**，注入块在会话内增长后，min 停留在旧 overhead。自造夹具：record 0 B=17,766、record 1 B=+6,745，读 **18,866**，低于**当前**真值 24,511 约 5,645（= 增量 − 冠军记录的 slack）。这是残余②，但发布面（CHANGELOG/docs/代码注释）把它写成无条件「对真值的上界，永不低读」。
- 方向：fail-open（沿残余②）。
- 建议：修文案一行（加「以测量时刻的非会话开销为 B；会话内注入刷新会低读其增量，见残余②」），或把残余②写进 CHANGELOG 的残余清单。

### N-2（nit，残余③表述与拒绝话术）replay-only 虚高窗口不止「首回合」，且拒绝文案仍把 baseline 当杆
- 位置：`design.md:141`（「首回合只有 predecessor 重放记录时」）、`threshold.ts:465`（`below-quality-knee` 仍输出 "a smaller baseline or keep is the lever"，而同文件 `:277` 的注释刚说不该把 baseline 当杆）。
- 现象：活树会话前缀扫描显示 131,433 持续到 record 3（4 条记录后 record 4 才出现更小 bound），期间 `floor=159,433 > knee 157k`、`resolveThreshold` 返回 undefined（`below-quality-knee`）。方向 fail-closed，但确实把自动交接关掉，与 issue 的原始症状同形；窗口长度取决于「何时出现更小 bound 的记录」，不是「首回合」。
- 建议：把残余③的量化改为「直到出现更小 bound 的记录；实测活树 4 条记录」，并把拒绝句改成 keep/窗口是杆（baseline 是测量值）——后者是未登记的文案面。

## 三、我无法独立验证的点

- **真实 provider 的 chars/token 上界**：本机没有离线 tokenizer（pi 安装里无 tiktoken/JS tokenizer），「文本不会超过 8 chars/token」「长空白/重复串会不会越带」只能靠文档与 BPE 常识，不能实测；I-1 的图像结论引用了 pi 自己的 "overestimates tokens" 注释与常见视觉定价，也未在本机调 provider。
- **I-2 的现场发生窗口**：我复现的是分支形状（记录计费后前插 replay / `context_edit` 改长），没有复现产生该顺序的真实并发/时序（test 4b 的注释声称 handoff 会出现，我无法独立证实）。
- **活树会话的 B_true**：只有回归区间 30–39k 与报告的「+12k 高读」推算；没有 provider 直报，因此 52,151 距当前真值的符号/量级只能信报告。
- **多 provider / cache 记账细节**：`prompt = input+cacheRead+cacheWrite` 在不同 provider 的归一化（例如 input 是否已含 cacheRead）我没有真机验证。
