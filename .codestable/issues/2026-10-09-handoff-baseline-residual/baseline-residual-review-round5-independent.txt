### 3. `rate > RATE_MAX` 不可达：证明成立，删除安全

接受样本进入 rate 对时必满足：`newer.split===false`（否则 rate 循环 `continue`）且 `Δprompt>0`（否则 `continue`）⇒ 推入时一致性规则的条件 `previous && !split && prompt>=previous.prompt` 必为真且未丢弃 ⇒ `chars−chars_p ≤ Δprompt·8`，即 `4·added ≤ Δprompt·8` ⇒ `rate ≤ 8`。无 split / prompt 缩小 / `previous` 是更早样本的绕路均被 `newer.split` 与 `deltaPrompt<=0` 排除。删除后只剩 `rate < RATE_MIN`；即使未来有人放宽豁免，rate 也不再参与 baseline（只影响回执换算），隐患有限，且注释已把前提写在过滤点上。

## 二、Findings

### IMPORTANT 1 — 同一目标 `null → 非 null` 的编辑没有镜像 pi 的 last-wins 投影

- 文件:行：`extensions/project-context/handoff/threshold.ts:267`（`editedMessages` 定义在 `:134`，`seen` 状态在 `:264-271`）
- 现象：编辑顺序应用在**上一次编辑后的** `target.messages` 上；先 `replacement: null`（删除 → `messages=[]`）再 non-null 时，`editedMessages([], repl)` 仍是 `[]`，目标永久消失。pi 的 `buildSessionProjection` 用 `edits.get(targetId) = 最后一条 edit` 应用到**原始**消息上，provider 实际收到恢复内容。`:131-132` 注释声称「mirrors what the provider is actually sent」，此形状不成立。
- 最小复现（公开 API，pi 1.2.0）：
  ```
  sm = SessionManager.inMemory(...)
  u1 = sm.appendMessage(user "x"×1000)
  sm.appendContextEdit(u1, null)                                   // pi core _omitRecoveryAttempt 的用法
  sm.appendContextEdit(u1, {content:[{text:"z"×9000}]})            // 扩展边界草稿 ContextEditEntryDraft
  sm.appendMessage(assistant "ok", usage:{input:30000,...})
  ```
  结果：`buildSessionProjection()` 含恢复后的 9,000 字符 user；冻结 `measureContext` 的 `plainBefore=0, baseline=30,000, estimated=1`；pi 忠实值 `baseline=28,875, estimated=2,251`（over-read 1,125 = 恢复文本 token 的一半）。旧 `acbf228` 读 29,875（同样是高读，只是量不同）。可达性：pi core `agent-session.js:850` 每次 overflow recovery 追加 null edit；`ContextEditEntryDraft` 是公开 API（`types.d.ts:765`），`appendContextEdit` 允许同一 target 再次编辑。
- 方向：**fail-closed**（baseline 高读 → `resolveThreshold` 的 `baseline + keep + MIN_DROP` floor 抬高 → 自动交接可能被无声拒绝，正是本 issue 的症状）；同时 `estimated` 低读当前内容。注意它**不在**残余①的界限内：残余①只界赢家记录自身的字符，这里的高读由**另一条**消息的内容带来，可任意大。
- 建议：修。`seen` 里同时保存 `raw`（插入时的原始消息），每条 edit 都用 `editedMessages(raw, entry.replacement)` 重算（等价 pi map 的 last-wins）；补一条「null→content 恢复」契约。若 operator 按「有界 fail-closed 可登记残余」处理，可降为 nit，但残余①的措辞要相应扩大，且该语义目前 0 变异覆盖（我实现的修复 0 FAIL）。

### NIT 2 — `design.md:175` 的 compaction 可达性说法错误

- 现象：「`index > 0` 的 compaction 贡献 0；线性分支实测只会返回最新那条」——后半句错。两条 compaction 的线性分支 `buildContextEntries` 明确会保留旧 compaction 于 index>0（pi 自己的注释也如此写明），这正是该规则存在的原因。我的夹具 `[c_new, m1, c_old, m2, a1]` 中 `c_old` 在 index=2，扩展镜像正确。
- 复现：`buildContextEntries(twoComp, "a1")` → `0:compaction(c_new) 1:message(m1) 2:compaction(c_old)…`；ref=ext=58,470。
- 方向：文档（无行为影响）。建议：改为「旧 compaction 可因 `firstKeptEntryId` 落在其之后而保留在 index>0（pi `session-manager.js` 注释），本条即镜像该情形」，避免后人误删规则。

### NIT 3 — `CHANGELOG.md:26-28` 的旧 R4 文段仍带着已被推翻的结论，与同段 R5 文段自相矛盾

- 现象：同一未发布的 v0.4.10 段里，旧 bullet 仍写「prompt 缩小的区间不检查 —— …那正是 `min` 本就会跳过的情形」「只有在它前面还有可参照样本时才被上一条规则捕获」；这正是 design §10 已删除的错误表述，下面新增的 R5 bullet 又说该形状是登记的残余⑤、会读低。
- 建议：因为是未发布版本，直接把旧 bullet 改成 R5 的订正措辞（保留历史可另开「本版内被取代的中间形态」条目，该段已有此先例）。

### NIT 4 — 4d 夹具注释把「文件级形状」写成了真实时序

- 文件:行：`tests/handoff-test.mjs:1636-1640`，另 `design.md:163` 的措辞。
- 现象：注释说「a stale local record whose prompt was billed before a replay landed」。pi 的写者只在 leaf 追加，路径祖先在记录计费时必然存在，s3（stamp(2)）在 s4（stamp(3)）之前 ⇒ 「先计费后插入」不可复现（R4 审查员自己写了「无法复现产生顺序的真实并发/时序」）。真实可达的低读只有 `SPLIT_TURN_MARKER` 注入（数 token）。把它登记为对「外部写者/手改 JSONL」的文件级容错完全合理，但注释最好照 design §10 的口径写「文件级形状」，避免后人误以为现场会出现 50k 级低读。
- 方向：文档。建议：改注释/报告措辞。

### NIT 5 — 「8 条 context_edit 对读数无影响」的因果说明不完整

- 文件:行：`review-report.md:226`（R5 验收段），`CHANGELOG.md:46-48`。
- 现象：8 条条目对 `chars` 确实零影响（目标全为空 content），R4↔R5 delta 实测为 0。但这 8 条整体不是惰性的：删掉它们后 `split` 少 8 个豁免点，活树读数从 52,151/35 samples 变 **161,788/2 samples**。读者可能误以为 context_edit 条目可忽略。
- 建议：把句子补成「对 chars 无影响；其 `split` 效应在 R4→R5 间未变，所以两版现场读数逐位相同」。

### NIT 6 — 变异矩阵里「后缀不写回执口径 1」的补丁没有唯一定义

- 文件:行：`review-report.md:223-226`、`CHANGELOG.md:52-56`。
- 现象：按「把未校准的 4.0 印成测得 rate」打才红 **1**（我复现）；按字面「不写 `receipt at` 整段」红 **3**；按「永远印 fallback」红 **2**。R4 报告里已经用过精确措辞（「后缀把未校准的 4.0 印成测得 rate」），R5 缩写后丢掉了。
- 建议：恢复精确措辞（我这边测得：measured-rate 1 / always-fallback 2 / 删整段 3）。
