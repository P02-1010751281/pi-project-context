## 二、假绿风险复核

排除了你列出的主要嫌疑：

- **`autolearnAt:0` 被改写**：实测 `getConfig` 对 `{autoLearn:true,autolearnAt:0}` 返回 `autolearnAt=0, turns=20, interval=1800000`。`positive(0,0)` 返回 `0`（非 nullish，`??` 不落到 legacy）；`legacyDefaults` 只在 raw 为 `undefined` 时生效。→ 不会。
- **`runIsDisabled()`**：仅由 `session_start` 的 flag 设置；I 段只触发 `agent_settled`，moduleCache:false 下为独立模块实例，`runDisabled` 保持 false。trace 证明已穿过该闸门到达 archived 检查。→ 不会。
- **`resolveAuxModel` 失败被 warn-once 吞**：正向对照证明同一 `ctx2` 下模型确实被调用；若解析失败，正向对照会红（`makeCtx` 默认 `hasConfiguredAuth=true` 且 `model` 存在）。→ 不会。
- **`due` 靠 interval 而非 turns**：确实靠 interval（`autolearnAt=0` ⇒ `Date.now()-0 ≥ 1.8e6`），与注释「material and interval are already due」一致，非缺陷。

**残留（minor）**：正向对照与负探针**共用** `emptyProjectCalls`，且第二次 `agent_settled` 可能被 pi2 的单飞 `active` 合并。后果：在 archived 闸门被变异且 pass 到达模型延迟 >500ms 时，负探针假绿，而正向对照因计数被负探针的迟到调用「喂饱」也假绿 → 整个 I 段可全绿。实测用人为延迟验证：

| 破坏闸门 + 模型前延迟 | 无 reset | 加 `emptyProjectCalls=0` |
|---|---|---|
| 0 / 100 / 300 ms | 负探针 FAIL（检出） | 负探针 + 正对照 FAIL（检出） |
| **600 ms** | **ALL OK（漏检）** | **ALL OK（仍漏检）** |

现实延迟 5–20ms，500ms 窗口有 ~25–100× 余量，空载/8/32 hogs 下均检出，非现实风险；但这是测试对闸门灵敏度的硬边界。建议在正向对照前加一行 `emptyProjectCalls = 0;`（实测 pristine 下 10/10、空载全绿，且让正对照语义独立）；彻底修需在第二次 settle 前 await 第一次 pass（例如暴露/轮询 `active`），成本较高，可不做。

## 三、稳定性

- 正/负对照实际时延 ~5–20ms，500ms / 1500ms 界余量极大。
- `waitUntil` 语义正确：`while(Date.now()<deadline){ if(await predicate()) return true; ...} return await predicate();`，异步谓词支持、末尾补判一次，负探针不会因轮询步长（10ms）漏判一次已发生的调用（调用会被 `emptyProjectCalls` 计数保留）。
- 实测重复：pristine I 段空载 **20/20 绿**，16 hogs **20/20 绿**；整包 run-all 空载 ×2 + 16 hogs ×1 + 32 hogs ×1 全绿。

## 四、副作用 / 卫生

- **跨测试污染**：`loadDefault`/`loadNamespace` 均为 `moduleCache:false`，实测两次调用返回不同模块实例（config / project-state / factory 全部 `=== false`）。因此第二个实例的 `config.cache`、`projectRootCache`（均按 root 键）、`throttle`、`warnedRoutes`、`runDisabled` 与首个实例互相独立；pi2 也未复用 pi 的 handler 集合。→ 无污染。
- **`warnedRoutes` warn-once**：进程级但每注册实例独立，且 I 段未触发该路由告警。→ 无。
- **tmp2 清理异常路径**：`finally { rm(tmp2,recursive,force) }` 覆盖异常路径，✓。
- **fire-and-forget 与 rm 竞争（minor）**：`agent_settled` 的 archive/autolearn 均为 `void` 异步。I 段两次 `runHandlers` 后立刻 `rm(tmp2)`，在「pass 真正运行 + 高负载」下可让迟到写（`writeAtomic` 会 `mkdir(recursive)`）重建 `tmp2/.agents/memory/session-logs/INDEX.md`，留下 `pi-autolearn-empty-*` 残目录。实测 32 hogs + 破坏闸门连跑 3 次产生 3 个残目录（仅含 `INDEX.md`）；pristine 常规运行未复现。属纯 `/tmp` 卫生问题，不触及沙箱仓库，且该 fire-and-forget 模式在 H/既有 archive 中已存在。建议清理前 drain 一次（如等待一次 `waitUntil(()=>exists(sessionIndexFile)===false)` 或短 settle），可选。

## 五、代码质量

- **注释不准确（minor）**：`tests/autolearn-test.mjs:167-169` 注释称第二个实例是为了「a fresh config cache」。实测 `moduleCache:false` 下 config 缓存每 `loadDefault` 本就独立，且 `getConfig` 按 root 键，复用同一 factory 也能通过（并且仍能检出 archived 变异）。第二个实例的**真实**必要性是 `pi.exec` 的 cwd，以及避免与 `pi` 共享 `registerAutolearn` 闭包里的单飞 `active`/`throttle`。建议改述为后者，避免误导后人删掉 `loadDefault` 或误信缓存说辞。
