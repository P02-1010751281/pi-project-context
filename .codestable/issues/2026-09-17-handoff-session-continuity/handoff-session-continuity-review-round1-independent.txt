## 发现

### 无 blocking

### important

1. **marker 文件未被 gitignore，会随 `.agents/memory/` 提交进版本库** — `handoff.ts:421,442` 写 `<project>/.agents/memory/handoff-session-settings.json`；但 `project-state.ts:156` 的 `MEMORY_GITIGNORE_LINES` 未包含 `handoff-session-settings.json`，且 `git check-ignore` 确认该文件「not ignored」。后果：瞬态状态（含 `previousSessionFile` 绝对路径，泄露用户名/目录结构）被用户 `git add .` 误提交，且与既有「本地产物不外泄」约定（README 74 行）冲突。建议：把 `handoff-session-settings.json` 加入 `MEMORY_GITIGNORE_LINES`，并在 staging 时（像 `logError` 那样）调用 `ensureMemoryGitignore`。

2. **`getProjectRoot`（git 子进程，超时 3s）在每次 `session_start` 无条件先跑，早于 `reason==="new"` 判定** — `handoff.ts:477-487`：`restoreHandoffSessionSettings` 先 `await getProjectRoot(pi, ctx.cwd)` 再读 marker、再判断 `event.reason !== "new"`。后果：每次会话启动（startup/resume/fork/switch）都多一次 `git rev-parse --show-toplevel`，启动路径首当其冲（虽然 `projectRootCache` 按 cwd 缓存，但首个会话与切换 cwd 时仍触发）。修复 trivial：把 `if (event.reason !== "new" || !event.previousSessionFile) return;` 提到 `getProjectRoot` 之前。

### minor

3. **`setThinkingLevel` 失败被静默吞掉，无任何诊断** — `handoff.ts:510-517` 的 catch 只有注释，无 `logError`/notify。虽然 ExtensionAPI 的 `setThinkingLevel` 实际是 clamp 不抛（`agent-session.js:1360-1383`），这是防御性 catch，但万一抛（未来版本/自定义 provider）会造成 thinking 等级静默回退、且不可诊断，与 (c) 要求「不可重新引入静默丢失」稍有出入。建议 catch 里 `logError(projectRoot, "handoff:restore-thinking", error)`。

4. **`setModel` 抛错与「返回 false」两种失败被同一句「no authentication」提示掩盖** — `handoff.ts:500-503`：`await pi.setModel(model).catch(() => false)` 把 API 抛出的 `No API key for ...`（实际是 checkAuth 抛错）与 `hasConfiguredAuth` 为假的 `return false` 都映射成 `no authentication` 警告。语义上可接受但提示可能有偏差（例如模型解析后 setModel 因其它原因 throw 也会显示「无认证」）。建议区分：`catch` 里单独告警真实错误，仅 `=== false` 才提示无认证。

5. **会话头首行 >64KB 时不扁平化** — `handoff.ts:423,551-555`：`SESSION_HEADER_BYTES=64KB`，`buffer.subarray(0,bytesRead).split("\n",1)[0]` 截断后 `JSON.parse` 抛错 → 返回 undefined → `resolveHandoffParentSession` 回退当前会话（旧行为）。Session 头只有 id/timestamp/cwd/parentSession，正常远小于 64KB，实际几乎不可能触发，属低概率防护边界。

6. **`newSession` 抛错（非 cancel）不清 marker** — `handoff.ts:1140-1174`：只有 `result.cancelled` 分支 clear，`ctx.newSession` 抛错走外层 catch 只设 `failureBackoff`，marker 残留到 TTL。后果：旧会话仍活跃时，用户手动 `/new`（`previousSessionFile` 恰好=旧会话文件、reason="new"）会意外「继承」上次 handoff 的 model/thinking。这实际上与「设置连续性」意图一致，不算错误，但属可料想之外的继承路径，建议在 catch 里一并 clear 或至少注释说明。

- **a) 时序/API**：核实无误，`session_start` 的 `pi.setModel/setThinkingLevel` 安全且早于 `withSession` 续接提示词；`ctx.model/ctx.thinkingLevel/pi.getThinkingLevel/getProjectRoot` 在 handoff 命令上下文均可用（`types.d.ts:993,1006-1013`；`runner.js:503-530` 惰性 getter）。
