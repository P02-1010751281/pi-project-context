## Findings (full diff, adversarial pass)

**1. [nit] Duplicated unsatisfiable-cap warning construction** — `extensions/project-context/index.ts:119` and `:146`. Both lines compute `memoryReplyTokens(cap)`, `max(config.maxTokens, config.maxOutputTokens)` and nearly the same sentence; only the prefix ("Memory cap warning"/"Memory cap set to …") differs. Impact: a future constant or wording change must be mirrored; the two can silently diverge. Boundaries are otherwise clear (`status` vs. `max-memory` verb). Minimal fix boundary: one local helper returning the warning text; do not touch `memoryCapUnsatisfiable`.

**2. [nit] Duplicated percentage/size formatting** — `extensions/project-context/index.ts:71` and `extensions/project-context/memory/report.ts:222` build the identical `empty / chars, X% of the N-char cap` string with different cap variable names. Impact: user-facing strings in two modules; the `/memory` and `status` surfaces can drift. Minimal fix boundary: a shared `memorySizeLabel(chars, cap)` exported from `memory/document.ts` or `report.ts` (the underlying measurement is already centralized in `document.ts`, which is the right call).

**3. [nit] Awkward constant naming** — `extensions/project-context/shared/limits.ts:9,11`: `MIN_MEMORY_CHARS` and `MAX_MEMORY_CHARS_LIMIT` use different suffix conventions for a symmetric pair. Minor readability cost in `report.ts:109` and `index.ts:127,136`, where the clamp reads `Math.max(MIN_MEMORY_CHARS, Math.min(…, MAX_MEMORY_CHARS_LIMIT))`. Minimal fix boundary: rename only if the constants are touched again; not worth a standalone churn commit.

**4. [suggestion] Upper-bound half of the suggestion contract is unasserted** — `tests/memory-ops-test.mjs:187` asserts only `suggested >= cap`. The ≤200000 half is guaranteed by `report.ts:109` by construction, but no test would notice if the `Math.min(…, MAX_MEMORY_CHARS_LIMIT)` leg were deleted (the `MIN` leg is what the current test kills). Minimal fix boundary: extend the existing check to assert `suggested <= MAX_MEMORY_CHARS_LIMIT` (import from `limits.ts`).

**5. [residual-risk] The suggestion measures the reply, not the stored document's marker+newline** — `report.ts:109` vs. `document.ts:78`: `memoryDocumentChars` excludes the carried marker and `normalizeMemoryDocument` always appends a trailing newline, so `neededChars` is a tight-but-exact body+heading size. I could not construct a case where the suggested cap leaves the stored document marked (the `MIN_MEMORY_CHARS = 4000` clamp absorbs the off-by-one for the 3983–4000 body range). Accepted trade-off; no action needed.

**6. [residual-risk] A reply that copies an old marker is under-measured by the marker length** — `document.ts:58` (via `parseMemoryValue`) vs. `memory.ts:129`. `exceedsMemoryCap` deliberately ignores copied markers (M6), so a reply whose `body + marker` straddles the cap skips the condensation attempt and is clipped by `normalizeMemoryDocument`. This is the documented M6 trade-off, bounded to ≤ one marker line of content; already accepted in the design, not a new regression.

**7. [learning] The two round-4 defects were classic measure-vs-render drift** — measuring the raw reply (`memoryText.length`) and measuring the heading even for an empty body. Both are now pinned at the *unit* and *e2e* layers; the pattern to repeat is to assert the user-visible surface (`status` output, toast text) and not just the helper.

No blocking, important, over-abstraction, hashing-abuse, exception-handling, monkey-patching, or unclear-boundary violations found in the diff. `git diff --check` is clean; the tracked tree is clean.
