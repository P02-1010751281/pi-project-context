## IMPORTANT items

### I1 — M6 half-fix: copied marker still re-attached and drives status — **PARTIALLY-CONFIRMED**
Finding itself is real. Probes reproduce it exactly:
- `normalizeMemoryDocument` re-appends `previous` whenever the body fits: `memory/document.ts:95` (and `93-97`).
- Real command path (`/memory-learn` with a short memory + copied marker): written `MEMORY.md` ends with `_[memory truncated at 4000 characters: 1234 dropped]_`; `calls=1`; `errors.log` has **no** cap warning; `/memory` (`memory/report.ts:223`) and `/project-context status` (`index.ts:76`) both print “at the cap, so both ends were kept…” even though the render is 100 chars/3%. Confirmed.
- The next prompt does carry the marker (`memory/prompt.ts:35-38` `<existing-memory>` contains `loadMemory` text).

**The proposed minimal fix is wrong and I verified it breaks the suite.** `exceedsMemoryCap(storedRender, cap)` is *always false* for any stored render, because the stored body was already clipped to fit (marker excluded); probe: genuine clipped document → `isMemoryTruncated=true`, `exceedsMemoryCap=false`. Gating status on `exceedsMemoryCap` therefore silences the **true** cap report as well. I applied exactly that change in `/tmp/pi-mut2` and `consolidation-test.mjs` fails (`FAIL status names the cap`, the e2e cap test at `tests/consolidation-test.mjs:924-928`); 1 of 12 suites failed.

**Correct boundary:** keep `isMemoryTruncated` for display; fix the write/read separation. `recordMemoryDocument`/the write path should not carry a model-supplied `previous` when the body fits (e.g. a `keepPrevious:false` normalization for model replies, or strip a copied marker before `recordMemoryDocument`), while the read/fold path (`memoryComparisonKey`, `loadMemory`) must keep re-attaching markers or every genuinely capped render loses its durable trace and the render-vs-fold comparison changes. This is a design decision on marker provenance, not a one-liner; the review's “at minimum” sentence is the one part of the review that would make the code worse.

### I2 — `50[234]` misses 500/501 — **CONFIRMED**
`extensions/project-context/shared/call-policy.ts:28`. Probe: `500 → "other"`, `501 → "other"`, `502 → "transient"`. Tests cover no 5xx at all. The “almost certainly a typo” is inference, but missing bare 500 is real for a retry policy. Fix `\b50[0-4]\b` + a 500 test is fine; keep 501 optional.

### I4 — `memoryCapUnsatisfiable` vs `fitMemoryInput` — **PARTIALLY-CONFIRMED**
Real math mismatch, reproduced:
- `fitMemoryInput(dense 32000, "", configured 40000, ceiling 32768)` → `clipped=false`, `maxTokens=40000`; `memoryCapUnsatisfiable(32000,32768)=true` (warning fires).
- 20000 dense memory + 32000 dense context + reasoning → `fitMemoryInput` clips, `memoryCapUnsatisfiable(20000,32768)=false`.
- model `maxTokens:8192` + 20000 dense → clips, warning false.

But “the default config always warns” is **intentional**: `docs/configuration.md` explicitly says “默认 32000 对 32768 已贴边”, and `tests/memory-ops-test.mjs` pins “status warns when the default cap is unsatisfiable”. The noise criticism is fair but it is not an accidental bug, and the proposed fix (“include the context/reasoning reserve in the estimate”) would make virtually every project with a large context warn constantly. **Minimal correct boundary:** compare against the effective ceiling actually used by `fitMemoryInput` — `Math.max(config.maxTokens, config.maxOutputTokens)`, and the resolved model’s `maxTokens` where available (note `adaptiveOutputTokens` itself lets `configured` exceed `ceiling`, so the status check cannot be a pure function of `maxOutputTokens`) — or drop the static warning in favour of the pass’s own `clipped`/truncation diagnostics.

### I5 — Condense call failure discards a valid first result — **CONFIRMED**
`memory/pass.ts:34` unguarded `await call(...)` at `:134`. Probe: first reply valid but over-cap, second call throws “Connection error” → `calls=2`, `MEMORY.md` unchanged, reply “Project memory update failed”, `noteModelFailure` armed in `call`. The fix-note’s own wording (“成功且仍不超 cap 才采用；否则保留原回复”) covers the throw case, so the code violates documented intent. Fix boundary is right (try/catch around the condense call, keep `result`), but the catch should also make the pass report that the condensation failed rather than plainly “updated”.

## FINDINGS A MISSED

1. **M2 makes a valid first-reply context disappear.** `memory/pass.ts:135` replaces the whole `result` (`result = condensed`), and `report.ts:71` then sees no context. Probe: first reply has a valid `context` (summary “FIRST CONTEXT”) + over-cap memory; condense reply has fitting memory but no `context` → `CONTEXT.md` keeps “OLD CONTEXT”, errors.log says “carried no context section”, toast says “Project memory and context updated”. The first reply’s valid context — which would have been written without M2 — is thrown away. **Fix:** adopt `condensed` only for `memory` and keep `result.context`/`contextUnusable` when the condensed reply lacks them (or merge fields explicitly).
2. **`memoryFailureNotice` misclassifies local errors exactly like I3, but on the memory side.** `report.ts:156,263-273` runs `classifyModelFailure` on the headline of *any* `consolidate()` failure. Probe: a held `MEMORY.md.lock` (no model failure) produces the toast “Project memory update failed: timed out waiting for the memory write lock … **It will retry with backoff instead of on every turn**”, while no cooldown was ever armed (only `completeWithMeta` errors pass through `noteModelFailure`, `memory/pass.ts:87-92`). The review’s “the memory pass does it right” is true only for arming. **Fix:** use the class-specific wording only when a cooldown/disable was actually armed for that `(scope, project)`, otherwise the generic message.
3. **Autolearn’s session disable is silent.** After `AUTO_DISABLE_AFTER` misclassified (or real) failures, `autolearn/pass.ts:35` just returns; there is no counterpart to `MEMORY_PAUSED_NOTICE` (`report.ts:136-159`), and automatic runs are `silent:true`. Combined with item 2/I3, five EACCES/skill-read failures turn autolearn off with only an errors.log line. **Fix:** add an autolearn paused notice (once per project/process) or at least a log entry naming the disable.
4. **Idempotence counterexample in the new clipper** (see P4): `memory/document.ts:75-81,93-97`; document it or fix the heading-separator handling.
5. **Prompt budget vs normalized check mismatch.** `memory/prompt.ts:24` tells the model “memory_markdown must stay under N characters”, but `exceedsMemoryCap` measures `parseMemoryValue` output, which re-adds the 18-char `# Project Memory\n\n` prefix (`document.ts:26-47`). Probe: a heading-less reply of exactly 4000 chars → `exceedsMemoryCap=true`; 3982 chars → false. A model can obey the written rule and still trigger a (billed) condensation call. **Fix:** tell the model the normalized-document budget (subtract the heading overhead) or compare the same form the model is told.

## CRITERIA COVERAGE

Adequate on behaviour: hashing abuse (P6), monkey-patching (P6 + test-hygiene note), exception handling (I3/I5/P6, though it missed the memory toast path and M2’s context loss), over-guarding (N5), dead API (N4), append-only invariant (P3). Thin:
- **Over-design/over-abstraction:** the review doesn’t discuss the two parallel budget systems (`memoryReplyTokens`/`memoryCapUnsatisfiable` vs `fitMemoryInput`) that already disagree (I4), or the dead `FailureRecord` surface beyond N4.
- **Fragmentation / SRP:** no assessment of `memory/report.ts` (300+ lines: command registration + write transaction + cap accounting + notification policy) or of `index.ts`’s growing command dispatch; `memoryFailureNotice` living in the reporter while `call-policy` already owns classification is duplicated policy.
- **Duplicated code:** `clipToLineBoundary`/`clipTailToLineBoundary` duplicate `shared/text.ts:clipText`’s surrogate logic (N7 gestures at it but doesn’t call it duplication); percentage/status formatting is duplicated between `index.ts:71` and `report.ts:216`; the two failure-classification call sites (pass `call` vs reporter toast).
- **Readability/unclear boundaries:** the write-vs-read boundary of `normalizeMemoryDocument` is the root of I1 and the review’s fix proposal shows it wasn’t fully analysed; `firstLine`/dedupe-key semantics are under-described.
- **Test-hygiene argument:** the “250 ms would pass vacuously — it asserts calls===1, so it fails safe, not false-pass” sentence (`tests/call-policy-test.mjs` parked checks) is self-contradictory: a delayed second call after the assertion is exactly a **false pass**. The tests are still reasonable; the reasoning isn’t.

Overall: the review is accurate on most findings and its probes reproduce, but one proposed fix boundary (I1) is actively harmful, P4’s idempotence claim is false for a real input class, I4 overstates the “default warning” as a bug, and it missed the M2 context-loss and the memory-toast misclassification.
