### 发现的问题（分级）

**important —— 无。**

**minor：**

1. **`handoff.ts:589`（`readSessionHeader` 的 1MB 上限存在 off-by-one）** — `if (newline < 0 && read >= SESSION_HEADER_MAX_BYTES) return undefined;`。当首行恰好 **等于** 1MB（换行符位于字节偏移 1048576 处，即第 17 个 chunk 的起始）时，循环在第 16 个 chunk 后 `read` 已达 MAX、换行符尚未读入，被误判为「无聊头」而退回 chaining。注释声明是「*anything larger* reads as no header」，但实现把「恰好等于上限」也算进去。pi 自己的 `readSessionHeader` 用「1 字节 EOF 探测」显式区分「恰好 MAX 后 EOF」与「还有更多字节」。**为什么要点出**：语义与注释不一致，虽 `==MAX` 的真实会话 header 几乎不可能出现，且后果是优雅降级（退回 chaining）而非崩溃。**最小修法**：循环退出后多读 1 字节探测，或在 `read >= MAX` 判定前把 `Buffer.concat` 的拼接也纳入（`read === MAX` 时若 `Buffer.concat(chunks).length` 恰好等于 MAX 且是 EOF 则允许），对齐 pi 的边界语义。

2. **`consolidate.ts:118`（`contextUnusable` 判定比 prompt 声明的「exactly these keys」宽松）** — 新 prompt 说「context must be an object with exactly these keys… with other key names, is discarded」，但 `parseContext` 只强制 `summary:string`；`title` 缺失给默认值、`key_points`/`open_tasks` 若为错误类型（如字符串而非数组）被 `strings()` 静默置空、多余键被忽略，这些情况 `context` 仍「可用」且**不会**触发 `contextUnusable`/errors.log。**为什么要点出**：这不算把不可用当可用（summary 仍会落到 CONTEXT.md，不会 stale），但 prompt 与校验的严格度不对称，可能让 `key_points` 改名漂移（如模型写 `keyPoints`）继续静默丢字段——正是本次要追的同一类根因的一个更窄变体。**最小修法**：在 `parseContext` 中把 `key_points`/`open_tasks` 非数组（非 null）视为 invalid 一并返回 undefined（或单独返回一个 `shapeUnusable` 信号），或把 prompt 措辞从「exactly」改为与校验一致的「at least summary:string; key_points/open_tasks arrays」。

3. **`consolidate.ts:425`（errors.log 文案在「无既有 CONTEXT.md」时轻微不精确）** — 当 context 不可用**且** `existingContext` 为空时，代码会走 `fallbackUpdate(ctx)` 写入 fallback，但日志恒写「the previous CONTEXT.md is kept」，此时并不存在「previous」。纯文案失准，无行为影响。
