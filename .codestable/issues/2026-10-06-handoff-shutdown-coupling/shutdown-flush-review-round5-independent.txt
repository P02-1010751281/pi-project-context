## blocking

### B1r.（第 4 轮 B1 的反向路径）`adoptExternalEdit` 的 borrowed-key 分支仍在原来的读—stat 窗口里，且本轮新写的“pre-publish 复检兜底”承诺在真实时序下不成立；更新的手改仍会从 journal 与磁盘双双消失
- **file:line**：`extensions/project-context/memory/store.ts:78-88`（`borrowedKey === undefined ? readRenderWithMtime : undefined`；borrowed 时 `renderKey` 来自 `:210-211` 的早期 `readOptional`，mtime 来自 `:85` 的 `stat`）；对照例外声明 `store.ts:74-76`（注释）与 `docs/architecture.md:106`。调用点 `extensions/project-context/memory/store.ts:210-211`（`recordMemoryDocument`）与 `extensions/project-context/memory/report.ts:206`。
- **事实/复现**（探针 `tests/probe-borrow2.mjs`，FIFO 让 `readOptional` 拿到旧字节 V1，路径已换成 V2；`basisKey` 取该 pass 的 prompt-time 记忆＝journal seed，即真实语义 `pass.ts:332 basisKey: existing.text`）：
  ```
  [basis = prompt-time seed (realistic)]
    result: {"written":false,"kept":"… Older bytes handed to the reader.\n"}
    journal has V2(replacement): false
    effective memory source: journal | has V2: false | has OLD: true
    flush result: {"adopted":false,"written":true}
    disk after flush has V2: false | has OLD: true     ← V2 在 journal 与磁盘双双消失
  ```
  机制：`recordMemoryDocument` 早期读得 V1（`:210`），`adoptExternalEdit` 的 `stat` 已见 V2（`:85`），于是把**陈旧 key V1** 追加进 journal 并推新 journal mtime（`:87`）；随后 `:218` 的 basisKey 复检因 `current=V1 ≠ basisKey` 先返回 `kept=V1`，**永远走不到 `:235-236` 的 pre-publish 复检**。journal mtime 已被推过 V2，之后任何 pass 都判 `renderMtime(V2) <= journalMtime`，V2 再也无法被采纳；下一次 flush 走 `publish` 用 fold(V1) 覆盖磁盘。反向探针第二条（basisKey 恰等于 V1）才会走到复检并保住 V2 —— 说明“兜底”只对特例成立。
- **影响**：与第 4 轮 blocking 同类的静默数据丢失（更新的用户手改在 journal 与磁盘都不留），只是发生在 `recordMemoryDocument` 的借键路由上。触发需要两次外部写（一次在模型调用期间，一次落在 `readOptional`→`stat` 窗口内），比自读路径窄，但窗口里还夹着对整个 journal 的 `foldMemoryJournal`（`:83`，同步遍历最多 512 KB），并非只有微秒级。
- **修复边界**：让借键路径也做一致性读——`recordMemoryDocument` 用 `readRenderWithMtime` 取 render 并把 `changed` 透传到 `adoptExternalEdit`（`changed ⇒ return false`），或当 `preRead.renderKey` 提供时在 adopt 内重新 `readRenderWithMtime` 校验版本。改后此场景 adopt 直接放弃，`loadMemory` 会看到 V2 比未动的 journal 新而返回 V2，复检保留 V2，下一 pass 正常采纳。若选择维持现状，则必须删掉 `store.ts:74-76` 与 `docs/architecture.md:106` 里“pre-publish 复检兜底”的承诺，并在报告里记为**未关闭的 B1 同类**，不能写“第 4 轮全部处置完毕”。

## learning

- “同一版本”不变量必须覆盖**每个自带读取的调用方**。第 3 轮的 learning 已经说过一次，本轮修复只闭合了 `flushRender` 自读，借键路由仍留同型窗口；`docs/architecture.md:106` 把例外写成“复检兜底”，但复检被更早的 basisKey 拒绝抢先，承诺就不成立。
- 记录里的“已修”必须逐条对代码复验：CONTEXT `:7` 被第 2 轮 N4 和第 4 轮 I2 两次点名、两次写“已修”，HEAD 仍是原文——渲染态记忆会持续吃掉修正，除非把修正落成 journal op。
- 红数矩阵会随补钉漂移：第 4 轮加边界断言后，M8 的实际红数从 2 变 3，矩阵未同步。

## residual-risk

- `readRenderWithMtime` 的 `changed` 是 mtime+size 启发式：同尺寸且 mtime 浮点相同（粗粒度 FS / 保留 mtime 的写法）检测不到；此时自读路径可能与 B1r 同源。
- 读期间文件被删（`after` 未定义）时 `changed:false`、`mtimeMs:undefined` → flush 走 `publish` 重建 fold 并备份；属“缺失即重发”的预期行为，但并发删除会触发一次写。
- 最终 `stat`→`writeAtomic` 的窗口（以及 `adoptExternalEdit` 循环退出→`writeAtomic` 的窗口）仍是第 2 轮已记录的已知残留，注释里已写明。
- settle 路仍可用带 header 的散文回复换掉整篇记忆（第 1 轮 R1），本 issue 未覆盖。
- 报告/记忆/CHANGELOG 三处修复依赖手工同步，渲染提交会再次回退（CONTEXT `:7` 已示范）；若不落 journal op，下一轮还会复发。
