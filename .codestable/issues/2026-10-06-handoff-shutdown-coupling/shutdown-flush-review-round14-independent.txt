## important

### I1. `loadMemory` 新增的 `!renderRead.changed` 早退**零覆盖**：删掉它整套 441 条断言仍全绿
- `file:line`：`extensions/project-context/memory/store.ts:287`（判据）、`tests/consolidation-test.mjs:2006-2019`（所谓 `read race` 三断言）
- 实测：变异 `M4 = 删除 "!renderRead.changed"` → `fails=0, oks=441`。单点探针（同一条 FIFO 夹具）却显示被审代码的行为差异真实存在：

  ```
  ---- BASELINE  ---- source=memory.jsonl  text="# Project Memory…Journal seed…"
  ---- M4 变异   ---- source=MEMORY.md    text="# Project Memory…Older bytes the read must not adopt…"
  ```
  即 `loadMemory` 在 M4 下确实把「旧字节 + 新 mtime」当成了外部编辑返回（R-L1 定义的那一版），**但测试的三个断言只查下游 artifact**，下游的 basisKey 复核（`store.ts:255-258`）会在任何情况下拒绝；声明的 `adopted.source.endsWith("memory.jsonl") && adopted.text.includes("Journal seed")` 因此对两种实现都成立。报告里「把实现还原成两读配对后恰红 1 条、其余 2 条仍绿」的论证不精确：M1（整块还原）确实红 1 条，但它红的是**旧代码在 mtime 阶段拒了旧字节**，不是 `changed` 早退；“恰红 1 条”被当成了这条早退的覆盖证据。
- 修复边界（测试侧，**不需要新机制**）：在 `read race` 里追加一条能区分的断言（例如在该夹具里把替换文件 `utimes` 到 `Date.now()+60_000` 再断言 `loadMemory` 的 `source` 仍是 journal / 或直接断言 `readRenderWithMtime` 返回 `changed===true`）；否则应在报告里注明这条早退是「防御性、未被测试钉住」，而不是「变异恰红」。当前那句“把实现还原成两读配对后恰红 1 条”作为覆盖声明**超出了实测**。

### I2. 当前实测下 `changed` 早退在文件系统粒度内其实常常不触发（与 I1 共同解释假绿）

## learning

- **「测试注释声明的现场」必须与证据逐字节对齐。** 本修订的测试注释引用 119 字节的现场，却把现场里决定判据走向的 `# Project Memory\n\n` 省略了；省略的那 17 字节恰好是判据的充要证据。以后凡引用现场串，直接 `git show`/journal 行复制，不做手工缩写。
- **一个只在“抓旧字节版/不抓旧字节版”之间切换的行为，必须有能观察该行为的断言。** 下游复核（basisKey / append 前复核）会在任何情况下把结果收敛到正确 artifact，所以只查 artifact 的断言对中间态守卫是死断言——本仓已经在第 7 轮吃过一次“夹具不再制造竞态后全绿”的亏，这次的形状不同（竞态还在，坏中间态没被观测量捕获），教训相同。
- **启发式（mtime+size）本身会成为“测试为什么绿”的原因。** 当被修行为依赖文件系统粒度时，绿可能是粒度给的，不是代码给的；区分这两者需要把替换的时间戳显式拨动（`utimes`）。
