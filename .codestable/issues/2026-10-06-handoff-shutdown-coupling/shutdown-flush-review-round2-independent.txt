## important

### I1. `store.ts:106-107` 的注释声称采纳循环关掉了覆盖窗口，但最后写回仍会覆盖未折叠的字节
- `extensions/project-context/memory/store.ts:106-107`：
  ```ts
  // An edit can land between an adopt read and the write below; adopt until the render and the
  // journal agree, so the flush never publishes a fold over bytes it did not fold in first.
  ```
  循环（`:109`）只是在 `adoptExternalEdit` 返回 true 时再试一次；一旦它返回 false（正常出口），flush 走 `readMemoryJournal → fold → readOptional(file)`（`:110-119`），若 `onDiskKey !== foldKey` 就无条件 `writeAtomic(file, folded)`（`:125`）。因此**在最后一次 adopt 读盘之后、`readOptional` 之前落下的手改，仍会被 fold 覆盖**——而且这次不 mtime 判断、不追加 journal。
- 实测（`/tmp/pi-rev2-race`，在循环后插入一个模拟并发手改写）：`flushMemoryRender` 返回 `{"adopted":false,"written":true}`，磁盘上的并发手改 `CONCURRENT-HAND-EDIT` 被 `fold` 覆盖。也就是说循环把窗口从「一次 adopt 读 → 写」缩到「最后一次 adopt 读 → `readOptional`」，但**没有**兑现注释里的绝对保证。
- 该窗口只在非锁写入者（人肉编辑 / 旧 build）下落地下手；同版本扩展走同一 `withMemoryLock`，会被串行化。
- 修复边界：把写回前的 `readOptional` 结果当作「刚读到的 render」，复用 `nextRenderSupersedes`/adopt 语义——若是更新的不同字节，先 `appendMemoryOp(file,"replace",nowKey)` 保住它，再决定是否写 fold；做不到就至少把注释降级为「循环缩小但不消除窗口」，并与 fix note 的「写回的最后一个窗口」保持一致。注意：fix note 已经承认该残留，但代码注释（和 `:121-122` 的「a fresh edit would have been adopted above」）仍是强保证。

### I2. `headless-runs` skill 的两条退出承诺与代码相反
- `.agents/skills/pi-project-context-headless-runs/SKILL.md:106`：
  > “Do not expect a consolidation pass, a `CONTEXT.md` write or **extra backup files** at exit, and **a project with no journal is left untouched (no memory directory, no lock)**.”
- 与代码/本仓自己的更正冲突：
  - 陈旧/撕裂 render 的重发路径会先 `backupMemoryBeforeWrite(file)`（`store.ts:123`），产生 `MEMORY.md.memory-backup-*`——新增测试「replacing a render backs it up first」正是在钉这件事；本轮 CHANGELOG `:13` 也写「写前备份」。
  - 裸项目的 `.agents/memory` 由**存档层自己的锁**创建（`archive/archive.ts:139 → updateSessionIndex → withMemoryLock → shared/lock.ts:183 ensureMemoryGitignore`），注册顺序上存档 handler 先于记忆 handler；round1 报告与 fix note 都已实测更正过这一点。
- 影响：headless 使用者按 skill 预期「退出无备份、无目录、无锁」会误判真实行为。
- 修复边界：改成「该 flush 不调模型、不写 `CONTEXT.md`、不生成内容；但陈旧/撕裂重发会在写前留一份备份；flush 自身不取记忆锁，存档层仍可能建目录并取其锁」。

## learning

- **`Date.now` 拨动是有效的，不造假红**：`report.ts` 的退出如果改回 `consolidate(ctx,true,true)`，`forceDedupeMs(15s)` 会因种子 pass 与退出相隔毫秒而把它去重——旧测试因此恒绿。测试把 `Date.now` 前拨 60s 后，M1 精确变红 5 条（含「退出无模型调用」「退出不合成内容」）。flush 自身不读 `Date.now`，所以拨动不会让修复路径产生假红。
- **`onDiskKey` 与旧 `memoryComparisonKey` 并非严格等价，但差异是刻意的**：`memoryComparisonKey("")` 并不是空串——`normalizeMemoryDocument` 会补 `# Project Memory\n`（`document.ts:27,125-128`）。旧代码 `memoryComparisonKey(onDisk) === memoryComparisonKey(folded)` 在「缺 render + fold 恰为裸 header」时会判等、**不写**；新代码 `renderKeyOf("") === ""` 为假，于是重发 fold（`:120`）。对非空 render 两者逐字节同口径；纯空白 render 同旧（都写）；缺失 render 新行为即 I5 要的「重发」。所以这是修复点，不是回归。
- **采纳循环的终止性成立**：每次 true 都 append `renderKey`，下一次 `foldedView` 已含该 key，`renderKey === foldedView` 立刻返回 false；最多 3 次，无热循环。
