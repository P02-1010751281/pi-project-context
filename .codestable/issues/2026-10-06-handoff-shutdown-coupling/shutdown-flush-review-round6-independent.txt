## nit

### N1. FIFO 用例的失败路径仍会挂起：`open` 的 10s `Promise.race` 只让断言失败，不终止进程
- **file:line**：`tests/consolidation-test.mjs:1969`（`await Promise.race([open(raceFile, "w"), …reject…])`）。
- **事实**：第 5 轮 N2 的处置写“写端 `open` 也套 10s `Promise.race` 超时；连跑 3 次稳定通过”，暗示失败路径已不挂起。但 `Promise.race` 只拒绝 JS promise，不取消底层对 FIFO 的阻塞 `open`。我用最小复现验证：`open(fifo,"w")` 与一个 2s reject 赛跑，超时后 `catch` 里 `rm` 掉 FIFO 再 throw —— node 仍不退出（`timeout 8 node` → `exit=124`），因为挂起的 `fs` 请求仍保持事件循环活跃。也就是说，若 `flushMemoryRender` 在成为 FIFO 读者之前就 reject（唯一现实触发是 `withMemoryLock` 5s 未取到锁），测试会先打印 FAIL、随后挂起，直到 `run-all.mjs` 的 60s 超时（standalone 直接跑则无限挂起）。
- **影响**：纯测试健壮性；当前夹具里 `flushMemoryRender` 一定会走到 `readOptional` 成为读者，故成功路径确定（我连跑 3 次三断言全 OK），失败路径不可达但有陷阱。
- **修复边界**：不要只加 `Promise.race`。要么在超时分支 `process.exit(1)` / 设置 `process.exitCode` 后强制退出，要么整段 FIFO 场景放子进程跑并由父进程硬超时，要么用 `fs.open` 的非阻塞语义（自旋 handler）代替阻塞写端。成功路径无泄漏（写端 close、读者 close、`rmTemp` 兜底）。

### N2. `docs/architecture.md:106` 的措辞与代码有细微出入（“用本调用的自读做判定”）
- **file:line**：`docs/architecture.md:106` vs `extensions/project-context/memory/store.ts:85-95`。
- **事实**：借键路径的实际判定是：`renderKey = preRead.renderKey`（append 的值也是它），fold 等值判断与空值判断用的都是**借用键**；本调用的 `readRenderWithMtime` 只提供 `mtimeMs`，再由 `verify` 要求“文件当前字节的 key 恰等于该借用键”。因此“自带 render key 的调用方也用本调用的自读做判定”只在“mtime + 事后校验”意义上成立，不是逐字（判定用的 key 本身不是自读产物）。
- **影响**：读者可能以为借键被直接丢弃；实际语义仍正确（verify 保证与当前文件一致）。**修复边界**：改为「自带 key 的调用方，其 mtime 判定取本调用的自读，并在 append 前校验该 key 仍是文件当前字节」。

### N3. “重发触发条件”在 `CHANGELOG.md:13` 与 fix note 里少写了“空/空白 render”

## learning

- “同一版本”不变量必须逐站点覆盖**读取方**，而不只是写 journal 的那一处。第 3–5 轮连续收敛了 flush 复检、adopt 自读、adopt 借键；本轮探查发现 `loadMemory` 这条**纯读**站点仍保留“旧字节 + 新 stat”配对——它的危害之所以不升级，是因为唯一的下游写路径用新的 `nowKey` 复检兜住了它，而不是因为它本身安全。判据与读取分离时，安全性往往来自别处的二次校验，这是本仓最该避免的隐性依赖。
- 单一守卫的收敛方向是对的：`adoptExternalEdit` 的 `verify` 同时服务自读与借键，删掉重叠的 `read.changed` 早退没有造成覆盖损失（`changed` 仍有 `verify.changed`、`flushActionOf` 的 `render.changed` 两个读者）。但“删它测试不变”只能证明它与 verify 重叠，不能证明任何 `changed` 判定都多余。
- 变异红数必须逐条独立复位复测：我第一次把 M7/M8 并行施加在同一副本上，得到被污染的 4 红；串行复测才是 M7=1、M8=3。报告里的红数本身没错，错的是并行变异手法。

## residual-risk

- **R1（本轮新增、未登记）`loadMemory` 的 read→stat 配对仍是“陈旧字节 + 新 mtime”**：`store.ts:279` `readOptional(target)` 读字节，`:285` 才 `stat(target)` 取 mtime，`:286` 再 `stat(journal)`；若 render 在两者间被替换，`external` 是替换前字节、mtime 是替换后文件的。我写了探针（`module.syncBuiltinESMExports` 只改 `readFile` 指向旧字节、`stat` 保持真实）：`loadMemory` 返回 external 的 V1、而磁盘是 V2 且比较用的是 V2 的 mtime。**可达性**：需并发写落在读与 stat 之间（微秒级外部窗口）。**危害**：只影响该次注入/提示/`/memory status` 的读数；它不写盘，无法单独推高 journal mtime；`recordMemoryDocument` 随后的 `nowKey`（`:244`）读的是新鲜字节，会拒绝发布。故不是 blocking，但确实是同一类缺陷的第 4 个站点，且不在 fix note/报告的 residual 列表里。修复边界见 S1/S2。
- **R2（本轮新增、未登记）`rotateMemoryJournalIfNeeded` 的 copy→rename 窗口**：`journal.ts:108` 读 entries、`:131` `copyFile` 归档、`:137` `rename` 覆盖。若在 `readMemoryJournal` 之后、`rename` 之前有 append，归档副本与 `collapsed` 都不含该 append，rename 会丢掉它。**可达性**：所有协作写入都在 `withMemoryLock(memoryFile)` 下串行，故对扩展自身不可达；仅对手工改 journal / 抢锁的外部写可达。**危害**：journal 丢一条记录。属低概率残留，建议登记即可。
- **R3（已登记，不重复报）最终写回窗口**：`recordMemoryDocument` 的 `nowKey`（`:244`）到 `writeAtomic`（`:253`）之间、以及 `flushMemoryRender` 的 `readRenderWithMtime`（`:176`）/备份到 `writeAtomic`（`:194`）之间的并发手改仍会丢；adopt 的“最后一次 verify 到 append”同理。报告“残留风险”节与 `MEMORY.md` invariant 已写明。
- **R4（已登记）** `readRenderWithMtime` 的 `changed` 是 mtime+size 启发式，保留 mtime 或粗粒度 FS 下同尺寸替换检测不到；超帽手改“journal 裁剪键 / 磁盘原文”；settle 路仍可用散文回复换整篇记忆（本 issue 外）。
