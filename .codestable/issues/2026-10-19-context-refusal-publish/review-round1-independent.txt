## Answers to the six questions

**1. Is `contextWritten = Boolean(update) && !memoryRefused` the right gate?**

Structurally, yes for the state it names. There is exactly one context write (`extensions/project-context/memory/report.ts:294`), and every path to it now passes through `contextWritten` (`:264`, `:287-302`). `memoryRefused` is assigned only inside `if (memoryChanged)` (`:201-214`), and a refusal can only arise from `recordMemoryDocument` (`store.ts:246-249`, `:260-268`), so no path reaches the write with `memoryRefused === true` and `contextWritten === true`.

Path-by-path:
- memory changed + published + `update` truthy → context written (`:264`, `:294`).
- memory changed + published + `update` undefined → no write, no claim; report `"updated"` (`:303`).
- memory changed + refused + `update` truthy (reply context or `fallbackUpdate`) → skipped, diagnostic at `:291`, stale toast/reply (`:313`, `:588`).
- memory changed + refused + `update` undefined → no write; older “carried no context section” line may fire (`:180-189`); stale toast/reply.
- memory unchanged (empty/short) → `memoryRefused` stays `false`; context still written (`:264`). This is the keep-adoption path the design protects, and tests `consolidation-test.mjs:1647` / `:2074` pin it. No regression.
- `fallbackUpdate` on a fresh project (`:173`) is truthy, so a refusal now skips the placeholder as well. That is consistent with “nothing publish-side on refusal”, but it is not the reply’s context section; the log wording is wrong (finding I1).
- deduped (`:161`) and thrown-error (`:352-366`) paths never reach the write.
- two concurrent callers of one outcome: `written` is claimed synchronously (`:160-164`), the second returns `"deduped"`; only one reaches the gate. A different pass gets a new outcome/version and a fresh basis. No refused reply’s context is published.
- The `written` claim is set before the memory write and **stays set on a normal refusal**; a replay of the same outcome is deduped, not re-published. That is safe for context, though an immediate `/memory update` then says “already up to date” (preexisting; see R2).

What the gate does **not** cover is a stale context with **no memory refusal** (context-only race, or keep-adoption/semantic-empty reply). That is not a “refused reply”, but it is the same lost-update class; see R1.

**2. Does the reply/toast tell the truth in every branch?**

Exact strings (probed; the refusal toast and command reply are the same string because both call `staleKeepSentence`):

- (a) memory refused + context carried: `Memory: kept the newer MEMORY.md you edited (this pass's reply was built from an older memory and was discarded).`
- (b) memory refused + no context: the same string.
- (c) memory unchanged + context written: toast `Memory: context updated; memory was kept unchanged.` Command reply: `Memory: context updated; memory was kept unchanged (the reply was not a writable memory document).` (or `…(the reply was too short to be a change).`).
- (d) memory changed + context written: toast `Memory: updated /path/.agents/memory/MEMORY.md`; command reply `Memory: updated.`
- (e) memory changed + context missing (`update === undefined`): toast `Memory: updated /path/.agents/memory/MEMORY.md`; command reply `Memory: updated.` No context claim.

These are truthful **by omission** for (a)/(b): the new reply no longer claims “context updated”. It does not affirmatively say “context was not updated”, which is what `CHANGELOG.md:13` says it does (N4). `report` remains `"updated"`/`"clipped"` (`:303`), so `/memory update` shows the refusal sentence at **info** severity unless the prompt was clipped (`:472`), while the automatic toast is `"warning"` (`:313`). The content is right; the severity is not (N3).

**3. Is the new diagnostic logged exactly once per refusal?**

It is logged once per `consolidate` call that both refuses and has a truthy `update`: one call site (`:291`), one `if (update)` block (`:287`), and concurrent callers of the same outcome dedupe before it (`:161`). It is not logged when `update` is undefined (reply has no usable context and a previous `CONTEXT.md` exists); the older “carried no context section” line (`:180-189`) handles that.

Two caveats:
- On a **fresh project with no `CONTEXT.md`**, `update` falls back to `fallbackUpdate(ctx)` (`:173`), so the new line fires even when the reply carried **no** context section — contradicting the external-edit test’s label “there was no context section to skip” (`external-edit-test.mjs:230`). That test passes only because its fixture has an existing `CONTEXT.md`.
- It **interacts with `contextShapeWarned`**: the shape warning runs before the refusal is known (`:174-179` vs `:214`). If the previous context is empty and the reply’s context is unusable, it says `only a placeholder context was written`; the new gate then skips the placeholder and the new line says the previous file stays effective. Both are false on a fresh project. Probe output:
  ```
  ... the consolidation reply carried a context section that could not be used ...; only a placeholder context was written
  ... the memory changed while this pass's reply was being built; the reply was not published ...
  ... the refused reply's context section was not published; the previous CONTEXT.md stays effective
  --- context --- (none)
  ```
  The marker is consumed, so the false claim is not corrected later. See I2.

**6. Adversarial pass**

I did not find a path where a **refused** reply still writes `CONTEXT.md`: the write is single-sited and gated, `fallbackUpdate` is also gated, `written`/dedupe prevents a second attempt of the same outcome, and thrown errors skip the write. The keep-adoption path is not dragged into the gate; its tests stay green.

The real remaining lost update is **context-only**: `pass.ts:182` reads `CONTEXT.md` for the prompt; if a human edits it during the model call and `MEMORY.md` does not change (or the reply is semantic-empty/short, or memory was cleared), `memoryRefused` is false, `contextWritten` is true, and `:294` overwrites the newer context with the reply’s stale context. The field incident happened to include a memory race, so this fix covers that incident, but it is a memory-basis proxy, not a context-basis guard. A context basis key would be the direct mechanism; the trade-off is a new normalization/publish-key/CAS surface and a conflict with the deliberately pinned keep-adoption behavior (“the same pass still writes the context” at `consolidation-test.mjs:1647`). The narrow fix is defensible for this commit; the residual should be registered/tested rather than silently assumed closed.

Also, `staleKeepSentence(true)` and `info.contextWritten === true` in the stale branch are now unreachable (`:264` makes `contextWritten` false whenever `memoryRefused`); the parameter is dead but harmless. The test’s “there was no context section to skip” assertion passes for a fixture-specific reason, not as a general property.

## Findings

### Blocking

None. The gate itself does not publish a refused reply’s context.

### Important

**I1. `extensions/project-context/memory/report.ts:291` — the new diagnostic can assert a previous file that does not exist.**
`update` includes `fallbackUpdate(ctx)` (`:173`). On a fresh project (no `CONTEXT.md`) where `MEMORY.md` appears during the pass, the memory is refused, `contextWritten` is false, and the log says:
`the refused reply's context section was not published; the previous CONTEXT.md stays effective`
while there is no `CONTEXT.md` at all. If the reply carried no context section, it also calls the locally generated fallback “the refused reply’s context section”. This is a new false operator-facing statement in the durable trace, and it contradicts `external-edit-test.mjs:230`’s “no context section to skip” label as a general claim.
**Smallest fix:** compute the diagnostic from `existingContext.trim()`, `outcome.result.context`, and `contextWritten` — e.g. only say “the previous CONTEXT.md stays effective” when one exists, and say “no CONTEXT.md was written” for the fallback case. Do **not** change the gate or start writing the fallback on refusal in this fix.

**I2. `extensions/project-context/memory/report.ts:174-179` vs `:264`/`:291` — the shape warning now contradicts the refusal.**
The `contextShapeWarned` block runs before `memoryRefused` is known. With an empty previous context it logs `only a placeholder context was written`; the new gate then skips the placeholder and the new line says the reply’s context was not published. `contextShapeWarned` is consumed, so the false line is not corrected later. `design.md:168` still justifies keeping the warning with “CONTEXT 照写 ⇒ 仍成立”, which is exactly what this change removed. Probe reproduced the three-line contradiction with no `CONTEXT.md` on disk.
**Smallest fix:** move the shape warning after the memory decision (or make its `kept` clause depend on `contextWritten`/`memoryRefused` and `existingContext`) and update the design row. Do **not** change the memory/context gate or the once-per-project marker’s purpose.

### Learning

**L1.** The design note placement is a live instance of the MEMORY.md table-contiguity rule; `run-all` checks trailing blank lines and rendered bullet punctuation but not Markdown table contiguity, so that rule still needs a manual check.
**L2.** A memory-basis refusal is a proxy for “the reply’s context is stale”; it fixes the field race but not the class. When a fix reuses a neighboring guard, state the guard’s actual predicate and the paths it cannot cover.
**L3.** A “no diagnostic” assertion can pass for a fixture-specific reason: `external-edit-test.mjs:230` passes because the fixture has an existing `CONTEXT.md`, not because the code generally suppresses the line when the reply has no context section.

### Praise

The core gate is placed at the single context write, not sprinkled across branches; the refusal string is shared by toast and command reply; the keep-adoption behavior is preserved and still tested; the store’s `basisKey` refusal is reused rather than duplicated; the new consolidation assertion fails under the exact mutation while the normal-path positive controls stay green; and the refusal no longer claims a context update. The field path is genuinely fixed.

### Residual-risk

**R1. Context-only lost update (main remaining gap).**
Pass reads `C1` (`pass.ts:182`); a human edits `CONTEXT.md` to `C2` during the model call; the reply carries a `C1`-based context; `MEMORY.md` is unchanged (or the reply is semantic-empty/short, or the owner cleared memory) → `memoryRefused` is false → `contextWritten` is true → `:294` overwrites `C2`. The fix note/docs only promise the memory-refusal case, so this is not a broken promise, but it is the same class of lost update. A context basis key would close it; the trade-off is a new mechanism and a change to the pinned keep-adoption semantics. Do not treat the current gate as a general context CAS.

**R2. Deduped retry after a refusal.**
The `written` claim is set even on refusal (`:160-164`). An immediate `/memory update` within `forceDedupeMs` returns `"deduped"` and the user sees `Memory: already up to date (deduped recently); nothing was rewritten.` even though the pass was refused and the context is still stale. This is preexisting dedupe behavior, not introduced here, but the fix’s “truthful command reply” claim does not cover it.

**R3. `lastWrite` concurrency.**
A concurrent pass can `lastWrite.delete(projectRoot)` between a refused pass setting its info and the command reading it, yielding `Memory: updated.` for a refused pass. Known residual in the design review; not addressed here.

**R4. No CAS on the context write.**
The memory write is under a lock and has a basis check; the context write is outside both. The design accepts the residual window. The fix reduces the field case but does not add a context CAS.
