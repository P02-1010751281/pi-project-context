### Findings

**F1 — important — `pickToolCall(toolCalls, name)` cannot implement the policy it is pinned to implement (missing reply text).**
- Where: design 接口改动 lines 252 and 255; current `shared/llm.ts:103-106`.
- Evidence: the pinned policy is "有 toolCall 但不可用**且文本为空** ⇒ 判错" and "名称匹配、以及「有 toolCall 但不可用且 text 为空」的判定，由共享的 `pickToolCall` 统一落实". But the signature has no text. `completeWithMeta` is deliberately name-agnostic: a `toolUse` reply with one structurally usable but name-mismatched toolCall and **non-empty** text returns `{text, toolCalls}` without throwing (suppression condition only requires one non-null-object-arguments toolCall). `pickToolCall(toolCalls, name)` cannot distinguish that valid text-fallback case from the empty-text error case.
- Impact: the implementer must either silently extend the signature (undocumented contract change) or throw on any name mismatch, which kills the fail-open text fallback for a mismatched call the design explicitly wants to keep; either way the "策略只一份" claim is false and the exact old duplication returns to the callers.
- Minimal fix boundary: pass the text (e.g. `pickToolCall(toolCalls, name, text)` / options bag), or make it return `{call, presentButUnusable}` and document the shared throw site; add the mismatched-toolCall+empty-text case to the I1 test (today's test only covers zero toolCalls).

**F2 — important — the merge left two stale name/accounting-ownership statements in 决策 7, contradicting the new shared abstraction.**
- Where: design lines 197, 198, 199 vs lines 251-255.
- Evidence: line 197 "「有 toolCall 但不可用且文本为空」仍由 pass 判为错误" and line 199 "名称匹配由 `autolearn/pass.ts` 自己判" directly contradict line 255 "名称匹配…由共享的 `pickToolCall` 统一落实" and line 252. Line 198 still cites the per-pass wrapper `autolearn/pass.ts:92-102` for `noteModelSuccess`/`noteModelFailure`, while line 196 says the wrapper exists only once in `callAux`. These lines were consistent with rev15 and are now stale (they were not in the amendment's merged 接口改动 pair, so the "two bullets merged" claim didn't reach them).
- Impact: an implementer reading 决策 7 (the autolearn section) can legitimately implement name matching and failure accounting in `autolearn/pass.ts`, re-creating exactly the duplication the amendment forbids; the test plan has no case that would catch the divergence.
- Minimal fix boundary: rewrite/delete lines 197 and 199 to reference `pickToolCall`/`callAux`, and state at line 198 that the pass wrappers stop calling `noteModel*` themselves.

**F3 — important (one-line fix) — `callAux`'s pinned options cannot carry the accounting identity its guarantee requires.**
- Where: design line 251 vs `shared/call-policy.ts:66,99` (`noteModelFailure(scope, projectRoot, error)`, `noteModelSuccess(scope, projectRoot)`) and `autolearn/pass.ts:92-102` / `memory/pass.ts:83-96`.
- Evidence: `callAux(ctx, prompt, { model, maxTokens, tools, state })` promises "`noteModelFailure` 只在两次都失败后记一次", but nothing in the signature supplies `scope`/`projectRoot`, and the design says only that `state` holds the sticky switch. `ctx` has no project root (`getProjectRoot(pi, ctx.cwd)` needs `pi`); callers already compute `projectRoot`. It also does not say callAux owns `noteModelSuccess` (the existing wrappers call it on every success, and failure counts reset only because of it).
- Impact: as written the single shared helper cannot deliver its pinned guarantee; the implementer must add parameters or re-split accounting — a design-level decision left unpinned.
- Minimal fix boundary: put `{ scope, projectRoot }` in the options/state bag and state that `callAux` owns both `noteModelSuccess` and the single post-both-attempts `noteModelFailure`; pass-specific side effects (`throttle.set`) stay in the caller's catch.
- Note on the question asked: sticky state *is* genuinely per-pass. `memory/pass.ts` makes up to 3 calls (initial :104, retry :121, condense :134) all inside one `consolidateProjectState` invocation; `autolearn/pass.ts` makes up to 3 (first look :117, evidence :127, plus the new length retry) inside one `run()`. A pass-local state object is sufficient, and the "once after both attempts" count is satisfiable inside one helper — once the identity issue above is fixed.
