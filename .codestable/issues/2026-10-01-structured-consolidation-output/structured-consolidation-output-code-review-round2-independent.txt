## 2. New findings (by severity)

**R2-B1 — BLOCKING: `isHeadingOnlyDocument` only strips one exact fence form, so a heading-only reply still overwrites memory.**
`memory/sections.ts:156-165`:
```ts
.replace(/^```(?:markdown)?\s*/i, "")
.replace(/\s*```\s*$/, "")
…
return lines.every((line) => line.startsWith("#") || isMemoryTruncationLine(line));
```
It treats every non-`#` line as content, so ` ```md `/` ```json ` info-string fences, `~~~` fences, a `---` frontmatter line, a prose preamble, ZWSP/soft-hyphen-only lines (`"# Project Memory\n\n## Project\n\n## Invariants\n\n## Pitfalls\n\n## Index\n"` prefixed by `"\u200b\n"` → `false`) and thematic breaks all defeat the gate. `report.ts:111` then sets `memoryChanged=true` and `recordMemoryDocument` replaces the file; the toast/reply say "Project memory and context updated." (`report.ts:390`). Probe `bypass-full.mjs`: all of `md-fence`, `json-fence`, `tilde-fence` overwrote; `adversarial.mjs` shows the same for the condense-adoption guard at `pass.ts:260` (first capped result discarded, N3 variants not covered). The existing test only pins ` ```markdown ` (`tests/sections-test.mjs:269`). Fix direction: normalise each line, strip any fence family/info string, and require at least one line that either contains `[\p{L}\p{N}]` or is a `- ` bullet.
Also note: `isHeadingOnlyDocument("*".repeat(60)) === false`, so a ≥40-char content-free separator is still adoptable/writable — that one is design-sanctioned decision-6 `>=40` for opaque, but the fence/preamble cases are exactly the B1 class the design amendment was meant to close.

**R2-I1 — IMPORTANT: `/memory update` still claims a memory write when the opaque memory was not written.**
`report.ts:182` sets `memoryKept: outcome.semanticEmpty`, but the write decision is `memoryChanged` (`report.ts:111`). For a short opaque reply (`memoryText.length < 40`, so `memoryChanged=false`) plus a usable context, `report="updated"`, `consolidateReply` takes neither the `memoryKept` branch (`report.ts:376`) nor the clipped branch and returns `"Project memory and context updated."` (`report.ts:390`) — while `MEMORY.md` is byte-identical. Probe `adversarial.mjs` E2E 3: reply `{memory_markdown:"Short note.", context:{…}}` → memory unchanged, command reply `"Project memory and context updated."`; the toast (`report.ts:202`) is correctly "memory was kept unchanged". `memoryKept` should be `!memoryChanged` (or carry the actual write flag) so the reply is truthful for every not-written reason.

**R2-I2 — IMPORTANT (design conformance): the opaque semantic gate is not a recorded deviation.**
The frozen decision 6 explicitly says "降级·不可解析沿用 `>= 40`" and round 1's fix boundary required a recorded design amendment. The fix table records B1, but the design's "实施期修订" (`design.md:391`) and the D-list still only mention D1–D6; frozen decision 6 still sanctions writing opaque `>=40` replies. The code now diverges (a good change) without the amendment the owner asked for. The same applies to N3's `!condensedEmpty` additive condition. Either record D7 (and update decision 6) or revert the gate to the frozen contract.

**R2-N1 — NIT: the line-start `#` heuristic rejects content-bearing opaque lines.**
`isHeadingOnlyDocument("#1 rule must hold") === true`, `("# Project Memory uses Postgres") === true`. Fail-safe (existing memory is kept), but on a fresh project no diagnostic is emitted (the "carried no entries" log is gated on `existing.text` at `pass.ts:287-289`), so a real first memory can be discarded silently as "Consolidation ran but produced no new memory or context."

**R2-N2 — NIT: D6 record is internally inconsistent** (see N7 row): note says 294→288; design says 294; actual reason field is 166 and tool description 294. No code impact.
