## Findings

### F4-1 — blocking — 决策 6’s gate is conjunctive on “no usable context”, so the N1 wipe survives whenever the reply carries a context
- Where: design 决策 6 (lines 129–134), esp. line 132; code `memory/report.ts:73`, `:84`, `:92–114`.
- Evidence: the rule fires only for “四个节**全空**且无可用 context”. But `memoryChanged = memoryText.trim().length >= 40` (`report.ts:73`) is evaluated independently of context, and `update = outcome.result.context ?? …` (`report.ts:84`) is written regardless. Probe: the headings-only render is **66 chars** (`"# Project Memory\n\n## Project\n\n## Invariants\n\n## Pitfalls\n\n## Index\n"`, trimmed 66) → `memoryChanged = true`; `memoryDocumentChars = 66 ≤ cap` → not a cap event. A schema-legal structured reply `{memory:{project:[],invariants:[],pitfalls:[],index:[]}, context:{…}}` therefore fails the gate (context usable) and `recordMemoryDocument` replaces MEMORY.md with the skeleton — exactly the round-3 N1 data-loss path. On this repo’s own MEMORY.md the old side is unparseable (`unknown section ## Documentation and review conventions`, probed), so the guard skip makes it silent. The N1 test (line 227) says “`{project:[],…}` 的合法回复 → 盘上记忆字节不变”, but the schema requires `context`, so if the mock carries one the stated rule fails the test; if it omits one, the test is weaker than the schema-legal case.
- Impact: the most plausible “nothing durable, but session state exists” reply still wipes memory down to four headings. The fix claims to close N1 but closes only the conjunction branch.
- Minimal fix boundary: key the **memory-write** gate on “all four adopted sections empty” alone — never write the skeleton; keep existing memory; treat the whole pass as `unchanged` only when there is also no usable context. Define “可用 context” explicitly (`result.context !== undefined` vs `contextUnusable`). Add both tests: empty-sections+context and empty-sections+no-context.

### F4-2 — important — Gate/guard placement and the pass→report carrier contract are unpinned; the gate cannot retract the guard’s removal warning
- Where: design 决策 5 line 120 vs 决策 6 line 132; `memory/pass.ts:17–22` (`ConsolidateOutcome = { result, version, clipped }`); 接口改动 lines 183–194.
- Evidence: the guard “在渲染器裁剪之前比较…实际采纳写入的 sections” runs in the pass, pre-render, and always emits a warning (`决策 5`), while 决策 6 says the gated case is “不写、**不告警**”. The emptiness/sections/dropped/kind are not in `ConsolidateOutcome`, and 接口改动 never says how they reach `report.ts`. An implementer following the doc emits “N invariants removed” for a pass that writes nothing, or has to invent the boundary the design left open.
- Impact: the “不告警” promise and the guard behaviour contradict; report.ts cannot honour the gate without new outcome fields the design doesn’t define.
- Minimal fix boundary: state that the gate is computed on adopted sections and carried (e.g. `semanticEmpty`), that `report.ts` forces `memoryChanged=false` when gated, that the guard is skipped when gated, and extend `ConsolidateOutcome` with the carriers (`sections`, `sectionDropped`, `itemTruncated`, `neededChars`, `kind`).

### F4-3 — important — N5 split contradicted inside 决策 4 itself (three different `dropped` contracts)
- Where: design 决策 4 lines 110, 115, 116; tests lines 220/223.
- Evidence: line 110 introduces “分开的两个计数：`sectionDropped` 与 `itemTruncated`…外加 `neededChars`”; line 115 keeps “返回 **`{ text, dropped }`**”; line 116 says “被截的项计入**同一个 `dropped`**”. The B1 test (line 220) still asserts `dropped>0`, and no test asserts item-only truncation produces cause-correct wording / no `raise max-memory` advice.
- Impact: implementer and verifier disagree on the renderer contract and cap-event semantics — the exact ambiguity N5 asked to remove.
- Minimal fix boundary: pin one shape (e.g. `{ text, sectionDropped, itemTruncated, neededChars }`); restate B1 as cap event = `sectionDropped>0 || itemTruncated>0`, condense trigger = `sectionDropped>0`; add an item-only diagnostic test.

### F4-4 — important — `neededChars` is the wrong number for share-based section clipping, so the cap-raise advice under-delivers
- Where: design 决策 1 (per-section budgets) + 决策 4 line 110; `memory/schema.ts:44–46` (shares of the cap).
- Evidence: budgets are hard per-section shares, so a section overflows its share while the untrimmed document is still ≤ cap. Example: Invariants 20 000 chars, other sections empty, cap 32 000 → share budget ≈ 12 769, `sectionDropped>0`, untrimmed length ≈ 20 076 < cap; `raise max-memory 20000` still clips Invariants to 40 % of 20 000 = 8 000. The cap that would fit it is ≈ 50 100. The old whole-document 60/40 path did not have this skew, so this is introduced by the per-section renderer.
- Impact: the operator follows the design’s own warning and still loses content; “cause-correct advice” is only half-fixed.
- Minimal fix boundary: compute `neededChars` as the cap at which no section overflows (`max_s(content_s / share_s) + overhead`), or reword the section-overflow advice away from a numeric cap.

### F4-5 — nit — N9 contradiction: llm.ts is told not to own the name policy, then given the name in its throw-suppression predicate
- Where: design lines 183–184 (`shared/llm.ts` bullets).
- Evidence: line 183: “通用多态，不内置 `record_memory` 名称策略，N9：名称匹配与可用性判定留给 `pass.ts`”. Line 184: llm.ts suppresses the `toolUse`+empty-text throw only when “name 匹配 `record_memory` **且** arguments 是非 null 对象”. The round-3 caveat also stands: `pass.ts` cannot observe “有 toolCall 但不可用” through the generic return shape unless the definition is restated as “no usable toolCall + empty text”.
- Minimal fix boundary: llm.ts suppresses on any usable `toolCall` part (non-null object args, name-agnostic) and returns them; `pass.ts` matches `record_memory` and throws on name-mismatch + empty text.

### F4-7 — suggestion — The gated empty-sections reply becomes an invisible no-op
- Where: design 决策 6 line 132 (“不写、不告警”); `memory/pass.ts:87` (`noteModelSuccess` fires on any successful call).
- Evidence: a model that persistently returns empty section arrays now produces neither a write, a warning, an `errors.log` entry, nor a backoff — it looks indistinguishable from “nothing new”.
- Impact: diagnosability regression, though no data loss. Safe default is retained.
- Minimal fix boundary: keep the no-write behaviour but log a plain diagnostic when existing memory was non-empty.

## Quality Bars

- **Over-engineering**: acceptable. The split counts and kind discriminator are justified by the B1/N5 loss path; the guard’s accepted false positives are documented.
- **Unclear boundaries**: `llm.ts` vs `pass.ts` name/usability policy (F4-5); `pass.ts` vs `report.ts` carriers for gate/guard/dropped/kind (F4-2/F4-3).
- **Unstated assumptions**: definition of “可用 context” and “全空”; where the gate is evaluated relative to the guard; unit of `itemTruncated` (count vs chars); condense-adoption predicate under the section renderer (what if the condensed reply still has `sectionDropped>0`, only item truncation, or is unparseable and falls to opaque).
- **Scope creep**: none found. S4, configurable CONTEXT cap, CONTEXT read-side migration, vault/encryption/archive upload and command renaming remain excluded; the strict compat config is owner-decided and does not change the pass contract.
