# Findings

## IMPORTANT

### F1. I3 is narrowed, not closed: the boundary probe only protects the last 256 bytes; the issue record claims full remediation
`extensions/project-context/archive/session-log.ts:75-92` and `:204-212`; test `tests/sync-test.mjs:274-280`; claims at `.codestable/issues/2026-09-30-session-log-append-duplication/session-log-append-duplication-fix-note.md:29-30,38,69`.

**Evidence (probes in `/tmp`, current code):**
- P-C2: source > 256 B, archive copied, then same-inode same-size `writeFile` changing only byte 0 of a 400-char field (the change is outside the last-256 window). After the next refresh `archive === source` is **false** and the archive still contains the old bytes (`archiveStale=true`). The guard passes, `sourceStat.size > cursor.dest.size` is false, so the call sets `appended=true` and the stale archive is never healed.
- P-D2: same-inode rewrite changing only early bytes plus an appended tail. Probe passes; the new tail is appended to the stale prefix → `archive === source` **false**, archive still starts with the old content.
- P-F: a difference 300 bytes from the end is **not** detected; a difference 255 bytes from the end is detected — confirming the window is exactly `[size-256, size)`.

**Impact:** a same-inode rewrite that keeps the last 256 bytes and does not shrink still yields a silent chimera — the precise failure class of prior finding I3. Practical likelihood is low for a normal append-only harness log, but the fix note's "同 inode 覆盖写检测" / "本轮已全部修复" (`fix-note.md:29,69`) and the test name "a growing in-place rewrite rebuilds" (`sync-test.mjs:280`) overstate what is guaranteed; the limitation only appears in the residual section (`fix-note.md:63`).

**Minimal fix boundary (do not implement here):** either (a) qualify the fix note/test name to "growing in-place rewrite whose last 256 bytes changed" and add a tail-preserving rewrite test that pins the documented bound, or (b) if full closure is required, verify the whole source prefix (content or maintained rolling hash) before appending — an O(n) per-refresh cost that must be an explicit design decision. A cheap full-coverage alternative does not exist; a source size+mtime stamp cannot work because every append changes it.

### F5. Comment scope vs `trim()` fallback; extra rewrites on trim-empty sources
`session-log.ts:209` (guard uses `cursor.dest.size`) vs `:229-236` (fallback for `existingRaw.trim()` empty). For a whitespace-only or unreadable source, the first refresh registers a cursor whose `dest.size` (synthesized header+entries) exceeds the 1-2 byte source, so every subsequent refresh fails `dest.size <= sourceStat.size` and rewrites the archive. Probe P-D: `rewrite-on-refresh=true`. Pre-fix code (`git show 42f0956:...session-log.ts:153`) no-op'd in this case, so this is a behavior change introduced by the remediation. No corruption (the synthesized content is refreshed from entries), and real session files are never whitespace-only; the comment says "empty/unreadable" while the condition is trim-empty. Minimal: state "trim-empty" in the comment, or skip cursor registration for trim-empty sources.

## SUGGESTION

### S1. Compare bytes, not decoded strings, in the boundary probe
`session-log.ts:87-91` does two UTF-8 decodes and compares strings. Two different malformed byte runs can decode to the same `U+FFFD` string, so a rewrite that mutates invalid bytes inside the window could still pass. Comparing `Buffer`s is also cheaper. Minimal: have `readSlice` (or a sibling) return `Buffer` for the probe and compare `equals`.

### S2. A probe read error aborts the write instead of forcing a rebuild
`session-log.ts:83-92`: if the source or archive disappears between `stampOf` and the probe's `open`, `readSlice` rejects and `writeSessionArtifacts` rejects (new archive-side failure window). Treating a failed probe read as "not intact" (rebuild) would be strictly more robust.

### S3. `readRange` is now a one-line wrapper
`session-log.ts:71-73`: `readRange(file, start)` adds no semantics over `readSlice(file, start)` and has exactly one caller (`:217`). Removing it reduces indirection.
